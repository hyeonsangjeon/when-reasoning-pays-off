# Site structure, i18n, and publish flow

![Locale pages linked by reciprocal hreflang alternates around a canonical English page, plus x-default.](assets/i18n-locale-hreflang-graph.svg)

This directory is the static source for the project's GitHub Pages site. It is
served verbatim (the `.nojekyll` marker disables any server-side processing),
so every page is plain HTML, CSS, and a tiny progressive-enhancement script.
There is no build framework and no runtime data fetching — all content is
authored or pre-rendered.

## Directory layout

```
docs/
  .nojekyll            disables Jekyll; serve files as-is
  index.html           root: detects the browser language and redirects to a
                       locale, degrading to English without JavaScript
  assets/
    hero.svg           the single evergreen hero visual (also used by the README)
    styles.css         shared styles
    i18n.js            progressive enhancement only (active-language highlight)
  en/index.html        English content (authored)
  ko/index.html        Korean content (authored)
  ja/index.html        Japanese (authored translation)
  zh-CN/index.html     Simplified Chinese (authored translation)
  hi/index.html        Hindi (authored translation)
  i18n.md              this document
  validate.sh          static validation + leakage grep (see below)
```

## Per-page release metadata (docs/16 §8.4 / §8.5)

The release policy (`docs/16-release-tiers-and-redaction-policy.md`, §8.4
"Per-surface gates") requires each published locale page to carry
machine-readable internationalisation metadata. Every locale `index.html`
therefore declares, in its `<head>`:

- a `canonical` link;
- `hreflang` alternates for every published locale (`en`, `ko`, `ja`,
  `zh-CN`, `hi`) plus `hreflang="x-default"` (which points at English);
- `<meta name="i18n:translation-status">` — one of `translated`,
  `machine_translated`, `stale`, or `untranslated_fallback_to_en`;
- `<meta name="i18n:last-translated-at">` — an ISO `YYYY-MM-DD` date;
- `<meta name="i18n:source-content-sha256">` — the SHA-256 of the English
  canonical source content the page was translated against.

| Locale tag | Language            | Translation status            |
| ---------- | ------------------- | ----------------------------- |
| `en`       | English             | `translated` (canonical)      |
| `ko`       | Korean              | `translated`                  |
| `ja`       | Japanese            | `translated`                  |
| `zh-CN`    | Simplified Chinese  | `translated`                  |
| `hi`       | Hindi               | `translated`                  |

### Source-content hash and stale detection

The canonical source content is the inner content of the single `<main>`
element of `docs/en/index.html`. `validate.sh` recomputes its SHA-256 and
compares it to the `i18n:source-content-sha256` recorded on every page.
Because metadata lives in `<head>` (outside the hashed region), updating the
metadata does not perturb the hash. When the English content changes, the
recorded hash no longer matches and the validator fails the page as **stale**
— matching the §8.5 stop-the-release condition. Remediate by re-translating
(or re-confirming the fallback) and updating the recorded hash on every page
to the new English value.

To recompute the hash after an English content edit:

```sh
awk '/<main>/{f=1;next} /<\/main>/{f=0} f' docs/en/index.html | shasum -a 256
```

Then update the `i18n:source-content-sha256` meta on all five pages.

### Glossary

Each page carries a `<section class="glossary">` covering the fixed term set
the policy mandates — *Foundry*, *PTU*, *PAYG*, *reasoning*, *cache*, *429* —
with a per-locale translation. Each entry is tagged with a locale-agnostic
`data-term` key (`foundry`, `ptu`, `payg`, `reasoning`, `cache`, `429`) so the
validator can confirm coverage without inspecting translated prose.

### Route casing note

The Simplified Chinese route is served from `docs/zh-CN/` (matching the
BCP-47 `lang`/`hreflang` tag `zh-CN`). The policy writes the route as
`/zh-cn`; the repository's canonical, validator-enforced casing is `zh-CN`.

## Internationalisation pattern

There is exactly one pattern: **one directory per locale at the site root**,
named with the BCP-47 tag used in the page `lang` attribute.

| Locale tag | Language            | Status      |
| ---------- | ------------------- | ----------- |
| `en`       | English             | authored    |
| `ko`       | Korean              | authored    |
| `ja`       | Japanese            | authored    |
| `zh-CN`    | Simplified Chinese  | authored    |
| `hi`       | Hindi               | authored    |

Rules:

- Each locale has its own `index.html` under `/<locale>/`.
- Every page carries the same language switcher: plain `<a>` links to each
  sibling locale, so navigation works with JavaScript disabled. The current
  language is marked with `aria-current="true"` in the static HTML.
- `English` is the canonical fallback. The root `index.html` redirects unknown
  or unsupported browser languages to `/en/`, and the `<noscript>` path does
  the same without JavaScript.
- Every published locale page is structurally complete and content-complete:
  header, switcher, hero, the lede, the "short answer" cards, the audience
  note, the research-artifact banner, a localised glossary, the per-page
  release metadata, and a link out to the GitHub repository. English remains
  the canonical fallback for unknown or unsupported browser languages.
- To add a locale: create `/<tag>/index.html` from an existing page, add the
  tag to the `SUPPORTED` lists in `index.html` and `assets/i18n.js`, and add a
  switcher link to every page.

## Validation / build command

This site has no compiler. The single introduced check is:

```sh
bash docs/validate.sh
```

It verifies that every declared locale has an `index.html`, that each language
switcher links to locales that exist, and that the hero asset is present. It
also enforces the per-page release metadata required by `docs/16` §8.4: a
canonical link, `hreflang` alternates for every locale plus `x-default`, a
machine-readable translation status, a `last_translated_at` date, and a
`source-content` SHA-256 that still matches the English canonical content
(a mismatch fails the page as stale, per §8.5), and that each page's glossary
covers the fixed term set. It then runs a leakage grep over the public-safe
surface and invokes the existing repository public-surface check when
available. The check is also wired into the project's CI workflow.

## Publish flow (mirror → Pages)

1. Author or update content in this directory only; keep it static and
   dependency-light.
2. Any data or asset promoted into this public mirror must already be
   sanitized or aggregate-only before it is added here — never publish raw
   per-request data.
3. Run `bash docs/validate.sh` locally and ensure it passes.
4. The maintainer enables GitHub Pages with the source set to **the default
   branch, `/docs` folder**. The site is then served at the project Pages URL.
5. The mirror keeps its own independent history; nothing is imported from the
   separate source history.
