同じトークン単価、異なる請求額

あるチームがワークロードを推論モデルへ移行したところ、トークン単価は以前と 変わらない一方で、新しい設定項目が一つ加わりました。推論強度です。この値を 上げても、ほとんどコストはかからないように見えます。それなら常に最大にして、 最良の回答を引き出せばよいと思うかもしれません。ところが、目に見える出力は ほぼ変わらないのに、請求額だけが増えます。原因は、表に出ない「思考」トークンです。 推論モデルはこのトークンを生成し、その分も課金しますが、応答には表示しません。 本プロジェクトでは、代表的な小規模タスク群を対象に、追加トークンがいつコストに 見合い、いつ請求額を膨らませるだけなのかを測定します。

チームにとって重要な理由

モデル移行後、エンジニアが直面する問いは明確です。なぜコストが変わったのか。 なぜレイテンシが変化したのか。なぜスロットリングが増えたのか。推論強度は、 この 3 つすべてに影響します。既定値を高くすると、利用者には見えない内部計算に トークンが消費されます。従量課金では実際の費用が増え、プロビジョニング済み容量 では貴重な余力が減ります。推論強度が実際に回答を変える地点を把握していれば、 確信を持ってロールアウトし、想定外の請求を避けられます。

何を測定したか

プロンプトとワークロード区分を固定したまま、短い事実回答、構造化データの 自然言語変換、多段階推論、ツールを使用するエージェントの 4 区分に、同じ 推論強度の段階を順に適用しました。すべての呼び出しについて、入力・キャッシュ・ 推論・出力の各トークンに加え、品質シグナルとレイテンシも含む使用量全体を 記録しました。この実測したトークン構成をもとに、同じワークロードが 従量課金（PAYG）とプロビジョニング済みスループット（PTU）でそれぞれ どのように課金されるかをモデル化し、比較しました。

測定結果

結果は区分によって異なりました。推論強度がコストに見合う区分もあれば、 見えない計算コストだけが増える区分もありました。ただし、次の 4 つの教訓は すべての区分に共通します。

推論トークンは必ず測定する

推論トークンは課金対象ですが、応答には返されません。すべての呼び出しで、 入力・キャッシュ・推論・出力の各トークンを分けて記録してください。

すべてのタスクに推論が必要なわけではない

短い事実回答、構造化データの自然言語変換、単純な分類では、品質が 向上しないままコストだけが増えるケースが多く見られました。

推論強度は主要なコスト調整手段

推論強度は最も低いレベルを既定値とし、品質評価によって追加コストの 必要性を確認できた場合にのみ引き上げてください。

課金モデルによって効果が変わる

従量課金（PAYG）では、推論トークンを減らすと請求額が下がります。 プロビジョニング済みスループット（PTU）では、固定費は変わらず、 同じ削減がスループットの向上として現れます。

対象読者

Azure OpenAI のデプロイを運用し、推論を有効にするか、またどの程度の強度に するかを判断する方、容量を見積もる方、モデル移行後のコスト・レイテンシ・ スロットリングの変化を調査する方を対象としています。

これは製品ではなく、研究成果物です。 ホスティングサービスや SLA は提供していません。本リポジトリでは、再現可能なベンチマーク、方法論、 意思決定ツール、サニタイズ済みの結果の一部のみを公開しています。

用語集

Foundry
Microsoft Foundry：本プロジェクトで測定したモデルをデプロイし、 提供するためのマネージドプラットフォーム。
PTU
プロビジョニング済みスループット単位：トークン数ではなく スループットに対して料金を支払う、予約済み固定容量の課金方式。
PAYG
従量課金：入力・キャッシュ・推論・出力の各トークンに応じて 課金される、使用量ベースの課金方式。
推論トークン
推論モデルが生成する課金対象の内部「思考」トークン。応答には 返されません。
キャッシュ
プロンプトキャッシュ：以前に処理したプロンプトの接頭部を 再利用し、通常より低いキャッシュ入力単価が適用される仕組み。
429
HTTP 429 Too Many Requests：デプロイがレートまたは容量の 上限を超えたときに返されるスロットリング応答。
