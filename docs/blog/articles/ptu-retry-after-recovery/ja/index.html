運用エッセイ · PTU の回復と 429 ハンドリング

429 は単なるエラーではなく、回復シグナルである

飽和した PTU ターゲットからの 429 で、当てずっぽうのポーリングループを 始めるべきではありません。それはすでに、クライアントが必要とする回復シグナル retry-after-ms を含んでいます。運用上の問いは「呼び出しは失敗したか?」 ではなく、「次の判断を誰が持つか: 待つ、リダイレクトする、あきらめる」です。

問い

PTU 容量が「今はだめ」と返したとき、クライアントは次の手をどう判断すべきか?

根拠

Microsoft Learn がヘッダーの契約を定義し、公開集計の実行が、中央値だけの待機ではテールを取りこぼす理由を示します。

判断

リトライのオーナーを一つに絞ります。ヘッダーを尊重し、ジッターを加え、遅延ポリシーが要求するときだけリダイレクトします。

公式仕様 · サービスが何を伝えるか

ヘッダーがアドミッションシグナルである

Microsoft Learn は、PTU の高負荷ハンドリングを、retry-after-ms と retry-after レスポンスヘッダーを伴う即時の 429 経路として 説明しています。同じ本番ガイドは、この待機をクライアント側のリトライにも、 リクエストを別のサービングターゲットへリダイレクトするためにも使えると述べて います。

文書化されていること

retry-after-ms をサービス提供の待機値として扱います。 推測した固定のリセット間隔よりも強い根拠になります。

文書化されていないこと

待機値の背後にある正確な計算式は公開されていません。クライアント側で 決定論的なリセットモデルを発明しないでください。

運用上の推論

ヘッダーがすでに再試行のタイミングを伝えているなら、ヘルスチェックの ポーリングは通常、弱いシグナルに加えて余分なトラフィックとノイズの多い テレメトリをもたらします。

観測された根拠 · 公開集計のみ

中央値は小さく、テールはそうではなかった

この表の読み方

中央値は、多くの 429 が短命だったことを示します。p99 は、本番のラッパーには やはりテールポリシーが必要であることを示します: 遅延予算までしかスリープせず、 その後はリダイレクトするか、優雅に失敗します。バースト型と予約型の負荷は同じ 形には見えなかったため、ソースの分割が重要です。

運用パターン · リトライのオーナーは一つ

リトライループを積み重ねない

安全なパターンは、意図的に退屈です: 429 の回復を持つコンポーネントを ちょうど一つだけ選びます。SDK がリトライするよう構成されているなら、待機は SDK に任せます。アプリケーションのルーターが回復を持つなら、SDK の自動 リトライを無効化し、ルーターに retry-after-ms を直接パースさせます。

スリープ経路

呼び出しごとの遅延よりもスループットが重要なときに使います。ヘッダー値とジッターの分だけ待ってから、再試行します。

リダイレクト経路

PTU に留まることよりも遅延が重要なときに使います。429 が来たらすぐに標準ターゲットへルーティングします。

あきらめる経路

待機もリダイレクトもポリシーに違反するときに使います。リトライの嵐を隠すのではなく、制御されたレスポンスを返します。

フォールバック · ネイティブかカスタムか

リダイレクトはポリシーの選択であり、パニックボタンではない

Microsoft Learn のスピルオーバー機能は、超過トラフィックを標準ターゲットへ リダイレクトでき、スピルオーバーの挙動を識別するヘッダーを公開します。 プラットフォームがサポートする形が合致するなら、それが運用の手間が少ない 経路です。カスタムルーターは、PTU ターゲットが 429 を返す前にアプリケーションが 判断しなければならないとき、あるいはルーティングポリシーがテナント、リージョン、 遅延予算、ビジネス優先度に依存するときに、依然として有用です。

ネイティブスピルオーバー

単純なオーバーフローレーンが合致し、追加のルーティングロジックが価値以上にリスクを増やすときに最適です。

カスタムルーター

ユーザー遅延が費やされる前に、待機・リダイレクト・あきらめのどれを選ぶかをアプリケーションポリシーが決めなければならないときに最適です。

アンチパターン

SDK のリトライ + ルーターのリトライ + スピルオーバーは、試行回数を掛け算で増やしかねません。まず所有権を統合します。
