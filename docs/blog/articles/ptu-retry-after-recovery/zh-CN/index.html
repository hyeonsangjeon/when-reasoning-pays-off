运维随笔 · PTU 恢复与 429 处理

429 是一种恢复信号，而不只是一个错误

一阵流量突发把 PTU 部署推到 100% 利用率，调用开始以 429 返回。出于本能，你会想 伸手去抓三种做法中的一种——开一个健康检查轮询循环，直到看上去有容量空出来；用 一个凭空猜的固定计时器去重试；或者把一切立刻改投到别的目标上。这三种都假设： 客户端必须自己去猜什么时候重试才安全。事实并非如此——429 已经把那个答案放进了 retry-after-ms 头里。所以运维上的问题不是"调用失败了没有"，而是"下一个 判断由谁来做——等待、重定向，还是放弃"。

为什么要读头，而不是靠猜

那三种反射都共享一个隐藏假设——客户端无从知道容量何时空出来，所以只能去试探、 按固定间隔等待，或者干脆走人。在接受这个假设之前，值得把两件事并排放一下。第一 件是 Microsoft Learn 记录的：在 100% 利用率下，服务会立刻返回 429，并附上 retry-after-ms——服务给出的、关于何时重试的等待值。第二件是本仓库跨多次 源运行实际观测到的 retry-after-ms 值、经脱敏的公开聚合，用来描述这些被 建议的等待实际看起来是什么样。两者合起来，"何时重试才安全"就从客户端的猜测，变成 了服务返回给你的值。

值得停下来的，是这份聚合的形态。被建议的等待中位数很短——整体 p50 ≈ 43 ms。 所以健康检查循环或凭空猜测的固定间隔退避，通常会等得比服务真正要求的久得多。但长尾 不能忽视：极少数等待向着 17,000 ms 延伸（整体 p99 ≈ 16,921 ms）。 这种"中位数短、长尾长"的形态，正是运维上要紧的事实——头应当被当成准入控制信号，而 不是一个固定的复位时钟。立刻返回的 429 和 retry-after-ms 契约是 Microsoft Learn 记录的；"用一个统一的延迟预算上限来决定何时停止等待、转而重定向"，则是本仓库 愿意为之背书的运维推断。下面的源图把这个分布明示出来。

问题

当 PTU 容量返回"现在不行"时，客户端该如何决定下一步？

证据

Microsoft Learn 的预置吞吐量与溢出文档，以及本仓库 PTU 准入控制器的运维笔记。

决策

把重试的归属收敛到唯一一处：尊重头、加抖动，只在延迟策略要求时才重定向。

按问题阅读： 官方信号 服务行为 运维模式 重定向的选择 来源

范围说明： 本文陈述的，是截至访问日期 Microsoft Learn 记录的 PTU 429 准入契约，以及本仓库 愿意为之背书的一小组运维经验法则。这是一份给重试封装器用的运维手册，而不是对某个 具体部署的测量。文中展示的那一份观测到的 retry-after-ms 分布，是本仓库源 运行里经脱敏的公开聚合，仅用来说明被建议的等待并非恒定——它不是服务级别保证。

官方规范 · 服务告诉你的内容

头就是准入信号

Microsoft Learn 把 PTU 的高负载处理，说明为一条立刻返回 429、并附带 retry-after-ms 与 retry-after 响应头的路径。同一份生产指南 指出，这个等待既可用于客户端重试，也可用于把请求重定向到另一个服务目标。

有文档记载的

把 retry-after-ms 当成服务给出的等待值，它是比你猜的固定复位 间隔更强的依据。

没有文档记载的

等待值背后确切的计算公式并未公开。不要在客户端发明一个确定性的复位模型。

运维推断

如果头已经告诉你何时重试，健康检查轮询通常只会在弱信号之外，多带来额外 流量和噪声很大的遥测。

服务行为 · 等待为什么不恒定

等待是准入控制，而不是固定冷却

Microsoft Learn 把 PTU 利用率记录为一种漏桶算法：每个请求加上一份估算的计算 成本——提示 token 数减去缓存 token，再加上调用的 max_tokens——而已部署 的容量按 PTU 数量成比例地持续排空。如果请求到达时利用率已经是 100%，服务就立刻 返回 HTTP 429，并附上 retry-after-ms 与 retry-after 头，告诉你 在下一个请求被接纳之前要等多久。

因为等待反映的是那一刻漏桶正在如何排空，所以它不是固定的冷却时间。也正因如此，同一份 有文档记载的契约支撑的是两条而非一条客户端路径：当等待落在调用方的延迟预算之内时， 尊重头；当等待超出那个预算时，把它当作重定向或失败的条件。"用一个统一的预算上限来 区分这两条路径"，是本仓库愿意为之背书的运维推断；立刻返回的 429 与头契约，则是 Microsoft Learn 记录的。

推断（Tier 2）

"调用方设一个统一的延迟预算上限，超过它就从等待切换到重定向"，是本仓库的经验法则，而不是 Learn 规范。

运维模式 · 重试由唯一责任方负责

不要叠加重试循环

安全的模式刻意做得很无聊：只挑唯一一个组件来负责 429 恢复。如果 SDK 被配置为 重试，就把等待交给 SDK；如果应用的路由器负责恢复，就关掉 SDK 的自动重试，让 路由器直接解析 retry-after-ms。

睡眠路径

当吞吐量比单次调用延迟更重要时使用。按头值加抖动等待，然后重试。

重定向路径

当延迟比留在 PTU 上更重要时使用。一旦 429 到来，立刻路由到标准目标。

放弃路径

当等待和重定向都违反策略时使用。返回一个受控的响应，而不是把重试风暴藏起来。

回退 · 原生或自定义

重定向是策略选择，而不是惊慌按钮

Microsoft Learn 的溢出能力可以把超额流量重定向到标准目标，并暴露用于识别溢出行为 的响应头。如果平台支持的形态正好契合，那是运维负担更小的路径。当应用必须在 PTU 目标返回 429 之前就做判断、或者路由策略取决于租户、区域、延迟预算、业务优先级时， 自定义路由器仍然有用。

原生溢出

当简单的溢流车道正好契合、额外的路由逻辑带来的风险大于价值时最合适。

自定义路由器

当应用策略必须在耗掉用户延迟之前，就决定是等待、重定向还是放弃时最合适。

反模式

SDK 重试 + 路由器重试 + 溢出，可能把尝试次数乘起来。先把所有权收归一处。

本文证明了什么、又没证明什么。它记录了截至访问日期 Microsoft Learn 明示的 PTU 准入契约——100% 利用率下的立即 429、retry-after-ms 与 retry-after 头，以及溢出的重定向路径——以及本仓库愿意为之背书的一小组运维 经验法则——尊重头、为打散机群同步而加抖动、只有在尊重等待反复重试仍不缓解时才向溢出 部署重定向。它不验证该契约在所有区域、模型 SKU、未来 API 版本下都一致成立，也不对 某个具体部署做负载下的测量。

实用准则

实用准则：当 PTU 部署返回 429 时，把 retry-after-ms 当成准入 契约——尊重它，为打散机群同步而加抖动，只有在尊重等待反复重试仍不缓解时，才向溢出 部署重定向。
