运维随笔 · PTU 恢复与 429 处理

429 是一种恢复信号，而不仅仅是错误

来自饱和 PTU 目标的 429 不应触发盲目的轮询循环。 它已经携带了客户端所需的恢复信号：retry-after-ms。 要回答的运维问题不是“调用是否失败了？”，而是“谁拥有下一个 决策权：等待、重定向，还是放弃？”

问题

当 PTU 容量表示“现在不行”时，客户端应如何决定下一步？

证据

Microsoft Learn 定义了响应头契约；公开的聚合运行结果说明了为何只看中位数的等待会错过尾部。

决策

使用唯一的重试责任方。遵循响应头，加入抖动，只有在延迟策略要求时才重定向。

官方规范 · 服务告诉你的内容

响应头就是准入信号

Microsoft Learn 将 PTU 高利用率处理描述为一条带有 retry-after-ms 和 retry-after 响应头的即时 429 路径。同一份生产指南说明了这个等待时间 既可用于客户端重试，也可用于将请求重定向到 不同的服务目标。

有文档记录的内容

将 retry-after-ms 视为服务提供的等待值。 它比猜测的固定重置间隔更可靠。

没有文档记录的内容

等待值背后的确切公式并未公开。不要在客户端 臆造一个确定性的重置模型。

运维推断

如果响应头已经告诉你何时重试，那么健康检查轮询 通常是更弱的信号，并带来额外流量和更嘈杂的遥测。

如何解读此表

中位数表明许多 429 都很短暂。p99 则表明生产环境的 包装器仍然需要尾部策略：只在延迟预算内休眠， 然后重定向或优雅失败。来源拆分很重要，因为 突发形态和预留形态的压力并不一样。

运维模式 · 重试由唯一责任方负责

不要叠加重试循环

安全的模式有意做到平淡无奇：恰好选定一个组件来负责 429 恢复。如果 SDK 被配置为重试，就让它负责等待。如果 由应用路由器负责恢复，则禁用 SDK 自动重试，并让 路由器直接解析 retry-after-ms。

休眠路径

当吞吐量比单次调用延迟更重要时使用。等待响应头的值加上抖动，然后重试。

重定向路径

当延迟比留在 PTU 上更重要时使用。一旦 429 到达就路由到标准目标。

放弃路径

当等待和重定向都违反策略时使用。返回受控的响应，而不是隐藏重试风暴。

回退 · 原生或自定义

重定向是一种策略选择，而不是惊慌按钮

Microsoft Learn 的溢出（spillover）功能可以将超额流量重定向到 标准目标，并暴露用于标识溢出行为的响应头。 当平台支持的形态适用时，这是运维成本最低的路径。 当应用必须在 PTU 目标返回 429 之前就做出决定， 或当路由策略取决于租户、区域、延迟预算或业务优先级时， 自定义路由器仍然有用。

原生溢出

当简单的溢出通道适用，且额外的路由逻辑带来的风险大于价值时最佳。

自定义路由器

当应用策略必须在耗费用户延迟之前在等待、重定向和放弃之间做出选择时最佳。

反模式

SDK 重试加路由器重试加溢出会成倍增加尝试次数。先整合所有权。
