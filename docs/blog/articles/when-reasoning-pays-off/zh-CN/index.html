概览文章 · 推理强度、质量与支出

什么时候推理值得付费：同样的 token 单价，不同的账单

团队打开一个推理模型，看到的还是那张和过去几乎一样的按 token 计价表，却注意到 一个新的控制项：推理强度。最自然的直觉就是先把推理强度调高——既然多想一点几乎是 免费的，何不到处都争取更好的答案？可是，同一张价目表下，推理模型仍然可能产生 差别巨大的账单，因为强度花掉的是在模型内部生成、像普通用量一样计费、却从不 出现在回复里的 token。所以真正的问题不是“推理贵不贵”，而是“额外的强度在哪些地方能换来更好的答案， 又在哪些地方换来的只有隐藏的计算”——本系列就用数据来检验它。

我们为什么要检验这个

这个情形很常见。一次迁移把团队带到推理模型面前，配置里多了推理强度这个选项， 而按 token 计价看上去没什么变化——于是把强度调高，读起来就像一份防错的廉价 保险。想到处都调高，是合理的直觉；缺的只是一个判断：多出来的思考究竟有没有 到达读者，还是只到达了账单。

由此就有了一个干净、可以按不同任务类型逐一验证的假设：更高的推理强度到底是 真的能换来更好的答案，还是主要换来隐藏 token、延迟和成本？听从直觉，就意味着 上线一个偏高的默认值，为可能永远不改变输出的思考付费；先做测量，才能让我们 只在配对的质量信号真的动了的地方调高强度——在没动的地方则保持低位。

于是我们动手做了实测。我们固定住提示词与工作负载切片，让短事实回答、 多步推理、使用工具的代理这几类任务，各自套上同一套推理强度档位， 并在每次调用中记录 token 构成、延迟与成本。在这份实测数据之上，我们 再叠加一层建模出来的 PTU/PAYG 规划面。结果像好的证据应有的那样分化 开来：在短事实工作上，再调高强度多半只会带来隐藏的推理 token， 而不是更好的答案；不可见 token 的视角解释了为什么可见输出几乎没变、账单却动了； 多步工作在评审者真的动起来时可以值回成本；工具代理的质量常常撞上天花板，再加 强度只增加延迟；而 PTU/PAYG 交叉点始终是一个建模出来的规划阈值，而不是测得的 容量结果。下面各节用各自的主题图把这些细节逐一展开，证据仪表盘则是每个数字 背后的审计轨迹。

问题

额外的推理强度什么时候能带来可衡量的质量，什么时候只是带来隐藏计算？

证据

公开图表数据比较成本、评审分数、token 构成、延迟，以及建模得到的预留容量交叉点。

发现

在短事实任务上，成本涨到约 7.6 倍，平均评审分却没有上升——从约 1.88 移到约 1.78；而在多步任务上，则从 1.5 升到了 2.0。

决策

只有在评估结果真正变化时才提高推理强度；让证据仪表盘保留为文章背后的审计线索。

阅读约定 · 柱、坐标轴和表格

如何阅读本文中的图表

本文中的小柱状图是完整源图表的导读，不是频率分布直方图。每个柱子表示一个强度单元的聚合测量值：baseline、minimal、low、medium、high 或 extra-high。

X轴

X轴是运营者可以调节的推理强度等级。从左到右表示允许模型消耗更多内部推理工作。

Y轴

Y轴随图表而变：成本是每个请求的 USD，质量是评审分数，延迟是毫秒，token 构成是 token 数，交叉点是建模的每分钟请求数。

柱子

柱子更高并不总是更好。质量柱更高可能是好事；成本、延迟或推理 token 柱更高，则需要相应的质量提升来证明其合理性。

源表格

精确值、标准差和样本数请看仪表盘表格。正文只提取对决策最重要的形状。

主题 · 短事实回答

短事实任务通常不值得增加推理

如何阅读这张柱状图

X轴是推理强度。成本图的 Y轴是每个请求的平均 USD；配对质量图的 Y轴是平均评审分数。 因此，柱子的形状提出一个简单问题：更高支出是否换来了更高分数，还是只让账单变高？

为什么需要这张图

它检验最简单的迁移陷阱：团队把推理强度全局调高，然后发现任务大多只是短事实回答，却不知道账单为什么变了。

它意味着什么

在短事实任务中，minimal 强度的平均成本是每个请求 $0.000663。 Xhigh 强度的平均成本是每个请求 $0.005043，账单达到 7.6x。 平均评审分数则从 1.87931 变为 1.779661。

运营启示

更高强度可能带来更多隐藏计算，却未必带来更好的答案。短事实任务应从最低强度开始，只有质量门槛显示真实收益时才提高。

主题 · 不可见的计费面

推理 token 解释了账单差异

为什么需要这张图

可见回复可能几乎没有变化，但模型为了生成它可能消耗了大量内部推理 token。只看输出长度会漏掉这部分可计费工作。

它意味着什么

在短事实任务中，minimal 强度平均每个请求使用 3.655172 个推理 token。 Xhigh 强度平均每个请求使用 311.474576 个推理 token。

运营启示

仅靠答案文本看不到这种差异。生产预算需要拆分用量：输入、缓存输入、输出和推理 token。

主题 · 多步骤推理

多步骤任务中，推理可能值得付费

为什么需要这张图

这是对照案例：一个中间推理确实承载正确性的任务，因此较高强度值得试验。

它意味着什么

在多步骤任务中，非推理基线得分为 1.5。High 强度在每个请求 $0.00125 的成本下得到 2.0。

运营启示

只有当评估结果移动到足够重要时，推理才真正值回成本。先看质量，再判断边际支出是否合理。

主题 · 使用工具的代理

工具代理任务需要检查天花板效应

为什么需要这张图

工具代理看起来似乎需要更多思考，但有时真正困难的部分已经由工具调用承担了。

它意味着什么

如果图表已经显示天花板效应，提高推理强度可能主要增加内部 token 和延迟，而不是更好的答案。

运营启示

把推理强度当作受控实验，而不是默认值。代理型任务要先判断瓶颈是推理质量、工具选择、工具延迟，还是编排方式。

主题 · 容量规划

PTU/PAYG 交叉点是规划模型

为什么需要这张图

PAYG 和预留容量回答的是不同问题。这张图把包含推理的 token 形状转换成一个规划阈值。

它意味着什么

对于短事实 xhigh 行，PTU/PAYG 交叉点是在 50 PTU 底线下得到的 149 rpm 建模假设。 它不是实测 PTU 吞吐量。

运营启示

把这个数看作规划阈值，而不是容量证据。在 PAYG 下，减少推理 token 会减少可变支出。 在 PTU 下，同样的减少可能表现为固定预留内可容纳更多请求。

实用准则

实用准则：只在这种工作负载形态下评审者真的动了的地方才提高推理强度； 在把这笔花费投入生产之前，把每一条成本主张都与它配对的质量、延迟和 token 构成图 并排着读。
