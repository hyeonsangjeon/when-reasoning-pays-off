運用パターン・ループと予算ガバナンス (L6)・新しい測定ではなく設計

エージェント型ループ：天井チェックが「止めるべき」と言ったあと、実際にループを止めるのは誰か

対になるトピックは、すっきりした結論で終わる。ツールエージェントの品質が天井に張り付いたら、推論 effort を上げても得られるのはスコアではなくレイテンシとコストだ。だから、上限に届く最も低い effort に振り分ければよい、という話だ。単一の呼び出しなら、その助言はまったく正しいものだ。けれども現実のエージェントが、一度の呼び出しで終わることはめったにない。計画し、ツールを呼び、結果を読み、もう一度推論し、また回る。タスクがループになった瞬間、コストは価格表から読める一つの数値ではなく、ステップにわたる積分になる。そして誰もが最初に触りたくなる呼び出しごとの effort 設定は、実際にコストが積み上がっている部分にはもう届かない。このトピックは天井チェックのもう半分だ。「この呼び出しにさらに effort をかける価値があるか」ではなく、「ループはいつ止まり、それを誰が決めたのか」だ。

このパターンが必要になる理由

このトピックが必要になる午後は、たいていこんな形をしている。エージェントは すべてのデモを通る。ところが、ごく普通のサポートチケットが一つ来ただけで、 ループに入る — 検索し、読み直し、別のツールを呼び、少しだけ深く考え、もう一度試す — そして四十回のツール呼び出しのあとで答えを返す。答えは正しい。 ただし、そのタスクに見込んでいた予算の40倍がかかっていて、月次請求書を見るまで 誰も気づかない。何も失敗していない。例外も、500も、アラートもない。 そこが暴走ループの危ないところだ。請求書を読む直前まで、 それは正常に動いているエージェントに見えるのだ。

そのエージェントが期待を下回ると、反射的にいつもの方向へ進みがちだ — もう少し 長くループさせよう、もう少し深く考えさせよう。対になる天井チェックは、単一の 呼び出しで「もっと考える」が効かなくなる場所をすでに示した。このトピックが 扱うのは、呼び出しごとのレバーが触れられない部分、つまり呼び出しの回数だ。 こうしたワークロードを運用しているなら、おそらくすでに呼び出しごとの effort 設定を 上げ下げし、それだけでは効き切らないことを感じているはずだ。

  • reasoning_effort（レバー L4）は、一つの呼び出しの推論トークンに境界を引く。ループが何回呼び出すかについては何も言わない。
  • max_output_tokens（レバー L5）は、一つの呼び出しの出力に境界を引く。反復全体の累積支出には境界を引けない。
  • プロンプトキャッシュの安定性（レバー L3）は、一つのプレフィックスの入力コストを下げる。ループではステップごとに履歴が伸びるため、請求額が最も大きくなる局面ほどキャッシュできる割合が小さくなる。

だからといって、呼び出しごとのレバーが間違っているわけではない。単一の 呼び出しでは、今でも最初に取るべき正しい手だ。ただ、それらはループより一段下で 作用しているだけだ。能力の問い — モデルはループできるのか、百万トークンを 保持できるのか — は、そもそも難所ではなかった。難しいのはループを 統制することだ。しきい値、介入、評価、追跡可能性、そして所有だ。

これは新しい測定ではなく、設計として読む。 このトピックは Tier 2 運用パターンだ。新しく測定した量は導入しない。 ここで測定済みの根拠として使っているのは、対になるトピックにある benchmark-03 の天井 （実際に公開された結果）だけだ。そしてここで述べるすべてのループ制御は、 このリポジトリ自身の測定ランナーがすでに実装しているガードをそのまま流用したものだ — ベンチマークバッチ自体が、暴走させてはいけない無境界コストのループだからだ。 本番のループが実際にどれほど頻繁に暴走するのか、またそのステップ数の分布は、 ここでは測定していない。その誠実な境界は、下の出典セクションで 明示したままにしている。正準の詳しい解説は docs/18 — エージェント型ループの予算ガバナンスだ。

問い

タスクがモデル呼び出しのループなら、累積コストには何が境界を引き、その境界は誰が所有するのだろうか。

パターン

運用レバー L6：ステップ上限とコスト天井、フェイルクローズのブレーカー、評価に基づくエスカレーション、ステップ単位のコスト追跡可能性。

対になる根拠

測定済み：benchmark-03 の品質天井は 1.97–2.00 にあり、コストは $0.002762 → $0.003499、レイテンシは 2.9秒 → 3.8秒 へ上がった — ループが尊重すべきステップ単位の知見だ。

判断

実行する前にループに境界を引き、ブレーカーをフェイルクローズにし、すべての天井を、誰かがホットフィックスで引き上げられる定数ではなく、コミットされレビューされるポリシーとして扱う。

観点ごとに読む： しきい値 介入 評価 追跡可能性 ガバナンス 出典と根拠の境界

対になるトピック： ツールエージェントの天井チェックは 検出の半分だ — 単一の呼び出しがどこで改善しなくなるかを示す。この トピックは介入の半分だ — それでもループが支出を続けるとき、何がそれを止めるのだろうか。

暴走コストは数値ではなく積分だ

ループに驚かされるのは、その請求額が事前に価格づけできる数値ではなく、 ステップにわたる和だからだ。 

total_cost ≈ Σ_step ( input_tokens_step    × input_rate
                    + reasoning_tokens_step × output_rate
                    + output_tokens_step    × output_rate )

その和を、誰の予想よりも速く大きくするものが三つある。第一に、反復回数に 境界がないことだ。ハードキャップがなければ、収束しないループ — 不安定なツール、 あいまいなサブゴール、「正しくなるまで改善し続ける」という指示 — は、課金対象の 呼び出しを出し続ける。モデルの中にそれを止めるものはない。第二に、 コンテキストがステップごとに伸びることだ。各反復は、前のトランスクリプトに 新しいツール出力を足して次の入力として再送するため、後半のステップほど高価になる。 さらにプレフィックスが一バイトでも変わるとキャッシュが無効になり、そのステップは入力単価どおりに 請求される。第三に、effort がループ内で掛け算されることだ。高い reasoning_effort のデフォルトは、ステップ単位の推論トークンに ステップ数を掛けることになり、間違えるには最も高くつく場所だ。

呼び出しごとのレバーは、それぞれその和の一項には効く。けれども、 項の数や進行中の合計に境界を引くことはできない。 そこにループの隙間が開く。以下の五つの観点で、その隙間を閉じる。

しきい値 — ステップ上限と累積コスト天井

一つのタスクが、隣のタスクの 40倍 を静かに使ったとき、初めてこれにぶつかりる。

仕組み。 ループには、単一の呼び出しには不要な二つの境界が 必要だ。最大反復回数と、タスク全体に対する累積トークン／コストの天井だ。 どちらか一つだけでは漏れる。ステップ上限だけでは、各ステップが巨大な場合に 高価な暴走を許す。コスト天井だけでは、安価な無限スピンを許す。

対応。 タスククラスごとに、max_iterations の ステップ上限と hard_ceiling_usd の累積天井を宣言する。 天井は、安全に見える丸い数字ではなく、代表的なサンプルの p99 — ステップ数と タスク単位のコスト — から導く。どちらも保守的に設定し、根拠があるときだけ 引き上げる。

リポジトリ内の根拠。 scripts/run_benchmark.py は すでにまさにこれを行っている。事前見積もり （estimate_experiment_cost_usd）を MAX_COST_PER_BENCHMARK_USD でゲートし、実行中の hard_ceiling_usd を BudgetTracker データクラスで追跡し、ツールループには max_iterations 上限 （agent.max_tool_iterations）を置いている。docs/05-methodology.md §6 「Budget guards」は、これを単なる運用衛生ではなく方法論として扱う。「静かな 予算超過は、静かな実験スコープ変更でもある」。同じ文は本番にも当てはまる — 静かなループ超過は、そのタスクに許されたコストが静かに変わったということだ。

介入 — フェイルクローズするサーキットブレーカー

ループがエラーになる代わりに一晩中回り続けたとき、初めてこれに出会う。

仕組み。 しきい値がループの途中で越えられたら、ループは 決定的かつ目に見える形で止まらならない — ベストエフォートの部分回答に、 型のある「予算超過」シグナルを添えて返す — 静かに続けても、静かに切り詰めても いけない。その選択こそが、境界づけられたコストと暴走のすべての違いだ。

対応。 次のいずれかでループを中断するサーキットブレーカーを 作る。ステップ上限に達した、累積コストが hard_ceiling_usd に 達した、または進捗なし検出器が発火した — たとえば同じツール呼び出しの反復だ。 中断時には、終了理由を持つ型付きの終端レコードを出し、そのうえで呼び出し元が なお使えるものを受け取れるよう、最後に回答だけの呼び出しを一度行う。 フェイルクローズにする。迷ったときのデフォルトは停止であり、 継続ではない。

リポジトリ内の根拠。 ランナーは型付きの BudgetExceededError（「事前見積もりまたは実行中の合計が予算ガードを 破ったときに送出される」）を送出し、BudgetTracker.is_halted は 合計が天井を越えた時点で次の呼び出しの前に停止を強制する。プロセスは専用の EXIT_BUDGET コードで終了する。ツールループは同じ考え方の きれいなモデルだ。iterations >= max_iterations になると、 モデルに最終回答を出させるために tools= なしで最後の呼び出しを一度行い、 tool_loop_terminated="iteration_cap" を記録し、回復用の区間を 軌跡に追加する。理由を残すフェイルクローズのブレーカーだ。そのまま本番へ 取り入れられる。

評価 — 効く場所でだけエスカレートする

「ただもっと考えさせよう」が助けにならなくなっても、請求だけは続く日に、これがやって来る。

仕組み。 このリポジトリの中心的な結果は、中程度を超えて effort を 上げても、スコアではなくコストが増えるというものだ。benchmark-03 では、品質は effort の 段階全体で 1.97–2.00 付近の天井に保たれ、その一方でリクエスト単位のコストは $0.002762 から $0.003499 へ、レイテンシは 2.9秒 から 3.8秒 へ上がった。 ループでは、同じ知見が継続の判断を支配する。もう一ステップ進むこと、 あるいは次の呼び出しでより高い effort を使うことには、それだけの理由が 必要だ。

対応。 エスカレーション — もう一回反復すること、または次の 呼び出しで reasoning_effort を上げること — を安価な評価の後ろに置く。 ルーブリックのスコア、自己一貫性や信頼度のシグナル、明示的な停止チェックだ。 デフォルトは停止にし、評価に継続の理由を主張させる。そうすれば、終わりのない 「終わるまでループする」は、境界のある「評価が継続を正当化しなくなるまでループする」に 変わる。これは単一呼び出しのルーティング判断を、ループの形にしただけだ。

リポジトリ内の根拠。 scripts/run_judge.py は、 すべてのベンチマークで品質を採点している既存のルーブリック判定器だ。同じ形が、 自然な継続ゲートになる。1.97–2.00 の天井 （results/summary.md §3; benchmarks/03-tool-using-agent/analysis.md）は、ゲートのない 「もっと考えて、もう一度ループする」というデフォルトが、見返りのある地点を大きく 越えて支出を続けてしまうことを示す測定済みの根拠だ。

追跡可能性 — ループごと、ステップごとにコストを帰属させる

$40 のタスクを前にして、どのステップが原因だったのか言えないとき、初めてこの問題が表に出る。

仕組み。 帰属できないものは管理できない。タスク終了時の 単一の数値は、どのステップが暴走したのか、なぜそうなったのかを隠す。 ガバナンスには、安定したループ id にひもづくステップ単位のレコードが必要だ。 各レコードは、そのステップの使用量、進行中の累積コスト、残っている予算余力を 持つ。

対応。 docs/14-observability-schema.md の リクエスト単位の捕捉を、ループスコープのフィールドで拡張する。安定した loop_id / タスク id、単調増加する step_index、 ステップ単位の usage ブロック（すでに捕捉されている — reasoning_tokens、cached_tokens、…）、 cumulative_cost_usd、そして budget_remaining_usd だ。 ステップごとに JSONL の行を一つ出す。ループの請求額はその和であり、 budget_remaining_usd が初めて非正になる行が介入点だ。 終了時の step_index の平均だけでなく、分布に アラームを置く — 暴走は分布の裾に現れる。

範囲メモ（誠実な境界）。 それらのループスコープのフィールドは、 すでに出荷済みのものではなく次の増分だ。既存の PTURequestRecord — すでに request_idx と完全な usage ブロックを持つもの — と schemas/ptu_request_record.schema.json に差し込まれる。 今日のランナーは、すでに反復ごとの usage オブジェクトを一つの セルレベルの dict に合算し、反復ごとの軌跡を記録している。ループの追跡可能性とは、 そのロールアップを第一級にすることだ — 合計だけを残すのではなく、ステップ単位の 行を残す。

ガバナンス — 予算は所有される契約だ

そしてこれは、誰かがホットフィックスで天井を引き上げ、記録もないまま請求額だけが増えたときに起こる。

仕組み。 ステップ上限とコスト天井は、魔法の数字ではなく ポリシーだ。システムが何をしてよいかを決める他の契約と同じように、所有され、 バージョン管理され、レビューを通じて変更されならない。天井の引き上げは スコープ変更であり、そう感じられるべきだ。

対応。 タスククラスごとの予算ポリシーは、サービス中に散らばる 定数ではなく、コミットされた設定として宣言する。すべての天井変更をレビューし、 超過率 — ブレーカーがどれほど頻繁に発火するか — を第一級の SLO として追跡し、 天井の引き上げには方法論変更と同じ儀式を与える。 docs/16-release-tiers-and-redaction-policy.md のリリースガバナンスの 規律は、公開データに適用された同じ形だ。ここではそれを支出に適用する。

リポジトリ内の根拠。 GOVERNANCE.md は、予算ポリシーが 従う、所有された契約の変更管理モデルだ。そして docs/05 §6 の 「静かな超過 = 静かなスコープ変更」という規則は、天井変更を日常作業ではなく レビュー対象にするための一文だ。

出典と根拠の境界

このトピックでは二つのことが起きており、それらは別々の Tier にある。 測定済みの基準点 — benchmark-03 の天井 — は、監査できる公開結果だ。 ループガバナンスのパターンは運用設計だ。このリポジトリにすでに存在する プリミティブを再利用するが、それが防ごうとしている暴走挙動そのものは、 ここでは測定されていない。下の Tier は、文書化された入力が終わり、設計上の 推論が始まる場所を示している。

  • [1] Tier 1 — 方法論契約： このリポジトリ、docs/05-methodology.md §6 「Budget guards」。このパターンが一般化している、事前見積もりと実行中のハード天井による中断だ。「静かな予算超過は、静かな実験スコープ変更でもある」という規則は、§5 に持ち込まれるガバナンス上の姿勢だ。
  • [2] Tier 2 — 測定済みの対になる根拠（benchmark-03）： このリポジトリ、results/summary.md §3 および benchmarks/03-tool-using-agent/analysis.md。測定済みの天井の出典だ — effort の段階全体で品質は 1.97–2.00 の範囲にあり、その間にリクエスト単位のコストは $0.002762 → $0.003499、レイテンシは 2.9秒 → 3.8秒 へ上がった。これは、ループのエスカレーションゲートが尊重すべきステップ単位の知見だ。
  • [3] 運用パターン（測定済み Tier ではなく設計）： ループ制御は scripts/run_benchmark.py からそのまま流用している — BudgetTracker / hard_ceiling_usd、BudgetExceededError、EXIT_BUDGET、estimate_experiment_cost_usd が MAX_COST_PER_BENCHMARK_USD によってゲートされること、agent.max_tool_iterations、そして tool_loop_terminated="iteration_cap" — さらに scripts/run_judge.py のルーブリックゲートだ。正準の詳しい解説は docs/18 で、docs/09-operator-guide-one-page.md では運用レバー L6 として導入されている。
  • [4] 提案されている次の増分（未実装）： §4 のループスコープのフィールド — loop_id、step_index、cumulative_cost_usd、budget_remaining_usd — は、docs/14-observability-schema.md と schemas/ptu_request_record.schema.json を拡張する。これらは設計にすぎない。このトピックのどこでも、出荷済みだとは主張していない。
  • [5] 根拠ダッシュボード： 測定済みの対になる根拠は、レンダリングされた benchmark-03 品質・コストチャートとして監査できる。

このトピックが確立すること、しないことは次のとおりだ。このリポジトリで すでに動いているガードを使ってループに境界を引く方法を示し、継続するかどうかを 決めるときに測定済みの天井を尊重する。一方で、ループがどれほど頻繁に暴走するか、 タスク形状ごとのステップ数の分布、あるいはロングコンテキストのコストスケーリング曲線は 測定していない — docs/04 §4 は、ここにあるどのベンチマークも ロングアウトプット／ロングコンテキストのワークロードを測っていないと、すでに記録している。 それらは静かな主張ではなく、将来の暴走特性を測るベンチマークが埋めるべき誠実な空白として 扱う。

このパターンによって言えること

ループ作業で役に立つ文は、「もっと強く考えさせよう」でも「もっと長くループさせよう」でもない。「走らせる前にループに境界を引き、その境界を自分たちが所有するものにする」だ。

概説エッセイへ戻る

実践上の規則

  1. すべての複数呼び出しタスクに、一つではなく二つの境界を与える。代表的な p99 からサイズを決めた max_iterations のステップ上限と hard_ceiling_usd の累積天井だ。
  2. ブレーカーをフェイルクローズにする — 上限、天井、進捗なしのいずれでも、停止し、型付きの理由を記録し、ベストエフォートの部分回答を返す。
  3. すべてのエスカレーションを安価な評価の後ろに置き、測定済みの天井を尊重する。中程度を超えると、effort を上げてもスコアは上がらず、コストだけが増えた。
  4. タスク終了時の合計だけでなくステップ単位の行を残し、どのステップが暴走したのか名指しできるようにする。
  5. 予算をコミットされレビューされるポリシーとして保持する。超過率を SLO として追跡し、天井の引き上げにはスコープ変更と同じ儀式を与える。

実践上の規則：L1–L5 は各呼び出しに境界を引き、L6 はループに境界を引く。 ループが走る前にいつ止めるかを決め、その決定を、モデルがデフォルトで到達する何かではなく、 自分たちが所有する何かにする。

対になる天井チェックを読む
