エージェント型ループ：上限チェックのあと、実際にループを止めるのは誰か

対になるトピックの結論は明快です。ツールエージェントの品質が上限に達したら、推論強度を上げても評価スコアは上がらず、レイテンシとコストだけが増えます。そのため、品質基準を満たす最も低い推論強度に振り分けます。単一の呼び出しには適切な方針ですが、実際のエージェントが一度の呼び出しで終わることはまれです。計画し、ツールを呼び、結果を読み、再び推論するというループを繰り返します。タスクがループになると、コストは価格表から読める一つの数値ではなく、ステップごとの合計になります。呼び出しごとの推論強度の設定だけでは、呼び出し回数によって積み上がるコストを制御できません。本記事では、「この呼び出しの推論強度をさらに上げる価値があるか」ではなく、「ループをいつ止め、誰がその境界を決めるか」を扱います。

このパターンが必要になる理由

このパターンが必要になる状況は、たいてい次のようなものです。エージェントは すべてのデモに合格します。ところが、通常のサポートチケットを一つ処理しただけで、 ループに入ります。 — 検索し、読み直し、別のツールを呼び、少しだけ深く考え、もう一度試す — そして四十回のツール呼び出しのあとで答えを返します。答えは正しいものです。 ただし、そのタスクに見込んでいた予算の40倍がかかっていて、月次請求書を見るまで 誰も気づきません。例外も、500も、アラートも発生していないからです。 そこが暴走ループの危険な点です。請求書を確認するまでは、 正常に動作しているエージェントに見えます。

エージェントが期待を下回ると、「もう少し長くループさせよう」「もう少し深く 考えさせよう」と対応しがちです。対になる上限チェックでは、単一の呼び出しで 「もっと考える」ことの効果がなくなる地点をすでに示しました。本記事が扱うのは、 呼び出しごとのレバーでは制御できない、呼び出しの回数です。

  • reasoning_effort（レバー L4）は、一つの呼び出しの推論トークンを制限しますが、ループの呼び出し回数は制限しません。
  • max_output_tokens（レバー L5）は、一つの呼び出しの出力を制限しますが、反復全体の累積支出は制限できません。
  • プロンプトキャッシュの安定性（レバー L3）は、同じプレフィックスの入力コストを下げます。ループではステップごとに履歴が伸びるため、請求額が最も大きくなる段階ほどキャッシュ可能な割合が小さくなります。

呼び出しごとのレバーが不要なわけではありません。単一の呼び出しでは、今でも 最初に調整すべき手段です。ただし、ループより一段下の層で作用します。難しいのは、 モデルがループできるかではなく、しきい値、介入、評価、追跡可能性、所有権によって ループを統制することです。

これは新しい実測ではなく、設計として読んでください。 このトピックは Tier 2 運用パターンです。新しい実測値は導入しません。 実測済みの根拠として使うのは、対になるトピックの benchmark-03 の上限 （公開済みの結果）だけです。ここで述べるループ制御は、 このリポジトリ自身の測定ランナーがすでに実装しているガードをそのまま流用したものだ — ベンチマークバッチ自体が、暴走を防ぐ必要のある無制限コストのループだからです。 本番のループが実際にどれほど頻繁に暴走するのか、またそのステップ数の分布は、 ここでは測定していない。その誠実な境界は、下の出典セクションで 明示しています。正準の詳しい解説は docs/18 — エージェント型ループの予算ガバナンスです。

問い

タスクがモデル呼び出しのループである場合、何が累積コストを制限し、誰がその境界を所有するのでしょうか。

パターン

運用レバー L6：ステップ上限とコスト上限、フェイルクローズのブレーカー、評価に基づくエスカレーション、ステップ単位のコスト追跡可能性。

対になる根拠

実測：benchmark-03 の品質は 1.97–2.00 の上限近くにとどまり、コストは $0.002762 → $0.003499、レイテンシは 2.9秒 → 3.8秒へ増加しました。ループが尊重すべきステップ単位の知見です。

判断

実行前にループを制限し、ブレーカーはフェイルクローズにします。すべての上限を、ホットフィックスで引き上げられる定数ではなく、コミットしてレビューするポリシーとして扱います。

観点ごとに読む： しきい値 介入 評価 追跡可能性 ガバナンス 出典と根拠の境界

対になるトピック： ツールエージェントの上限チェックは 検出を扱い、単一の呼び出しがどこで改善しなくなるかを示します。本記事は介入を扱い、 それでもループが支出を続けるときに何が止めるかを説明します。

暴走コストは一つの数値ではなく累積値です

ループの請求額は、事前に確定できる一つの数値ではなく、ステップごとに積み上がる合計です。 

total_cost ≈ Σ_step ( input_tokens_step    × input_rate
                    + reasoning_tokens_step × output_rate
                    + output_tokens_step    × output_rate )

その合計を予想以上に速く増やす要因が三つあります。第一に、反復回数に 上限がないことです。ハードキャップがなければ、収束しないループ — 不安定なツール、 あいまいなサブゴール、「正しくなるまで改善し続ける」という指示 — は、課金対象の 呼び出しを続けます。モデル自体にはそれを止める仕組みがありません。第二に、 コンテキストがステップごとに伸びることです。各反復では、前のトランスクリプトに 新しいツール出力を足して次の入力として再送するため、後半のステップほど高価になります。 さらにプレフィックスが一バイトでも変わるとキャッシュが無効になり、そのステップは入力単価どおりに 請求されます。第三に、推論強度によるコストがループ内で繰り返されることです。高い reasoning_effort のデフォルトは、ステップ単位の推論トークンに ステップ数だけ繰り返すことになり、誤った既定値の影響が最も大きくなります。

呼び出しごとのレバーは、それぞれ合計の一項を抑えます。しかし、 項の数や進行中の合計は制限できません。 以下の五つの観点で、この不足を補います。

しきい値 — ステップ上限と累積コスト上限

一つのタスクが、同種のタスクの 40倍 を気づかないうちに使ったとき、しきい値が必要になります。

仕組み。 ループには二つの境界が必要です。最大反復回数と、 タスク全体に対する累積トークン／コストの上限です。どちらか一つだけでは 不十分です。ステップ上限だけでは、各ステップが大きい場合の高額な暴走を防げません。 コスト上限だけでは、低コストの無限ループを防げません。

対応。 タスククラスごとに、max_iterations の ステップ上限と hard_ceiling_usd の累積上限を宣言します。 上限は、安全に見える丸い数字ではなく、代表的なサンプルの p99 — ステップ数と タスク単位のコスト — から導きます。どちらも保守的に設定し、根拠がある場合にだけ 引き上げます。

リポジトリ内の根拠。 scripts/run_benchmark.py は すでにこの仕組みを実装しています。事前見積もり （estimate_experiment_cost_usd）を MAX_COST_PER_BENCHMARK_USD でゲートし、実行中の hard_ceiling_usd を BudgetTracker データクラスで追跡し、ツールループには max_iterations 上限 （agent.max_tool_iterations）を設けています。docs/05-methodology.md §6「Budget guards」は、これを運用上の注意ではなく方法論として扱っています。 「気づかないうちの予算超過は、気づかないうちの実験スコープ変更でもある」という原則は、 本番にも当てはまります。

介入 — フェイルクローズするサーキットブレーカー

ループがエラーを返さず一晩中動き続けたとき、サーキットブレーカーが必要になります。

仕組み。 ループの途中でしきい値を超えたら、ループは 確実かつ目に見える形で停止する必要があります。ベストエフォートの部分回答に、 型のある「予算超過」シグナルを添えて返す — 静かに続けても、静かに切り詰めても いけません。この選択が、制限されたコストと暴走を分けます。

対応。 次のいずれかでループを中断するサーキットブレーカーを 実装します。ステップ上限に達した、累積コストが hard_ceiling_usd に 達した、進捗なし検出器が作動した — たとえば同じツール呼び出しを繰り返した場合です。 中断時には、終了理由を持つ型付きの終端レコードを出し、そのうえで呼び出し元が なお使えるものを受け取れるよう、最後に回答だけを生成する呼び出しを一度行います。 フェイルクローズにし、判断できない場合の既定値は継続ではなく停止にします。

リポジトリ内の根拠。 ランナーは型付きの BudgetExceededError（「事前見積もりまたは実行中の合計が予算ガードを 破ったときに送出される」）を送出し、BudgetTracker.is_halted は 合計が上限を超えた時点で次の呼び出し前に停止を強制します。プロセスは専用の EXIT_BUDGET コードで終了します。ツールループも同じ考え方です。 iterations >= max_iterations になると、 モデルに最終回答を出させるために tools= なしで最後の呼び出しを一度行い、 tool_loop_terminated="iteration_cap" を記録し、回復用の区間を 軌跡に追加します。停止理由を残すフェイルクローズのブレーカーであり、 本番にも同じ方式を適用できます。

評価 — 効果がある場合にだけエスカレートする

「もっと考えさせる」ことが役に立たず、課金だけが続く場合に評価が必要になります。

仕組み。 このリポジトリの中心的な結果は、中程度を超えて推論強度を 上げても、評価スコアは上がらずコストが増えるというものです。benchmark-03 では、品質は推論強度の 段階全体で 1.97–2.00 付近の上限に保たれ、その一方でリクエスト単位のコストは $0.002762 から $0.003499 へ、レイテンシは 2.9秒 から 3.8秒 へ増加しました。 ループでは、この知見を継続の判断にも適用します。もう一ステップ進むこと、 あるいは次の呼び出しでより高い推論強度を使うことには、それだけの理由が 必要です。

対応。 エスカレーション — もう一度反復すること、または次の 呼び出しで reasoning_effort を上げること — は、低コストの評価を通過した場合にだけ許可します。 ルーブリックの評価スコア、自己一貫性や信頼度のシグナル、明示的な停止チェックを利用できます。 既定値は停止とし、評価を通過した場合にだけ継続します。そうすれば、終わりのない 「終わるまでループする」は、境界のある「評価が継続を正当化しなくなるまでループする」に 変わります。これは単一呼び出しのルーティング判断をループに適用したものです。

リポジトリ内の根拠。 scripts/run_judge.py は、 すべてのベンチマークで評価モデルを実行し、品質を採点する既存のスクリプトです。同じ仕組みを 継続ゲートに利用できます。1.97–2.00 の上限 （results/summary.md §3; benchmarks/03-tool-using-agent/analysis.md）は、ゲートのない 「もっと考えて、もう一度ループする」というデフォルトが、見返りのある地点を大きく 超えて支出を続けてしまうことを示す実測の根拠です。

追跡可能性 — ループごと、ステップごとにコストを帰属させる

$40 のタスクで、どのステップが原因だったのか特定できない場合に、この問題が表面化します。

仕組み。 帰属できないものは管理できません。タスク終了時の 単一の数値では、どのステップがなぜ暴走したのかがわかりません。 ガバナンスには、安定したループ id にひもづくステップ単位のレコードが必要です。 各レコードは、そのステップの使用量、進行中の累積コスト、残っている予算余力を 記録します。

対応。 docs/14-observability-schema.md の リクエスト単位の捕捉を、ループスコープのフィールドで拡張します。安定した loop_id / タスク id、単調増加する step_index、 ステップ単位の usage ブロック（すでに捕捉されている — reasoning_tokens、cached_tokens、…）、 cumulative_cost_usd、そして budget_remaining_usd です。 ステップごとに JSONL の行を一つ出力します。ループの請求額はその合計であり、 budget_remaining_usd が初めて非正になる行が介入点です。 終了時の step_index の平均だけでなく、分布に アラームを設定してください。暴走は分布の裾に現れます。

範囲メモ（根拠の境界）。 これらのループスコープのフィールドは、 すでにリリース済みのものではなく、次の拡張案です。既存の PTURequestRecord — すでに request_idx と完全な usage ブロックを持つもの — と schemas/ptu_request_record.schema.json を拡張します。 今日のランナーは、すでに反復ごとの usage オブジェクトを一つの セルレベルの dict に合算し、反復ごとの軌跡を記録しています。ループの追跡可能性を 確保するには、合計だけでなくステップ単位の行を主要なデータとして残します。

ガバナンス — 予算は所有者のいる契約です

誰かがホットフィックスで上限を引き上げ、記録がないまま請求額だけが増えた場合に、ガバナンスが必要になります。

仕組み。 ステップ上限とコスト上限は、根拠のない定数ではなく ポリシーです。システムが何をしてよいかを決めるほかの契約と同様に、所有者を定め、 バージョン管理し、レビューを経て変更する必要があります。上限の引き上げは スコープ変更として扱います。

対応。 タスククラスごとの予算ポリシーは、サービス内に散在する 定数ではなく、コミットされた設定として宣言します。すべての上限変更をレビューし、 超過率 — ブレーカーがどれほど頻繁に発火するか — を主要な SLO として追跡し、 上限の引き上げには方法論変更と同じ手続きを適用します。 docs/16-release-tiers-and-redaction-policy.md のリリースガバナンスの 規律は、同じ仕組みを公開データに適用したものです。ここでは支出に適用します。

リポジトリ内の根拠。 GOVERNANCE.md は、予算ポリシーにも 適用できる、所有者のいる契約の変更管理モデルです。また、docs/05 §6 の 「静かな超過 = 静かなスコープ変更」という規則は、上限変更を日常作業ではなく レビュー対象にするための原則です。

出典と根拠の境界

このトピックでは、別々の Tier に属する二種類の根拠を扱います。 実測済みの基準点 — benchmark-03 の上限 — は、監査可能な公開結果です。 ループガバナンスのパターンは運用設計です。このリポジトリにすでに存在する プリミティブを再利用するが、それが防ごうとしている暴走挙動そのものは、 ここでは測定していません。以下の Tier で、文書化された入力と設計上の 推論の境界を示します。

  • [1] Tier 1 — 方法論契約： 本リポジトリ、docs/05-methodology.md §6「Budget guards」。このパターンは、事前見積もりと実行中のハード上限による中断を一般化したものです。「気づかないうちの予算超過は、気づかないうちの実験スコープ変更でもある」という原則は、§5 にも引き継がれるガバナンス上の姿勢です。
  • [2] Tier 2 — 対になる実測の根拠（benchmark-03）： 本リポジトリ、results/summary.md §3 および benchmarks/03-tool-using-agent/analysis.md。実測した上限の出典です。推論強度の全段階で品質は 1.97–2.00 の範囲にとどまり、その間にリクエストあたりのコストは $0.002762 → $0.003499、レイテンシは 2.9秒 → 3.8秒へ増加しました。ループのエスカレーションゲートが尊重すべきステップ単位の知見です。
  • [3] 運用パターン（実測済みの Tier ではなく設計）： ループ制御は scripts/run_benchmark.py の仕組みを応用しています。BudgetTracker / hard_ceiling_usd、BudgetExceededError、EXIT_BUDGET、estimate_experiment_cost_usd をゲートする MAX_COST_PER_BENCHMARK_USD、agent.max_tool_iterations、tool_loop_terminated="iteration_cap"、および scripts/run_judge.py のルーブリックゲートです。正準の詳しい解説は docs/18 で、docs/09-operator-guide-one-page.md では運用レバー L6 として導入されています。
  • [4] 提案されている次の拡張（未実装）： §4 のループスコープのフィールド — loop_id、step_index、cumulative_cost_usd、budget_remaining_usd — は、docs/14-observability-schema.md と schemas/ptu_request_record.schema.json を拡張します。これらは設計案であり、リリース済みとは主張していません。
  • [5] 根拠ダッシュボード： 対になる実測の根拠は、レンダリングされた benchmark-03 品質・コストチャートで監査できます。

本記事では、このリポジトリですでに動いているガードを使ってループを制限する方法を示し、 継続を判断するときに実測した上限を尊重します。一方、ループがどれほど頻繁に暴走するか、 タスク形状ごとのステップ数の分布、あるいはロングコンテキストのコストスケーリング曲線は 測定していません。docs/04 §4 にも、ここにあるベンチマークでは ロングアウトプット／ロングコンテキストのワークロードを測っていないと記録されています。 これらは推測で補わず、将来の暴走特性ベンチマークで検証すべき空白として扱います。

このパターンによって言えること

ループ作業では、「もっと強く考えさせる」「もっと長くループさせる」のではなく、実行前にループを制限し、その境界の所有者を明確にします。

概要記事に戻る

実践上の規則

  1. すべての複数呼び出しタスクに、代表的な p99 から定めた max_iterations のステップ上限と hard_ceiling_usd の累積上限を設定してください。
  2. ブレーカーはフェイルクローズにしてください。ステップ上限、コスト上限、進捗なしのいずれでも停止し、型付きの理由を記録して、ベストエフォートの部分回答を返します。
  3. すべてのエスカレーションを低コストの評価後に行い、実測した上限を尊重してください。中程度を超えると、推論強度を上げても評価スコアは上がらず、コストだけが増えました。
  4. タスク終了時の合計だけでなくステップ単位の行を残し、どのステップが暴走したのか特定できるようにしてください。
  5. 予算をコミットしてレビューするポリシーとして管理してください。超過率を SLO として追跡し、上限の引き上げにはスコープ変更と同じ手続きを適用します。

実践上の規則：L1–L5 は各呼び出しに境界を引き、L6 はループに境界を引く。 ループを実行する前に停止条件を決め、その決定をモデルの既定動作に任せず、 自分たちが所有するポリシーにしてください。
