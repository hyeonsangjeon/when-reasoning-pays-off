運用パターン · ループと予算ガバナンス (L6) · 新しい測定ではなく設計

エージェント型ループ：天井チェックが「止めるべき」と言ったあと、実際にループを止めるのは誰か

対になるトピックは、きれいな結論で終わります。ツールエージェントの品質が天井に張り付いたら、推論 effort を上げても得られるのはスコアではなくレイテンシとコストである。だから、上限に届く最も低い effort にルーティングすればよい。単一の呼び出しなら、その助言はまったく正しいものです。けれども現実のエージェントが、一度の呼び出しで終わることはめったにありません。計画し、ツールを呼び、結果を読み、もう一度推論し、ループします。タスクがループになった瞬間、コストは価格表から読み取れる数値ではなく、ステップにわたる積分になります。そして誰もが最初に手を伸ばす呼び出し単位の effort ダイヤルは、実際にお金を使っている対象にはもう届きません。このトピックは天井チェックのもう半分です。「この呼び出しにさらに effort をかける価値があるか」ではなく、「ループはいつ止まるのか、そして誰がそう決めたのか」です。

このパターンが必要になる理由

このトピックを生む午後の形は、だいたいこうです。あなたのエージェントは すべてのデモを通過します。ところが、ごく普通のサポートチケットが一つ、 それをループへ押し込みます — 検索し、読み直し、別のツールを呼び、少しだけ深く考え、もう一度試す — そして四十回のツール呼び出しのあとで答えを返します。答えは正しい。 ただし、そのタスクに見込んでいた予算の40×がかかっていて、月次請求書を見るまで 誰も気づきません。何も失敗していません。例外も、500も、アラートもない。 それが暴走するループを危険にします。請求書を読む直前まで、 それは正常に動いているエージェントに見えるのです。

そのエージェントが期待を下回ると、直感はいつもの方向へ向かいます — もう少し 長くループさせよう、もう少し強く考えさせよう。対になる天井チェックは、単一の 呼び出しで「もっと考える」が効かなくなる場所をすでに示しました。このトピックが 扱うのは、呼び出し単位のレバーが触れられない部分、つまり呼び出しの回数です。 こうしたワークロードを運用しているなら、おそらくすでに呼び出し単位のダイヤルに 手を伸ばし、それが十分には効かないことを感じているはずです。

  • reasoning_effort（レバー L4）は、一つの呼び出しの推論トークンに境界を引きます。ループが何回呼び出すかについては何も言いません。
  • max_output_tokens（レバー L5）は、一つの呼び出しの出力に境界を引きます。反復全体の累積支出には境界を引けません。
  • プロンプトキャッシュの安定性（レバー L3）は、一つのプレフィックスの入力コストを下げます。ループではステップごとにトランスクリプトが伸びるため、請求額が最も大きいときに、まさにキャッシュ可能な割合が小さくなります。

だからといって、呼び出し単位のレバーが間違っているわけではありません。単一の 呼び出しでは、なお最初に取るべき正しい手です。ただ、それらはループの一層下で 作用しているだけです。能力の問い — モデルはループできるのか、百万トークンを 保持できるのか — は、そもそも難所ではありませんでした。難しいのはループを 統治することです。しきい値、介入、評価、追跡可能性、そして所有です。

これは新しい測定ではなく、設計として読んでください。 このトピックは Tier 2 運用パターンです。新しく測定した量は導入しません。 依拠している測定済みの支点は、対になるトピックの benchmark-03 の天井 （実際に公開された結果）だけです。そしてここで述べるすべてのループ制御は、 このリポジトリ自身の測定ランナーがすでに実装しているガードから取り出したものです — ベンチマークバッチ自体が、暴走してはならない無境界コストのループだからです。 本番のループが実際にどれほど頻繁に暴走するのか、またそのステップ数の分布は、 ここでは測定していません。その誠実な境界は、下の出典セクションで 明示したままにしています。正準の書き下ろしは docs/18 — エージェント型ループの予算ガバナンスです。

問い

タスクがモデル呼び出しのループであるとき、累積コストに境界を引くものは何か — そしてその境界を誰が所有するのか。

パターン

運用レバー L6：ステップ上限とコスト天井、フェイルクローズのブレーカー、評価に基づくエスカレーション、ステップ単位のコスト追跡可能性。

対になる根拠

測定済み：benchmark-03 の品質天井は 1.97–2.00 にあり、コストは $0.002762 → $0.003499、レイテンシは 2.9s → 3.8s へ上がりました — ループが尊重すべきステップ単位の知見です。

判断

実行する前にループに境界を引き、ブレーカーをフェイルクローズにし、すべての天井を、誰かがホットフィックスで引き上げられる定数ではなく、コミットされレビューされるポリシーとして扱います。

面ごとに読む： しきい値 介入 評価 追跡可能性 ガバナンス 出典と根拠の境界

対になるトピック： ツールエージェントの天井チェックは 検出の半分です — 単一の呼び出しがどこで改善しなくなるかを示します。この トピックは介入の半分です — それでもループが支出を続けるとき、何がそれを止めるのか。

暴走コストは数値ではなく積分である

ループに驚かされるのは、その請求額が事前に価格づけできる数値ではなく、 ステップにわたる和だからです。 

total_cost ≈ Σ_step ( input_tokens_step    × input_rate
                    + reasoning_tokens_step × output_rate
                    + output_tokens_step    × output_rate )

その和を、誰の予想よりも速く大きくするものが三つあります。第一に、反復回数に 境界がないことです。ハードキャップがなければ、収束しないループ — 不安定なツール、 あいまいなサブゴール、「正しくなるまで改善し続ける」という指示 — は、課金対象の 呼び出しを出し続けます。モデルの中にそれを止めるものはありません。第二に、 コンテキストがステップごとに伸びることです。各反復は、前のトランスクリプトに 新しいツール出力を足して次の入力として再送するため、後半のステップほど高価になります。 さらにプレフィックスの一バイトの変化がキャッシュを無効にし、それらは入力単価どおりに 請求されます。第三に、effort がループ内で掛け算されることです。高い reasoning_effort のデフォルトは、ステップ単位の推論トークンに ステップ数を掛けることになり、間違えるには最も高くつく場所です。

呼び出し単位のレバーは、それぞれその和の一項を攻めます。けれども、 項の数や進行中の合計に境界を引くことはできません。 それがループの開く隙間であり、下の五つの面がその閉じ方です。

しきい値 — ステップ上限と累積コスト天井

一つのタスクが、隣のタスクの 40× を静かに使ったとき、初めてこれにぶつかります。

仕組み。 ループには、単一の呼び出しには不要な二つの境界が 必要です。最大反復回数と、タスク全体に対する累積トークン／コストの天井です。 どちらか一つだけでは漏れます。ステップ上限だけでは、各ステップが巨大な場合に 高価な暴走を許します。コスト天井だけでは、安価な無限スピンを許します。

対応。 タスククラスごとに、max_iterations の ステップ上限と hard_ceiling_usd の累積天井を宣言します。 天井は、安全に見える丸い数字ではなく、代表的なサンプルの p99 — ステップ数と タスク単位のコスト — から導きます。どちらも保守的に設定し、根拠があるときだけ 引き上げます。

リポジトリ内の根拠。 scripts/run_benchmark.py は すでにまさにこれを行っています。事前見積もり （estimate_experiment_cost_usd）を MAX_COST_PER_BENCHMARK_USD でゲートし、実行中の hard_ceiling_usd を BudgetTracker データクラスで追跡し、ツールループには max_iterations 上限 （agent.max_tool_iterations）を置いています。docs/05-methodology.md §6 「Budget guards」は、これを衛生ではなく方法論として扱います。「静かな 予算超過は、静かな実験スコープ変更でもある」。同じ文は本番にも当てはまります — 静かなループ超過は、そのタスクに許されたコストが静かに変わったということです。

介入 — フェイルクローズするサーキットブレーカー

ループがエラーになる代わりに一晩中回り続けたとき、初めてこれに出会います。

仕組み。 しきい値がループの途中で越えられたら、ループは 決定的かつ目に見える形で止まらなければなりません — ベストエフォートの部分回答に、 型のある「予算超過」シグナルを添えて返す — 静かに続けても、静かに切り詰めても いけません。その選択こそが、境界づけられたコストと暴走のすべての違いです。

対応。 次のいずれかでループを中断するサーキットブレーカーを 作ります。ステップ上限に達した、累積コストが hard_ceiling_usd に 達した、または進捗なし検出器が発火した — たとえば同じツール呼び出しの反復です。 中断時には、終了理由を持つ型付きの終端レコードを出し、そのうえで呼び出し元が なお使えるものを受け取れるよう、最後に回答だけの呼び出しを一度行います。 フェイルクローズにします。迷ったときのデフォルトは停止であり、 継続ではありません。

リポジトリ内の根拠。 ランナーは型付きの BudgetExceededError（「事前見積もりまたは実行中の合計が予算ガードを 破ったときに送出される」）を送出し、BudgetTracker.is_halted は 合計が天井を越えた時点で次の呼び出しの前に停止を強制します。プロセスは専用の EXIT_BUDGET コードで終了します。ツールループは同じ考え方の きれいなモデルです。iterations >= max_iterations になると、 モデルに最終回答を出させるために tools= なしで最後の呼び出しを一度行い、 tool_loop_terminated="iteration_cap" を記録し、回復のレッグを 軌跡に追加します。理由を残すフェイルクローズのブレーカーです。そのまま本番へ 持ち上げられます。

評価 — 効く場所でだけエスカレートする

「ただもっと考えさせよう」が助けにならなくなっても、請求だけは続く日に、これがやって来ます。

仕組み。 このリポジトリの中心的な結果は、中程度を超える effort が 品質ではなくコストを買う、というものです。benchmark-03 では、品質は effort の はしご全体で 1.97–2.00 付近の天井に保たれ、その一方でリクエスト単位のコストは $0.002762 から $0.003499 へ、レイテンシは 2.9s から 3.8s へ上がりました。 ループでは、同じ知見が継続の判断を支配します。もう一ステップ、 あるいは次の呼び出しでより高い effort を使うなら、その場所を得るだけの理由が 必要です。

対応。 エスカレーション — もう一回反復すること、または次の 呼び出しで reasoning_effort を上げること — を安価な評価の後ろに置きます。 ルーブリックのスコア、自己一貫性や信頼度のシグナル、明示的な停止チェックです。 デフォルトは停止にし、評価に継続の理由を主張させます。そうすれば、終わりのない 「終わるまでループする」は、境界のある「評価が効かなくなるまでループする」に 変わります。それは単一呼び出しのルーティング判断を、ループの形にしただけです。

リポジトリ内の根拠。 scripts/run_judge.py は、 すべてのベンチマークで品質を採点している既存のルーブリック判定器です。同じ形が、 自然な継続ゲートになります。1.97–2.00 の天井 （results/summary.md §3; benchmarks/03-tool-using-agent/analysis.md）は、ゲートのない 「もっと考えて、もう一度ループする」というデフォルトが、リターンの地点を大きく 越えて支出を続けることを示す測定済みの根拠です。

追跡可能性 — ループごと、ステップごとにコストを帰属させる

$40 のタスクを前にして、どのステップが原因だったのか言えないとき、初めてこれが姿を現します。

仕組み。 帰属できないものは統治できません。タスク終了時の 単一の数値は、どのステップが暴走したのか、なぜそうなったのかを隠します。 ガバナンスには、安定したループ id にひもづくステップ単位のレコードが必要です。 各レコードは、そのステップの使用量、進行中の累積コスト、残っている予算余力を 持ちます。

対応。 docs/14-observability-schema.md の リクエスト単位の捕捉を、ループスコープのフィールドで拡張します。安定した loop_id / タスク id、単調増加する step_index、 ステップ単位の usage ブロック（すでに捕捉されています — reasoning_tokens、cached_tokens、…）、 cumulative_cost_usd、そして budget_remaining_usd です。 ステップごとに JSONL の行を一つ出します。ループの請求額はその和であり、 budget_remaining_usd が初めて非正になる行が介入点です。 終了時の step_index の平均だけでなく、分布に アラームを置きます — 暴走は裾に住んでいます。

範囲メモ（誠実な境界）。 それらのループスコープのフィールドは、 すでに出荷済みのものではなく次の増分です。既存の PTURequestRecord — すでに request_idx と完全な usage ブロックを持つもの — と schemas/ptu_request_record.schema.json に差し込まれます。 今日のランナーは、すでに反復ごとの usage オブジェクトを一つの セルレベルの dict に合算し、反復ごとの軌跡を記録しています。ループの追跡可能性とは、 そのロールアップを第一級にすることです — 合計だけを残すのではなく、ステップ単位の 行を残してください。

ガバナンス — 予算は所有される契約である

そしてこれは、誰かがホットフィックスで天井を引き上げ、請求額だけが記録もなく動いたときに起こります。

仕組み。 ステップ上限とコスト天井は、魔法の数字ではなく ポリシーです。システムが何をしてよいかを決める他の契約と同じように、所有され、 バージョン管理され、レビューを通じて変更されなければなりません。天井の引き上げは スコープ変更であり、そう感じられるべきです。

対応。 タスククラスごとの予算ポリシーは、サービス中に散らばる 定数ではなく、コミットされた設定として宣言します。すべての天井変更をレビューし、 超過率 — ブレーカーがどれほど頻繁に発火するか — を第一級の SLO として追跡し、 天井の引き上げには方法論変更と同じ儀式を与えます。 docs/16-release-tiers-and-redaction-policy.md のリリースガバナンスの 規律は、公開データに適用された同じ形です。ここではそれを支出に適用します。

リポジトリ内の根拠。 GOVERNANCE.md は、予算ポリシーが 従う、所有された契約の変更管理モデルです。そして docs/05 §6 の 「静かな超過 = 静かなスコープ変更」という規則は、天井変更を日常作業ではなく レビュー可能なものにする文です。

出典と根拠の境界

このトピックでは二つのことが起きており、それらは別々の Tier にあります。 測定済みの支点 — benchmark-03 の天井 — は、監査できる公開結果です。 ループガバナンスのパターンは運用設計です。このリポジトリにすでに存在する プリミティブを再利用しますが、それが防ごうとしている暴走挙動そのものは、 ここでは測定されていません。下の Tier は、文書化された入力が終わり、設計上の 推論が始まる場所を示しています。

  • [1] Tier 1 — 方法論契約： このリポジトリ、docs/05-methodology.md §6 「Budget guards」。このパターンが一般化している、事前見積もりと実行中のハード天井による中断です。「静かな予算超過は、静かな実験スコープ変更でもある」という規則は、§5 に持ち込まれるガバナンス上の姿勢です。
  • [2] Tier 2 — 測定済みの対になる根拠（benchmark-03）： このリポジトリ、results/summary.md §3 および benchmarks/03-tool-using-agent/analysis.md。測定済みの天井の出典です — effort のはしご全体で品質は 1.97–2.00 の範囲にあり、その間にリクエスト単位のコストは $0.002762 → $0.003499、レイテンシは 2.9s → 3.8s へ上がりました。これは、ループのエスカレーションゲートが尊重すべきステップ単位の知見です。
  • [3] 運用パターン（測定済み Tier ではなく設計）： ループ制御は scripts/run_benchmark.py から取り出されています — BudgetTracker / hard_ceiling_usd、BudgetExceededError、EXIT_BUDGET、estimate_experiment_cost_usd が MAX_COST_PER_BENCHMARK_USD によってゲートされること、agent.max_tool_iterations、そして tool_loop_terminated="iteration_cap" — さらに scripts/run_judge.py のルーブリックゲートです。正準の書き下ろしは docs/18 で、docs/09-operator-guide-one-page.md では運用レバー L6 として導入されています。
  • [4] 提案されている次の増分（未実装）： §4 のループスコープのフィールド — loop_id、step_index、cumulative_cost_usd、budget_remaining_usd — は、docs/14-observability-schema.md と schemas/ptu_request_record.schema.json を拡張します。これらは設計にすぎません。このトピックのどこでも、出荷済みだとは主張していません。
  • [5] 根拠ダッシュボード： 測定済みの対になる根拠は、レンダリングされた benchmark-03 品質・コストチャートとして監査できます。

このトピックが確立すること、しないことは次のとおりです。このリポジトリで すでに動いているガードを使ってループに境界を引く方法を示し、継続するかどうかを 決めるときに測定済みの天井を尊重します。一方で、ループがどれほど頻繁に暴走するか、 タスク形状ごとのステップ数の分布、あるいはロングコンテキストのコストスケーリング曲線は 測定していません — docs/04 §4 は、ここにあるどのベンチマークも ロングアウトプット／ロングコンテキストのワークロードを測っていないと、すでに記録しています。 それらは静かな主張ではなく、将来の暴走特性化ベンチマークが閉じるべき誠実な空白として 扱ってください。

このパターンによって言えること

ループ作業で役に立つ文は、「もっと強く考えさせよう」でも「もっと長くループさせよう」でもありません。「走らせる前にループに境界を引き、その境界を自分たちが所有するものにする」です。

概説エッセイへ戻る

実践上の規則

  1. すべての複数呼び出しタスクに、一つではなく二つの境界を与えます。代表的な p99 からサイズを決めた max_iterations のステップ上限と hard_ceiling_usd の累積天井です。
  2. ブレーカーをフェイルクローズにします — 上限、天井、進捗なしのいずれでも、停止し、型付きの理由を記録し、ベストエフォートの部分回答を返します。
  3. すべてのエスカレーションを安価な評価の後ろに置き、測定済みの天井を尊重します。中程度を超えると、effort が買ったのはスコアではなくコストでした。
  4. タスク終了時の合計だけでなくステップ単位の行を残し、どのステップが暴走したのか名指しできるようにします。
  5. 予算をコミットされレビューされるポリシーとして保持します。超過率を SLO として追跡し、天井の引き上げにはスコープ変更と同じ儀式を与えます。

実践上の規則：L1–L5 は各呼び出しに境界を引き、L6 はループに境界を引きます。 ループが走る前にいつ止めるかを決め、その決定を、モデルがデフォルトで到達する何かではなく、 自分たちが所有する何かにしてください。

対になる天井チェックを読む
