运营模式、循环与预算治理 (L6)、设计而非新的测量

智能体循环：当上限检查说该停之后，究竟由谁真正停下循环？

配套主题最后给了一个干净的结论：一旦工具智能体的质量已经顶到上限，更多推理强度换来的只是延迟和成本，而不是分数——所以应该路由到刚好够到上限的最低强度。对单次调用来说，这条建议完全正确。但真实智能体很少只调用一次。它会先规划，再调用工具、读取结果、再次推理，然后继续循环。任务变成循环的那一刻，成本就不再是价格页上能查到的单个数字，而成了跨步骤的积分；大家最先想到的那种逐次调用调节强度的手段，也碰不到真正烧钱的地方。这个主题是上限检查的另一半：问题不是“这次调用值不值得加推理强度”，而是“循环什么时候停，谁拍板让它停”。

为什么需要这个模式

这个主题大概就诞生在这样的下午：你的智能体每次演示都能过。然后，一个普通的支持工单把它带进循环 ——搜索、重读、再调用一个工具、再多想一点、再试一次—— 40 次工具调用之后，它给出了答案。答案是正确的。 但它也花掉了你为这类任务预留预算的40 倍，而在月度账单出现之前，没有人注意到。 系统没有任何“失败”：没有异常，没有 500，也没有告警。 这就是失控循环危险的地方。直到你看到账单之前，它都像一个工作正常的智能体。

当这个智能体表现不够好时，本能反应很熟悉——让它多循环一会儿，让它再多想一点。 配套的上限检查已经说明，在单次调用里，“多想一点”到哪里就不再划算。 本文讨论的是逐次调用的调节手段碰不到的部分：调用的次数。 如果你运营过这样的工作负载，大概率已经试过按调用去调强度，也发现它们并不能真正咬住问题。

  • reasoning_effort（杠杆 L4）约束的是一次调用的推理 token。它并不说明循环会发起多少次调用。
  • max_output_tokens（杠杆 L5）约束的是一次调用的输出。它不能约束跨迭代的累计支出。
  • 提示缓存稳定性（杠杆 L3）降低的是某个前缀的输入成本。在循环里，对话轨迹每一步都在增长；账单最重的时候，能命中缓存的比例反而在变小。

这并不是说按调用的杠杆错了；对任何单次调用，它们仍然是正确的第一步。 只是它们作用在循环下面的一层。能力问题——模型能不能循环、能不能容纳一百万 token——从来不是最难的。 真正难的是治理循环：阈值、干预、评估、可追踪性，以及所有权。

请把本文读作设计，而不是新的测量。 这个主题是一个 Tier 2 运营模式：它没有引入新的实测量。 它依赖的唯一实测锚点，是配套主题里的 benchmark-03 上限（一个真实、已发布的结果）； 它描述的每一种循环控制，都直接取自本仓库自己的测量运行器已经实现的防护—— 因为一批基准测试本身就是一个成本没有上界的循环，不能放任它失控。 生产里的循环到底多久失控一次、步骤数分布长什么样，本文没有测量； 这个边界会在下面的来源部分明确写出来。规范性说明见 docs/18 — 智能体循环预算治理。

问题

当一个任务由一串模型调用组成时，谁来约束累计成本——这条边界又归谁负责？

模式

运营杠杆 L6：步骤上限与成本上限、失败即关闭的断路器、评估把关的升级，以及按步骤可追踪的成本。

配套证据

实测：benchmark-03 的质量卡在 1.97–2.00 的上限附近，同时成本从 $0.002762 升至 $0.003499，延迟从 2.9秒 升至 3.8秒——这是循环里的每一步都必须尊重的结论。

决定

运行前先约束循环，让断路器失败即关闭；每一个上限都要当成已提交、经审查的政策，而不是某个人能在热修复里随手调高的常量。

按方面阅读： 阈值 干预 评估 可追踪性 治理 来源与证据边界

配套主题： 工具智能体上限检查 是检测的一半——它说明单次调用到哪里就不再变好。本文是干预的一半——当循环还在继续花钱时，什么负责让它停下。

失控成本是积分，不是一个数字

循环会让人措手不及，是因为账单按步骤累加，而不是一个能提前标价的数： 

total_cost ≈ Σ_step ( input_tokens_step    × input_rate
                    + reasoning_tokens_step × output_rate
                    + output_tokens_step    × output_rate )

有三件事会让这个总和涨得比预期快。第一，迭代次数没有上界： 没有硬性上限时，一个无法收敛的循环——不稳定的工具、含糊的子目标、一条“继续打磨直到正确”的指令—— 会一直发起可计费调用，而模型自己不会停手。第二，上下文每一步都在增长： 每次迭代都会把之前的对话轨迹加上新的工具输出，作为下一次输入重新发送。 所以后面的步骤最贵；前缀里哪怕只变了一个字节，也可能让缓存失效，使这些步骤按完整输入费率计费。 第三，强度会在循环里被放大：较高的 reasoning_effort 默认值，会把每步推理 token 乘上步骤数， 这是最不该出错、也最贵的地方。

每个按调用的杠杆都只能压住这个总和里的某一项。它们做不到的是约束项数，也约束不了运行中的总额。 这就是循环撕开的缺口；下面五个方面说明怎么把它关上。

阈值——步骤上限与累计成本上限

当你第一次发现一个任务悄悄花掉相邻任务 40× 的成本时，就会撞上它。

机制。 循环需要两条单次调用不需要的边界：最大迭代次数，以及整个任务的累计 token/成本上限。 只设其中一条都会漏。只有步骤上限时，如果每一步都很大，仍然可能跑出昂贵的失控； 只有成本上限时，又可能允许便宜但无止境的空转。

行动。 按任务类别声明一个 max_iterations 步骤上限和一个 hard_ceiling_usd 累计上限。 上限要从代表性样本的 p99 推出来——同时看步骤数和单任务成本——不要拍一个“感觉安全”的整数。 两条边界都先保守设置，只有拿到证据再提高。

仓库内证据。 scripts/run_benchmark.py 已经就是这样做的：运行前估算 (estimate_experiment_cost_usd) 由 MAX_COST_PER_BENCHMARK_USD 把关；运行过程中的 hard_ceiling_usd 由 BudgetTracker 数据类跟踪；并设置工具循环的 max_iterations 上限 (agent.max_tool_iterations)。 docs/05-methodology.md §6 “预算防护” 把这视为方法论，而不是卫生习惯： “无声的预算超支，也是实验范围的无声改变。” 同一句话放到生产里也成立——循环悄悄超支， 就等于悄悄改变了这个任务被允许花多少钱。

干预——失败即关闭的断路器

当你第一次看到循环没有报错、而是空转一整晚时，就会遇到它。

机制。 当阈值在循环中途被越过时，循环必须用确定、可见的方式停下来—— 返回一个尽力而为的部分答案，并带上有类型的“预算超出”信号——绝不能静默继续，也不能静默截断。 有界成本和失控之间，差别就在这个选择上。

行动。 构建一个断路器，只要出现以下任一情况就中止循环：达到步骤上限，累计成本达到 hard_ceiling_usd，或无进展检测器触发——例如同一个工具调用反复出现。 中止时，发出一条带终止原因的有类型终止记录，然后再做一次只产出答案的最终调用， 让调用方仍然拿到可用结果。失败即关闭：拿不准时，默认是停止，不是继续。

仓库内证据。 运行器会抛出有类型的 BudgetExceededError（“当预运行估算或运行中总额突破预算防护时抛出”），并且 BudgetTracker.is_halted 会在总额越过上限后、发起下一次调用之前强制停止；进程以专用的 EXIT_BUDGET 代码退出。 工具循环是同一思想的干净模型：当 iterations >= max_iterations 时， 它会在没有 tools= 的情况下发起一次最终调用，迫使模型给出最终答案， 记录 tool_loop_terminated="iteration_cap"，并把恢复段追加到轨迹中。 这就是一个会留下原因的失败即关闭断路器——可以原样搬到生产里。

评估——只在有回报的地方升级

当“就让它多想一点”不再有帮助、却还在计费的那一天，你就会遇到它。

机制。 本仓库的核心结果是：超过中档之后，更高强度只增加成本，并不提升质量。 在 benchmark-03 上，质量在整个强度档位上都贴近 1.97–2.00 的上限，而每请求成本从 $0.002762 升至 $0.003499，延迟从 2.9秒 升至 3.8秒。在循环里，同一个发现约束的是继续决策： 再走一步，或下一次调用改用更高强度，都必须先证明自己值得。

行动。 把升级——再迭代一次，或在下一次调用上提高 reasoning_effort——放到廉价评估之后：可以是评分量表分数、自一致性或置信度信号，也可以是明确的停止检查。 默认停止，让评估来证明为什么值得继续。这样，开放式的“循环直到完成”就变成了有边界的 “循环直到评估显示继续不再划算”；这只是把单次调用的路由决策写成循环版本。

仓库内证据。 scripts/run_judge.py 是已经在每个基准中为质量打分的评分量表评审； 同样的结构天然适合作为继续门。1.97–2.00 上限 (results/summary.md §3; benchmarks/03-tool-using-agent/analysis.md) 是一条实测证据： 没有门控的“更努力思考、再循环一次”默认策略，会在回报已经到头之后继续花很久的钱。

可追踪性——按循环、按步骤归因成本

当你第一次面对一个 $40 任务，却说不出是哪一步造成的时，就会需要它。

机制。 不能归因，就谈不上治理。任务结束时的一个总数，会把哪一步失控、为什么失控都盖住。 治理需要以稳定循环 id 为键，保留每一步的记录：每条记录都要带上该步骤的用量、运行中的累计成本，以及还剩多少预算。

行动。 用循环级字段扩展 docs/14-observability-schema.md 里已有的按请求采集： 一个稳定的 loop_id / 任务 id，一个单调递增的 step_index， 每步的 usage 块（已捕获——reasoning_tokens、cached_tokens、…）， 一个 cumulative_cost_usd，以及一个 budget_remaining_usd。 每一步输出一行 JSONL；循环账单就是这些行的总和，而 budget_remaining_usd 第一次变为非正的那一行，就是你的干预点。对终止时 step_index 的分布告警，不要只看均值——失控通常藏在尾部。

范围说明（诚实边界）。 这些循环级字段是下一个增量，不是已经交付的东西。 它们可以挂到既有的 PTURequestRecord 上——其中已经携带 request_idx 和完整的 usage 块——以及 schemas/ptu_request_record.schema.json。今天的运行器已经把每次迭代的 usage 对象汇总成一个单元级字典，并记录逐迭代轨迹； 循环可追踪性就是让这个汇总成为一等对象——保留每步记录行，不要只保留总和。

治理——预算是一份有所有者的契约

当有人在热修复里调高上限、账单也随之变化，却没有任何书面痕迹时，你会遇到这一点。

机制。 步骤上限和成本上限是政策，不是魔法数字。 它们必须像任何决定系统能做什么的契约一样，有明确所有者、纳入版本控制，并通过审查来变更。 提高上限就是范围变更，流程上也应该让人感受到这一点。

行动。 在已提交的配置里声明每类任务的预算政策，不要把常量散落在各个服务里。 每一次上限变更都要审查；把超支率——也就是断路器触发频率——作为一等 SLO 跟踪； 提高上限要有和方法论变更同等的流程。 docs/16-release-tiers-and-redaction-policy.md 中的发布治理纪律，是同一种结构在已发布数据上的应用；这里把它用到支出上。

仓库内证据。 GOVERNANCE.md 就是预算政策应该遵循的、有所有者的契约变更控制模型， 而 docs/05 §6 中“无声超支 = 无声范围变更”的规则， 让上限变更成为需要审查的事项，而不是顺手改个常量。

这个主题里有两件事，它们属于不同层级。实测锚点——benchmark-03 上限——是一个可审计的已发布结果。 循环治理模式是运营设计：它复用了本仓库已经存在的原语，但它防范的失控行为本身并没有在这里测量。 下面这些层级说明：文档化输入到哪里为止，设计推断从哪里开始。

  • [1] Tier 1 — 方法论契约： 本仓库，docs/05-methodology.md §6 “预算防护”。这个模式泛化的，是运行前估算加运行中硬上限中止；“无声的预算超支，也是实验范围的无声改变”这条规则，则是带入 §5 的治理立场。
  • [2] Tier 2 — 实测配套项（benchmark-03）： 本仓库，results/summary.md §3 和 benchmarks/03-tool-using-agent/analysis.md。实测上限的来源——在整个强度档位上，质量保持在 1.97–2.00 内，而每请求成本从 $0.002762 → $0.003499，延迟从 2.9秒 → 3.8秒。这是循环的升级门必须尊重的单步结论。
  • [3] 运营模式（设计，不是实测层级）： 循环控制直接取自 scripts/run_benchmark.py——BudgetTracker / hard_ceiling_usd、BudgetExceededError、EXIT_BUDGET、estimate_experiment_cost_usd 由 MAX_COST_PER_BENCHMARK_USD 把关、agent.max_tool_iterations，以及 tool_loop_terminated="iteration_cap"——和 scripts/run_judge.py 中的评分量表关口。规范性文章是 docs/18，并在 docs/09-operator-guide-one-page.md 中作为运营杠杆 L6 引入。
  • [4] 提议的下一个增量（尚未构建）： §4 中的循环级字段——loop_id、step_index、cumulative_cost_usd、budget_remaining_usd——扩展 docs/14-observability-schema.md 和 schemas/ptu_request_record.schema.json。它们只是设计；本主题没有声称它们已经交付。

本主题能说明什么、不能说明什么：它展示了如何用本仓库已经在运行的防护来约束循环， 并在决定是否继续时尊重一个实测上限。它没有测量循环多久失控一次、不同任务形状下步骤数如何分布， 也没有测量长上下文成本缩放曲线——docs/04 §4 已经记录，这里没有任何基准测量长输出 / 长上下文工作负载。 请把这些看作未来失控特征化基准需要补上的诚实空白，而不是悄悄塞进来的主张。

这个模式让我们能够说什么

对循环型任务来说，有用的句子不是“让它多想一点”或“让它多循环一会儿”。而是：“运行之前先约束循环，并让这条边界归你负责。”

实践规则

  1. 给每个多调用任务两条边界，而不是一条：一个 max_iterations 步骤上限和一个 hard_ceiling_usd 累计上限，两者都用代表性 p99 来定。
  2. 让断路器失败即关闭——遇到步骤上限、成本上限或无进展时停止，记录有类型的原因，并返回尽力而为的部分答案。
  3. 把每一次升级都放在廉价评估之后，并尊重实测上限：超过中档后，更高强度只增加成本，并不提升分数。
  4. 保留每步记录行，而不只是任务结束时的总和，这样你才能指出是哪一步失控。
  5. 把预算当成已提交、经审查的政策来维护；把超支率作为 SLO 跟踪，并让提高上限具备范围变更的流程。

实践规则：L1–L5 约束每次调用；L6 约束循环。 在循环运行之前决定何时停止，并让这个决定归你负责，而不是让模型一路默认走到某个结果。
