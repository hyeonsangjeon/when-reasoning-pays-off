Operator pattern: loop & budget governance (L6), नई measurement नहीं बल्कि design

Agentic loops: ceiling check “रुको” कह दे, उसके बाद सचमुच loop को रोकता कौन है?

साथ वाला topic एक साफ़ बात पर खत्म होता है: tool-agent quality जब अपने ceiling पर अटक जाए, तब अधिक reasoning effort से score नहीं बढ़ता, सिर्फ latency और लागत बढ़ती है — इसलिए उस सबसे कम effort पर route करें जो cap तक पहुंचता है। एक call के लिए यह सलाह बिल्कुल सही है। लेकिन असली agent शायद ही कभी सिर्फ एक call होता है। वह plan करता है, tool call करता है, result पढ़ता है, फिर reason करता है, और loop में जाता है। task जैसे ही loop बनता है, लागत pricing page से पढ़ी जाने वाली एक संख्या नहीं रहती; वह steps पर integral बन जाती है। और per-call effort सेटिंग — वही lever जिसे सब पहले पकड़ते हैं — अब उस हिस्से तक नहीं पहुंचती जो असल में पैसा खर्च कर रहा है। यह topic ceiling check का दूसरा आधा है: “इस call पर और effort लगाने से फायदा है?” नहीं, बल्कि “loop कब रुकेगा, और यह किसने तय किया?”

यह pattern क्यों मौजूद है

जिस दोपहर से यह topic पैदा होता है, वह कुछ ऐसी होती है। आपका agent हर demo पास कर देता है। फिर एक सामान्य support ticket उसे loop में डाल देता है — search, फिर से पढ़ना, दूसरा tool call, थोड़ा और सोचना, फिर कोशिश — और कई tool calls बाद वह जवाब देता है। जवाब सही है। लेकिन उस task की लागत आपके budget से कई गुना निकल चुकी है, और monthly invoice आने तक किसी को पता नहीं चलता। कुछ fail नहीं हुआ: कोई exception नहीं, कोई 500 नहीं, कोई alert नहीं। runaway loop इसी वजह से खतरनाक है। बिल पढ़ने तक वह बिल्कुल working agent जैसा दिखता है।

जब agent कमजोर पड़ता है, instinct वही पुरानी होती है — उसे थोड़ा और loop करने दें, थोड़ा और सोचने दें। साथ वाले ceiling check ने पहले ही दिखा दिया कि single call पर “think harder” कहां payoff देना बंद कर देता है। यह topic उस हिस्से पर है जिसे per-call levers छू ही नहीं सकते: calls की संख्या। अगर आप ऐसा workload चला रहे हैं, तो शायद आपने per-call सेटिंगें आज़मा ली होंगी और पाया होगा कि वे यहां पूरी पकड़ नहीं बनाते।

  • reasoning_effort (lever L4) एक call के reasoning tokens को bound करता है। यह loop कितने calls करेगा, इस बारे में कुछ नहीं कहता।
  • max_output_tokens (lever L5) एक call के output को bound करता है। यह iterations के पार cumulative spend को bound नहीं करता।
  • Prompt-cache stability (lever L3) एक prefix की input लागत घटाती है। loop में transcript हर step पर बढ़ता है, इसलिए cacheable fraction ठीक तब घटता है जब बिल सबसे बड़ा होता है।

इसका मतलब यह नहीं कि per-call levers गलत हैं; किसी भी single call पर वे अभी भी सही first move हैं। बस वे loop से एक layer नीचे काम करते हैं। capability वाला सवाल — क्या model loop कर सकता है, क्या वह million tokens संभाल सकता है — असली कठिन सवाल कभी था ही नहीं। कठिन हिस्सा loop को govern करना है: thresholds, intervention, evals, traceability, और ownership।

इसे नई measurement नहीं, design की तरह पढ़ें। यह topic एक Tier 2 operator pattern है: यह कोई नई measured magnitude introduce नहीं करता। इसका एक measured anchor साथ वाले topic का benchmark-03 ceiling है (एक वास्तविक, published result), और यहां बताए गए हर loop control को इस repository के अपने measurement runner में पहले से मौजूद guard से सीधे लिया गया है — क्योंकि benchmark batch खुद भी unbounded-लागत loop है; उसे भी runaway नहीं होने देना होता। production loops सच में कितनी बार runaway होते हैं, और उनके step counts का distribution क्या है, यह यहां measured नहीं है; यह boundary नीचे sources section में साफ़ रखी गई है। canonical write-up है docs/18 — agentic loop budget governance.

प्रश्न

जब task model calls का loop हो, तो cumulative लागत को क्या bound करता है — और उस bound का owner कौन है?

Pattern

Operator lever L6: step cap और लागत ceiling, fail-closed breaker, eval-gated escalation, और per-step लागत traceability।

साथ वाला evidence

Measured: benchmark-03 का 1.97–2.00 quality ceiling, जबकि लागत $0.002762 → $0.003499 और latency 2.9s → 3.8s बढ़ी — यही per-step finding loop को माननी होगी।

निर्णय

loop चलाने से पहले उसे bound करें, breaker को fail closed रखें, और हर ceiling को committed, reviewed policy मानें — ऐसा constant नहीं जिसे कोई hotfix में बढ़ा दे।

पहलू के हिसाब से पढ़ें: Thresholds Intervention Evals Traceability Governance Sources और evidence boundary

साथ वाला topic: Tool-agent ceiling checks detection वाला आधा है — यह दिखाता है कि single call कहां improve होना बंद करता है। यह topic intervention वाला आधा है — जब loop फिर भी spend करता रहता है, तो उसे कौन रोकता है।

Runaway लागत एक integral है, कोई एक number नहीं

loop आपको इसलिए चौंकाता है क्योंकि उसका बिल steps का sum होता है, कोई ऐसी figure नहीं जिसका अंदाज़ा आप पहले से भरोसे के साथ लगा सकें: 

total_cost ≈ Σ_step ( input_tokens_step    × input_rate
                    + reasoning_tokens_step × output_rate
                    + output_tokens_step    × output_rate )

तीन बातें उस sum को उम्मीद से तेज़ बढ़ाती हैं। पहली, iteration count unbounded होता है: hard cap न हो तो जो loop converge नहीं करता — flaky tool, ambiguous sub-goal, “सही होने तक refine करते रहो” instruction — वह billable calls चलाता रहता है, और model के अंदर कोई चीज़ उसे अपने-आप नहीं रोकती। दूसरी, context हर step पर बढ़ता है: हर iteration पुराने transcript के साथ नया tool output जोड़कर next input के रूप में भेजता है, इसलिए late steps सबसे महंगे होते हैं। prefix में single byte change भी cache flush कर देता है, और फिर वही steps full input rate पर बिल होते हैं। तीसरी, effort loop के भीतर multiply होता है: high reasoning_effort default per-step reasoning tokens को step count से multiply करता है; यहां गलती सबसे महंगी पड़ती है।

per-call levers उस sum के अलग-अलग term को संभालते हैं। वे जो नहीं कर सकते, वह है terms की संख्या या running total को bound करना। यही gap loop खोलता है, और नीचे दिए पाँच पहलू उसे बंद करने का तरीका हैं।

Thresholds — step cap और cumulative लागत ceiling

यह पहली बार तब दिखता है जब एक task चुपचाप अपने पड़ोसी tasks से 40× खर्च कर देता है।

तंत्र। loop को दो bounds चाहिए, जो single call को नहीं चाहिए: maximum iteration count, और पूरे task के लिए cumulative token/लागत ceiling। सिर्फ एक bound leak कर जाता है। step cap के बावजूद expensive runaway हो सकता है अगर हर step बहुत बड़ा हो; सिर्फ लागत ceiling हो तो endless cheap spin चल सकता है।

क्या करें। task class के हिसाब से max_iterations step cap और hard_ceiling_usd cumulative ceiling declare करें। ceiling को representative sample के p99 से निकालें — step count और per-task लागत — किसी ऐसे round number से नहीं जो देखने में safe लगे। दोनों को conservative रखें और केवल evidence के साथ raise करें।

Repo के भीतर evidence। scripts/run_benchmark.py पहले से यही करता है: pre-run estimate (estimate_experiment_cost_usd) जिसे MAX_COST_PER_BENCHMARK_USD gate करता है, mid-run hard_ceiling_usd जिसे BudgetTracker dataclass track करता है, और tool-loop max_iterations cap (agent.max_tool_iterations)। docs/05-methodology.md §6 “Budget guards” इसे hygiene नहीं, methodology मानता है: “silent budget overrun भी experiment scope में silent change है।” यही बात production में भी लागू होती है — silent loop overrun, task की allowed लागत में silent change है।

Intervention — fail closed करने वाला circuit-breaker

यह पहली बार तब सामने आता है जब loop error देने के बजाय पूरी रात spin करता रहता है।

तंत्र। जब threshold mid-loop cross होती है, तो loop को deterministic और visible तरीके से रुकना चाहिए — best-effort partial answer और typed “budget exceeded” signal लौटाते हुए। वह कभी silently चलता न रहे, और कभी silently truncate न करे। bounded लागत और runaway के बीच असली फर्क यही choice है।

क्या करें। ऐसा circuit-breaker बनाएं जो इनमें से किसी भी स्थिति पर loop abort करे: step cap hit हो, cumulative लागत hard_ceiling_usd तक पहुंच गई, या no-progress detector fire हुआ — जैसे वही tool call बार-बार repeat हो। abort पर termination reason वाला typed terminal record emit करें, फिर एक final answer-only call करें ताकि caller को फिर भी कुछ usable मिले। Fail closed: संदेह हो तो default stop है, continue नहीं।

Repo के भीतर evidence। runner typed BudgetExceededError raise करता है (“Raised when pre-run estimate or running total breaches a budget guard”), और BudgetTracker.is_halted total ceiling cross करते ही next call से पहले halt enforce करता है; process dedicated EXIT_BUDGET code से exit करता है। tool loop उसी idea का clean model है: iterations >= max_iterations पर यह tools= के बिना one final call fire करता है ताकि model final answer emit करने पर मजबूर हो, tool_loop_terminated="iteration_cap" record करता है, और recovery leg को trajectory में append करता है। यह reason छोड़ने वाला fail-closed breaker है — इसे production में as-is अपनाएं।

Evals — escalation केवल वहीं करें जहां payoff हो

यह उस दिन आता है जब “बस इसे और सोचने दें” मदद करना बंद कर देता है, लेकिन बिलिंग चलती रहती है।

तंत्र। repo का central result यह है कि mid-range से ऊपर effort से quality नहीं बढ़ती, सिर्फ लागत बढ़ती है। benchmark-03 पर quality effort की पूरी range में 1.97–2.00 के पास ceiling पर रही, जबकि per-request लागत $0.002762 से $0.003499 और latency 2.9s से 3.8s तक बढ़ी। loop में यही finding continuation decision govern करती है: एक और step, या next call पर higher effort, अपनी जगह साबित करे।

क्या करें। escalation — एक और iteration, या next call पर higher reasoning_effort — को cheap eval के पीछे gate करें: कोई rubric score, self-consistency या confidence signal, explicit stop check। default stop रखें, और eval से continue करने का कारण मांगें। इससे open-ended “loop until done” bounded “loop until eval says continue” में बदलता है, यानी single-call routing decision का loop form।

Repo के भीतर evidence। scripts/run_judge.py वही rubric जज है जो हर benchmark में quality score करता है; वही pattern natural continuation gate बनता है। 1.97–2.00 ceiling (results/summary.md §3; benchmarks/03-tool-using-agent/analysis.md) measured evidence है कि ungated “think harder, loop again” default return के point से काफी आगे तक spend करवाता रहता है।

Traceability — लागत को per loop, per step attribute करें

यह पहली बार तब चुभता है जब $40 task सामने हो और आप बता न पाएं कि कौन सा step वजह था।

तंत्र। जिसे आप attribute नहीं कर सकते, उसे govern नहीं कर सकते। single end-of-task number यह छिपा देता है कि कौन सा step runaway हुआ और क्यों। Governance के लिए stable loop id से keyed per-step records चाहिए, जिनमें step का usage, running cumulative लागत, और बची हुई budget headroom हो।

क्या करें। docs/14-observability-schema.md में per-request capture को loop-scoped fields से extend करें: stable loop_id / task id, monotonic step_index, per-step usage block (already captured — reasoning_tokens, cached_tokens, …), cumulative_cost_usd, और budget_remaining_usd। हर step पर एक JSONL row emit करें; loop का बिल इन rows का sum है, और वह row जहां budget_remaining_usd पहली बार non-positive होता है, आपका intervention point है। termination पर step_index के distribution पर alarm करें, सिर्फ mean पर नहीं — runaways tail में रहते हैं।

Scope note (ईमानदार सीमा)। ये loop-scoped fields next increment हैं, already shipped चीज़ नहीं। ये existing PTURequestRecord पर fit होते हैं — जिसमें पहले से request_idx और full usage block है — और schemas/ptu_request_record.schema.json पर। आज runner पहले से per-iteration usage objects को एक cell-level dict में sum करता है और per-iteration trajectory record करता है; loop traceability उसी roll-up को first-class बनाती है — per-step rows रखें, केवल sum नहीं।

Governance — budget एक owned contract है

और यह तब चोट करता है जब कोई hotfix में ceiling bump कर देता है और बिल बिना किसी दर्ज रिकॉर्ड के बढ़ जाता है।

तंत्र। Step caps और लागत ceilings policy हैं, magic numbers नहीं। उन्हें owned, version-controlled, और review के जरिए change होना चाहिए — किसी भी ऐसे contract की तरह जो तय करता है system को क्या करने की अनुमति है। ceiling raise scope change है, और उसे वैसा ही महसूस होना चाहिए।

क्या करें। per-task-class budget policy committed config में declare करें, services में scattered constants में नहीं। हर ceiling change review करें; overrun rate — breaker कितनी बार fire होता है — को first-class SLO की तरह track करें; और ceiling raise को methodology change जितनी ceremony दें। docs/16-release-tiers-and-redaction-policy.md में release-governance discipline published डेटा पर यही pattern लागू करता है; यहां वही spend पर लागू होता है।

Repo के भीतर evidence। GOVERNANCE.md वही owned-contract change-control model है जिसका budget policy पालन करती है, और docs/05 §6 का “silent overrun = silent scope change” rule वह line है जो ceiling change को routine नहीं, reviewable बनाती है।

Sources और evidence boundary

यह topic क्या establish करता है और क्या नहीं: यह दिखाता है कि इस repository में पहले से चल रहे guards से loop को कैसे bound करें, और continue करने का decision लेते समय measured ceiling को कैसे respect करें। यह measure नहीं करता कि loops कितनी बार runaway होते हैं, task shape के हिसाब से step counts का distribution क्या है, या long-context लागत-scaling curve कैसा है — docs/04 §4 पहले से record करता है कि यहां कोई benchmark long-output / long-context workloads measure नहीं करता। इन्हें future runaway-characterization benchmark से close होने वाले honest gaps मानें, quiet claims नहीं।

loop work के लिए उपयोगी sentence “इसे और सोचने दें” या “इसे और लंबे समय तक loop करने दें” नहीं है। उपयोगी sentence है: “loop चलाने से पहले उसे bound करें, और उस bound का owner तय करें।”

अवलोकन निबंध पर वापस जाएं

व्यावहारिक नियम

  1. हर multi-call task को एक नहीं, दो bounds दें: max_iterations step cap और hard_ceiling_usd cumulative ceiling, दोनों representative p99 से sized।
  2. breaker को fail closed बनाएं — cap, ceiling, या no-progress पर stop करें, typed reason record करें, और best-effort partial answer return करें।
  3. हर escalation को cheap eval के पीछे gate करें, और measured ceiling को मानें: mid-range से ऊपर, effort से score नहीं बढ़ा, सिर्फ लागत बढ़ी।
  4. सिर्फ end-of-task sum नहीं, per-step rows रखें, ताकि आप runaway हुए step का नाम ले सकें।
  5. budget को committed, reviewed policy की तरह रखें; overrun rate को SLO की तरह track करें और ceiling raise को scope change जैसी ceremony दें।

व्यावहारिक नियम: L1–L5 हर call को bound करते हैं; L6 loop को bound करता है। loop चलने से पहले तय करें कि कब stop करना है, और उस decision को model के default पर छोड़ी गई चीज़ नहीं, बल्कि आपकी owned चीज़ बनाएं।
