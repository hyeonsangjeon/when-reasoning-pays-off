Operator pattern: loop & budget governance (L6), design rather than a new measurement

Agentic loops: enforcing stop conditions after the ceiling check

The companion topic establishes a call-level rule: once tool-agent quality is pinned against its ceiling, route to the lowest effort that reaches the cap because more reasoning buys latency and cost rather than score. A real agent, however, plans, calls a tool, reads the result, reasons again, and loops. Its cost becomes an integral over steps, which the per-call effort dial cannot bound. This topic extends the ceiling check from "is this call worth more effort," to "when does the loop stop, and who decided."

Why this pattern exists

An agent can pass every demo, then encounter an ordinary support ticket that sends it into a loop — search, re-read, call another tool, think a little harder, try again — and forty tool calls later it answers. The answer is correct. It also cost forty times what you budgeted for that task, and nobody noticed until the monthly invoice. Nothing failed: no exception, no 500, no alert. That is what makes a runaway loop dangerous. It looks like a working agent right up until you read the bill.

When that agent underperforms, letting it loop longer or think harder is an intuitive response. The companion ceiling check already showed where "think harder" stops paying on a single call. This topic addresses what per-call levers cannot control: the number of calls.

  • reasoning_effort (lever L4) bounds the reasoning tokens of one call. It says nothing about how many calls the loop makes.
  • max_output_tokens (lever L5) bounds the output of one call. It does not bound the cumulative spend across iterations.
  • Prompt-cache stability (lever L3) lowers the input cost of one prefix. In a loop the transcript grows every step, so the cacheable fraction shrinks exactly when the bill is largest.

None of that makes the per-call levers wrong; they are still the right first move on any single call. They simply operate one layer below the loop. Governing the loop requires thresholds, intervention, evals, traceability, and ownership; the model's ability to loop or hold a million tokens does not provide those controls.

Read this as design, not a new measurement. This topic is a Tier 2 operator pattern: it introduces no new measured magnitudes. The one measured anchor it leans on is the benchmark-03 ceiling from the companion topic (a published result), and every loop control it describes is lifted from a guard this repository's own measurement runner already implements — because a benchmark batch is itself an unbounded-cost loop that must not run away. How often production loops actually run away, and the distribution of their step counts, is not measured here; the sources section preserves that boundary. The canonical write-up is docs/18 — agentic loop budget governance.

Question

When a task is a loop of model calls, what bounds the cumulative cost — and who owns that bound?

Pattern

Operator lever L6: a step cap and cost ceiling, a fail-closed breaker, eval-gated escalation, and per-step cost traceability.

Companion evidence

Measured: benchmark-03's 1.97–2.00 quality ceiling while cost rose $0.002762 → $0.003499 and latency 2.9s → 3.8s — the per-step finding the loop must respect.

Decision

Bound the loop before you run it, make the breaker fail closed, and treat every ceiling as committed, reviewed policy — not a constant someone can bump in a hotfix.

The runaway cost is an integral, not a number

A loop surprises you because its bill is a sum over steps, not a figure you can price in advance: 

total_cost ≈ Σ_step ( input_tokens_step    × input_rate
                    + reasoning_tokens_step × output_rate
                    + output_tokens_step    × output_rate )

Three mechanisms make that sum grow quickly. First, the iteration count is unbounded: with no hard cap, a loop that fails to converge — a flaky tool, an ambiguous sub-goal, a "keep refining until it's right" instruction — just keeps issuing billable calls, and nothing in the model stops it. Second, the context grows every step: each iteration re-sends the prior transcript plus the new tool output as the next input, so the late steps are the most expensive ones, and a single byte change in the prefix flushes the cache so they bill at full input rate. Third, effort is multiplied inside the loop: a high reasoning_effort default multiplies the per-step reasoning tokens by the step count, which is the most expensive place to be wrong.

The per-call levers each attack one term of that sum. What they cannot do is bound the number of terms or the running total. That is the gap a loop opens, and the five surfaces below are how you close it.

Thresholds — a step cap and a cumulative cost ceiling

You hit this the first time one task quietly costs 40× its neighbors.

Mechanism. A loop needs two bounds a single call never does: a maximum iteration count, and a cumulative token/cost ceiling for the whole task. Either one alone leaks. A step cap still allows an expensive runaway if each step is huge; a cost ceiling alone still allows an endless cheap spin.

Action. Declare, per task class, a max_iterations step cap and a hard_ceiling_usd cumulative ceiling. Derive the ceiling from the p99 (99th-percentile) of a representative sample — step count and per-task cost — not from a round number that feels safe. Set both conservatively and raise them only with evidence.

In-repo evidence. scripts/run_benchmark.py already does exactly this: a pre-run estimate (estimate_experiment_cost_usd) gated by MAX_COST_PER_BENCHMARK_USD, a mid-run hard_ceiling_usd tracked by the BudgetTracker dataclass, and a tool-loop max_iterations cap (agent.max_tool_iterations). docs/05-methodology.md §6 "Budget guards" treats this as methodology, not hygiene: "a silent budget overrun is also a silent change in experiment scope." The same sentence holds in production — a silent loop overrun is a silent change in what the task was allowed to cost.

Intervention — a circuit-breaker that fails closed

You meet this the first time a loop spins all night instead of erroring out.

Mechanism. When a threshold is crossed mid-loop, the loop has to stop deterministically and visibly — return a best-effort partial answer plus a typed "budget exceeded" signal — never silently keep going, and never silently truncate. This behavior distinguishes a bounded cost from a runaway.

Action. Build a circuit-breaker that aborts the loop on any of: the step cap is reached, cumulative cost reaches hard_ceiling_usd, or a no-progress detector fires — for example, the same tool call repeating. On abort, emit a typed terminal record with the termination reason, then make one final answer-only call so the caller still gets something usable. Fail closed: when in doubt, the default is stop, not continue.

In-repo evidence. The runner raises a typed BudgetExceededError ("Raised when pre-run estimate or running total breaches a budget guard"), and BudgetTracker.is_halted enforces a halt before the next call once the total crosses the ceiling; the process exits with a dedicated EXIT_BUDGET code. The tool loop is a clean model of the same idea: on iterations >= max_iterations it fires one final call without tools= so the model is forced to emit a final answer, records tool_loop_terminated="iteration_cap", and appends the recovery leg to the trajectory. That is a fail-closed breaker that leaves a reason behind — lift it into production as-is.

Evals — escalate only where it pays

This one arrives the day "just let it think harder" stops helping but keeps billing.

Mechanism. The repo's central result is that effort above the mid-range buys cost, not quality. On benchmark-03, quality held to a ceiling near 1.97–2.00 across the whole effort ladder while per-request cost rose from $0.002762 to $0.003499 and latency from 2.9s to 3.8s. In a loop the same finding governs the continuation decision: another step, or a higher effort on the next call, should have to earn its place.

Action. Gate escalation — one more iteration, or a higher reasoning_effort on the next call — behind a cheap eval: a rubric score, a self-consistency or confidence signal, an explicit stop check. Default to stop, and make the eval argue for continuing. That turns an open-ended "loop until done" into a bounded "loop until the eval stops paying," which is just the single-call routing decision in loop form.

In-repo evidence. scripts/run_judge.py is the rubric judge already scoring quality in every benchmark; the same shape is the natural continuation gate. The 1.97–2.00 ceiling (results/summary.md §3; benchmarks/03-tool-using-agent/analysis.md) is the measured evidence that an un-gated "think harder, loop again" default keeps spending well past the point of return.

Traceability — attribute cost per loop, per step

This shows up the first time you face a $40 task and can't say which step caused it.

Mechanism. You cannot govern what you cannot attribute. A single end-of-task number hides which step ran away and why. Governance needs per-step records keyed to a stable loop id, each carrying the step's usage, the running cumulative cost, and the budget headroom left.

Action. Extend the per-request capture in docs/14-observability-schema.md with loop-scoped fields: a stable loop_id / task id, a monotonic step_index, the per-step usage block (already captured — reasoning_tokens, cached_tokens, …), a cumulative_cost_usd, and a budget_remaining_usd. Emit one JSONL row per step; the loop's bill is the sum, and the row where budget_remaining_usd first goes non-positive is your intervention point. Alarm on the distribution of step_index at termination, not just its mean — the tail is where the runaways live.

Scope note. Those loop-scoped fields are the next increment, not something already shipped. They slot onto the existing PTURequestRecord — which already carries request_idx and the full usage block — and schemas/ptu_request_record.schema.json. The runner today already sums the per-iteration usage objects into one cell-level dict and records a per-iteration trajectory; loop traceability is that roll-up made first-class — keep the per-step rows, don't only keep the sum.

Governance — the budget is an owned contract

And this one lands when someone bumps a ceiling in a hotfix and the bill moves with no paper trail.

Mechanism. Step caps and cost ceilings are policy, not magic numbers. They have to be owned, version-controlled, and changed through review — like any other contract that decides what the system is allowed to do. A ceiling raise is a scope change, and it should feel like one.

Action. Declare per-task-class budget policy in committed config, not in constants scattered across services. Review every ceiling change; track the overrun rate — how often the breaker fires — as a first-class service-level objective (SLO); and give a ceiling raise the same ceremony as a methodology change. The release-governance discipline in docs/16-release-tiers-and-redaction-policy.md is the same shape applied to published data; this applies it to spend.

In-repo evidence. GOVERNANCE.md provides the owned-contract change-control model for budget policy, and the "silent overrun = silent scope change" rule from docs/05 §6 is the sentence that makes a ceiling change reviewable rather than routine.

Sources and evidence boundary

This topic combines evidence from two tiers. The measured anchor — the benchmark-03 ceiling — is a published result you can audit. The loop-governance pattern is operational design: it reuses primitives that already exist in this repository, but the runaway behavior it guards against is not itself measured here. The tiers below mark where the documented input ends and the design inference begins.

  • [1] Tier 1 — methodology contract: this repository, docs/05-methodology.md §6 "Budget guards." The pre-run estimate plus mid-run hard-ceiling abort this pattern generalizes; the rule "a silent budget overrun is also a silent change in experiment scope" is the governance stance carried into §5.
  • [2] Tier 2 — measured companion (benchmark-03): this repository, results/summary.md §3 and benchmarks/03-tool-using-agent/analysis.md. This is the per-step finding the loop's escalation gate must respect.
  • [3] Operator pattern (design, not a measured tier): the loop controls are lifted from scripts/run_benchmark.py — BudgetTracker / hard_ceiling_usd, BudgetExceededError, EXIT_BUDGET, estimate_experiment_cost_usd gated by MAX_COST_PER_BENCHMARK_USD, agent.max_tool_iterations, and tool_loop_terminated="iteration_cap" — and the rubric gate from scripts/run_judge.py. The canonical write-up is docs/18, introduced as operator lever L6 in docs/09-operator-guide-one-page.md.
  • [4] Proposed next increment (unbuilt): the loop-scoped fields in §4 — loop_id, step_index, cumulative_cost_usd, budget_remaining_usd — extend docs/14-observability-schema.md and schemas/ptu_request_record.schema.json. They are design only; nothing in this topic claims they are shipped.
  • [5] Evidence dashboard: the measured companion is auditable as the rendered benchmark-03 quality and cost chart.

What this topic does and does not establish: it shows how to bound a loop using guards that already run in this repository, and it respects a measured ceiling when deciding whether to continue. It does not measure how often loops run away, the distribution of step counts by task shape, or the long-context cost-scaling curve — docs/04 §4 already records that no benchmark here measures long-output / long-context workloads. These are gaps for a future runaway-characterization benchmark to close, not claims made here.

What the pattern lets us say

For loop work, the useful sentence is not "let it think harder" or "let it loop longer." It is "bound the loop before you run it, and make the bound something you own."

The practical rule

  1. Give every multi-call task two bounds, not one: a max_iterations step cap and a hard_ceiling_usd cumulative ceiling, both sized from a representative p99.
  2. Make the breaker fail closed — on cap, ceiling, or no-progress, stop, record a typed reason, and return a best-effort partial answer.
  3. Gate every escalation behind a cheap eval, and respect the measured ceiling: above the mid-range, effort bought cost, not score.
  4. Keep per-step rows, not just the end-of-task sum, so you can name the step that ran away.
  5. Hold the budget as committed, reviewed policy; track the overrun rate as an SLO and give a ceiling raise the ceremony of a scope change.

L1–L5 bound each call; L6 bounds the loop. Decide when to stop before the loop runs, and make that decision something you own rather than something the model reaches by default.
