专题随笔 · PTU/PAYG 规划模型

PTU/PAYG 交叉点：一条规划线，而非容量结论

这张交叉点图之所以有用，恰恰是因为它有边界。它把公开的成本与 token 形态快照，转化成一个规划问题：在多大的请求速率下，固定的 PTU 花销才会比 PAYG 更划算——针对的是这份被测出来的工作负载形态。它并不能证明一个在线运行的 PTU 资源在压力下会如何表现。

问题

一条被建模出来的 PTU/PAYG 交叉点能告诉我们什么，又绝不能宣称什么？

证据

公开的交叉点 JSON、定价快照，以及 token 形态的吞吐系数。

结论

交叉点是一个决策提示，而不是饱和、429 起点或在线容量的直接证据。

这个模型回答的是一个很窄的问题

交叉点计算把每个请求的平均成本、token 形态的吞吐系数、一份公开定价快照，以及 50 PTU 的下限组合在一起，输出一个被建模出来的盈亏平衡 RPM。举例来说，benchmark-01 extra-high effort 落在约 149 rpm，benchmark-02 none 约 2,680 rpm，benchmark-03 low 约 564 rpm。

这些数字之所以有用，是因为它们揭示了工作负载形态如何改变规划这场对话。它们不是在线压测的测量值——它们不会告诉你 429 从哪里开始、缓存在接近饱和时如何表现，也不会告诉你某套具体服务配置在 p95 延迟下会怎样。

这张图该怎么读

横轴是一组选定的基准行，纵轴是被建模出来的盈亏平衡 RPM。柱子越高，意味着 PAYG 可以爬到更高的请求速率，才会让被建模的 PTU 下限显得更便宜；柱子越矮，意味着这份工作负载更早触及建模出的交叉点。

这些柱子并不是一条连续的容量曲线。它们是从公开聚合数据和一份定价快照推导出来的规划标记。

为什么这个区分很重要

少了这个区分，一张交叉点图很容易被误读成一种承诺。人们很容易说：交叉点在 149 rpm 的那一行“需要 PTU”，而交叉点在 2,680 rpm 的那一行“不需要 PTU”。但证据要比这谨慎得多。这张图说的是：在建模假设之下，经济账长什么样。一个在线系统仍然需要延迟、缓存、重试和饱和方面的证据。

这份谨慎并不是软弱，它正是让这张图可用的原因：它告诉团队何时该去跑一次容量实验，而不是替你预言那次实验会发现什么。

值得记住的那句话

PAYG 和 PTU 回答的是不同的问题。PAYG 问的是每个已完成的请求要花多少钱；PTU 问的是固定容量在可接受的质量与延迟水平下能扛住多少。交叉点这条线把这两个世界连了起来，却没有把它们塌缩成同一个测量。

所以在本项目里，这条线被明确标注为一个被建模出来的假设。它该摆在那些被测量出来的图旁边，而不是凌驾其上。
