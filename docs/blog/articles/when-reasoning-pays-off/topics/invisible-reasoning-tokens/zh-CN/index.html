专题随笔 · 隐藏的计费面

看不见的 reasoning tokens：账单里那段回答没有显示的部分

如果只读回答，那次短问答（short-factual）的运行看上去平平无奇——大多数响应都很简短。但账单讲的是另一个故事：推理模型会在生成可见文字之前，先在模型内部消耗大量 token。这些内部 token 不会展示给用户，却实实在在地被计入了用量。

问题

既然回答文本一直很短，多出来的成本到底是从哪儿来的？

证据

把 benchmark-01 的 token 构成、成本与延迟三张图，当作同一条证据链来读。

结论

沿着 effort 阶梯往上走，可见回答的长度几乎没动，隐藏的 reasoning tokens 却一路上涨。

回答很短，内部的活儿一点不少

benchmark-01 真正值得玩味的地方，并不是 extra-high effort 更贵——这本在意料之中。值得玩味的是：这部分增长，在最终回答里几乎看不出来。minimal effort 平均产出 12.7 个可见输出 token、3.7 个 reasoning tokens；extra-high effort 平均产出 17.9 个可见输出 token，却用掉了 311.5 个 reasoning tokens。

这意味着，读者看到的文字，并不能很好地代表你买下的那部分算力。一个简短的回答可能藏着一大笔推理预算；而一个看似合理的回答，如果配套的质量图没有动，仍然可能是一笔糟糕的经济账。

这张图该怎么读

每根柱子是按 effort 聚合的实验格，而不是单个请求的直方图。横轴是 reasoning-effort 档位，纵轴是每个请求的平均 reasoning tokens；柱子下方那行小字，给出同一格的平均可见输出 token。

从下往上读：先问可见输出有没有变化到足以解释账单；再去比对隐藏的 reasoning 柱。在这一片数据里，能解释账单的不是回答长度，而是内部的运算。

源图补上了什么

token 构成解释了机制，但单凭它还不够。成本图显示账单在上涨；质量图追问这笔账单有没有换来更好的回答；延迟图则反映用户那一端要等多久。把它们放在一起，隐藏的计费面才变得可读：在这一片短问答的切片里，内部 token 更多、花销更大、延迟更长，而质量却没有相应抬升。

值得记住的那句话

这堂课不是说 reasoning tokens 不好——它们正是推理模型的意义所在。这堂课是说：它们需要有活儿可干。如果任务只需要一个简短的事实回答，内部推理就可能变成一处无声的预算漏点；如果任务需要多步推演，同样这些 token 也许恰恰是质量提升的来源。

这也正是综述随笔为什么始终把成本、质量、延迟和 token 构成放在一起看：账单并没有完全显示在回答里。
