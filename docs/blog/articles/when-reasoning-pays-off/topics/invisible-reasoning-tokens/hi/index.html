अदृश्य reasoning tokens: बिल का वह हिस्सा जो जवाब में नहीं दिखता

अगर आप सिर्फ़ जवाब पढ़ें तो short-factual run बिलकुल सामान्य लगता है। ज़्यादातर responses छोटे थे। पर बिल एक अलग कहानी कहता है, क्योंकि reasoning models visible text तैयार करने से पहले model के भीतर ही tokens खर्च कर सकते हैं। ये भीतरी tokens user को नहीं दिखाए जाते, फिर भी ये मापी गई usage surface का हिस्सा होते हैं।

सवाल

अगर जवाब का text छोटा ही रहता है, तो अतिरिक्त लागत आख़िर कहाँ से आई?

निष्कर्ष

दिखने वाले जवाब की लंबाई मुश्किल से बदली, जबकि छिपे हुए reasoning tokens effort ladder के साथ बढ़ते गए।

विषय-सूत्र के अनुसार पढ़ें: जवाब छोटा था; भीतर का काम नहीं chart को कैसे पढ़ें source charts क्या जोड़ती हैं याद रखने लायक कहानी साक्ष्य तालिका

संबंधित source chart खोलें: benchmark-01 token composition chart।

जवाब छोटा था; भीतर का काम नहीं

benchmark-01 में काम की हैरानी यह नहीं है कि extra-high effort की लागत ज़्यादा रही—वह तो अपेक्षित ही था। काम की हैरानी यह है कि इस बढ़ोतरी का कितना कम हिस्सा final answer में दिखा। minimal effort पर औसतन 12.7 visible output tokens और 3.7 reasoning tokens रहे। extra-high effort पर औसतन 17.9 visible output tokens और 311.5 reasoning tokens रहे।

इसका मतलब है कि पाठक को दिखने वाला text उस computation का कमज़ोर proxy है जिसके लिए असल में भुगतान हुआ। एक छोटा जवाब बड़े reasoning budget को छिपा सकता है, और अगर साथ वाली quality chart नहीं हिलती तो एक भरोसेमंद-सा जवाब भी आर्थिक रूप से घाटे का सौदा हो सकता है।

chart को कैसे पढ़ें

ये bars समुच्चय (aggregate) effort cells हैं, अलग-अलग requests का histogram नहीं। X-axis पर reasoning-effort setting है। Y-axis पर प्रति request औसत reasoning tokens हैं। हर bar के नीचे का छोटा label उसी cell के औसत visible output tokens बताता है।

chart को नीचे से ऊपर की ओर पढ़ें: पहले पूछें कि क्या visible output इतना बदला कि बिल की व्याख्या हो सके; फिर छिपे हुए reasoning bar से तुलना करें। इस slice में व्याख्या जवाब की लंबाई नहीं है—यह भीतर का काम है।

source charts क्या जोड़ती हैं

Token composition तंत्र को समझाती है, पर अकेले यह काफ़ी नहीं। cost chart दिखाती है कि बिल बढ़ रहा है। quality chart पूछती है कि क्या उस बिल ने बेहतर जवाब खरीदा। latency chart user को दिखने वाला इंतज़ार दिखाती है। मिलकर ये छिपी हुई surface को पढ़ने लायक बनाती हैं: ज़्यादा भीतरी tokens, ज़्यादा खर्च, ज़्यादा latency—और इस short factual slice में कोई संगत quality लाभ नहीं।

याद रखने लायक कहानी

सबक यह नहीं कि reasoning tokens बुरे हैं—वे तो reasoning model का मूल उद्देश्य हैं। सबक यह है कि उन्हें कोई काम चाहिए। अगर task को सिर्फ़ छोटा factual जवाब चाहिए, तो भीतरी reasoning एक मौन budget leak बन सकता है। अगर task को multi-step समाधान चाहिए, तो वही tokens शायद ठीक वही हों जो quality लाभ कमाते हैं।

यही वजह है कि overview निबंध cost, quality, latency और token composition को एक साथ रखता है। बिल जवाब में पूरी तरह नहीं दिखता।
