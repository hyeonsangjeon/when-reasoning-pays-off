見えない推論トークン：回答には現れない請求の中身

推論への移行後、あるいは誰かが推論努力度のつまみを一段上げたあとでも、回答は相変わらず短く、何事もないように見えることがあります。画面に出るテキストからは、コストが増えた気配は読み取れません。それでも同じワークロードに対して、財務とテレメトリにはより大きな請求が現れます。そこで自然に浮かぶのが、回答が長くなっていないなら、そのコストはどこで発生しているのか、という問いです。

なぜこれを検証したか

この見方は、ほとんどのチームにあります。リクエストのコストを考えるとき、まず目が向くのは目に見える回答の長さです。短い返答は安く、長い返答は高く感じられます。推論以前の時代の大半では、その直感は実務に使える程度には当たっていました。

そうなると、確かめるべき論点ははっきりします。見えている回答の長さが本当に支出を説明していて、より大きな請求は、誰も気づかなかったわずかに長い返答に隠れているのかもしれません。あるいは、推論モデルがその直感を崩し、コストがユーザーの目に触れない隠れた推論トークンへ移ったのかもしれません。どちらが変化を動かしているのかは、チャートで確かめられます。

そこで、請求された各リクエストを入力、キャッシュされた入力、見える出力、隠れた推論に分けました。その分解をコスト・品質・レイテンシの隣に置き、まず短い事実回答の区間、次に多段の区間として読みます。見つかったのは、その対比です。短い事実回答では、隠れた推論チャネルはほとんど開きませんでした。見える出力は推論努力度の階段全体で約 14.0 から 14.8 トークンへ動いただけで、隠れた推論は minimal effort の 0 から、ピークでも 1 トークン未満に近い水準にとどまりました。だからこそ、リクエストあたりの請求は平らでした。見えないチャネルが開いたのは、タスクが多段の解決を求めたときだけです。その場合はリクエストあたり約 110 推論トークンまで増えました。下の1枚要約がその対比を一つの枠に収め、続く各節で計測した詳細を示します。

問い

回答テキストが短いままなら、追加のコストはどこから来ているのでしょうか。

根拠

benchmark-01 と benchmark-02 のトークン構成を、コスト・品質・レイテンシと並べて一本の根拠の連なりとして読みます。

わかったこと

短い事実回答では隠れた推論チャネルがほぼゼロにとどまったため請求は平らでした。多段の作業では同じチャネルがリクエストあたり 0 から約 110 トークンまで増えました。

判断

回答が短いままでも、推論トークンはテレメトリで追跡します。隠れたトークンの予算を、回答が見せない請求の一部として扱います。

筋ごとに読む： 隠れたチャネルが閉じているとき、開くとき チャートの読み方 元チャートが付け加えるもの 押さえておきたい要点 根拠の表

対応する元チャートを開く： benchmark-01 (control) と benchmark-02 (multi-step) のトークン構成。

隠れたチャネルが閉じているとき、開くとき

benchmark-01 で有用な驚きは、何が起きなかった起きなかったかです。推論努力度のつまみを上げても、隠れた予算は静かに膨らみませんでした。minimal effort は平均で約 14.0 の見える出力トークンと 0 推論トークンでした。xhigh effort は平均で約 14.8 の見える出力トークン、そしてなお 1 トークン未満の推論トークンでした。隠れたチャネルは閉じたままだったので、請求は平らで、gpt-5.2 の各セルは gpt-4o ベースライン以下に収まりました。短い事実回答では、モデルに熟考する対象がなかったのです。

多段の区間では、同じ分解が逆の話をします。そこでは隠れた推論が minimal effort の 0 トークンから xhigh の約 110 トークンへ増え、見える出力も約 6 から 117 トークンへ一緒に増えました。直感が外すのはこのケースです。読者が見るテキストは、購入された計算量の代理指標として弱くなります。増えている作業のかなりの部分が、回答に到達しないからです。教訓は、短い回答が安いということではありません。隠れた予算が使われているかどうかは、トークン分解だけが教えてくれるということです。

チャートの読み方

棒は強度設定ごとの集計セルで、個々のリクエストのヒストグラムではありません。X 軸は推論努力度の設定、Y 軸はリクエストあたりの平均推論トークンです。各棒の下にある小さなラベルは、同じセルでの平均見える出力トークン数を示しています。

チャートは下から上へ読みます。まず、請求額を説明できるほど見える出力が変化したかを確かめます。次に、隠れた推論の棒と見比べます。短い事実回答の control ではどちらの棒も低いので、平らな請求に隠れた説明は要りません。多段の区間では、隠れた棒が上がります。

元チャートが付け加えるもの

トークン構成は仕組みを説明しますが、それだけでは十分ではありません。コストチャートは請求額が動いたかを示します。品質チャートは、その支出がより良い回答を買ったのかを問い、レイテンシチャートはユーザーが体感する待ち時間を示します。三つを並べてはじめて、隠れた面が読めるようになります。短い事実回答の control では、内部トークン、支出、品質がそろって平らにとどまります。多段の作業では、内部トークンが請求を動かします。

押さえておきたい要点

教訓は、「推論トークンが悪い」ということではありません。推論トークンは推論モデルの本質そのものです。ここでの教訓は、そのトークンに見合う仕事が必要だという点にあります。タスクが短い事実回答しか求めないなら、内部の推論は静かな予算の漏れになりえます。反対に、タスクが多段の解決を必要とするなら、同じトークンが品質向上を支える中身になりえます。

だからこそ概要記事では、コスト・品質・レイテンシ・トークン構成を常に並べて扱います。請求額のすべてが、回答の中に見えているわけではありません。

出典と根拠の境界

上記の数値はすべて本リポジトリの公開成果物までたどれます。コストに関する記述は、いずれも日付付きの価格スナップショットを基に算定しています。推論トークンの予算をテレメトリで見えるように保つというこの記事の会計上の扱いは、この記事で置いている運用上の解釈です。下の二つの Tier は、文書化された入力がどこで終わり、推論がどこから始まるかを示しています。

  • [1] Tier 1 — 方法論の契約： 本リポジトリ、docs/05-methodology.md（v1.0）です。セルあたり N = 20 のサンプル、R = 3 回の反復で、対象は公開集計の区間のみです。チャート読解の本文はこの固定前提に立っており、誤差バーは信頼区間ではなく標準偏差で、N = 20 では p 値を主張しません。
  • [2] Tier 1 — PAYG 価格スナップショット： リクエストあたりのコストは本リポジトリの pricing/azure-openai-payg-2026-05.yaml で算定しています。2026-05-19 アクセス：Azure OpenAI 価格ページ、アーカイブです。定価が動けば、隠れたトークンの請求も変わります。
  • [3] Tier 2 — benchmark-01 区間の測定（control）： 本リポジトリ、benchmarks/01-short-factual/analysis.json です。平らな隠れトークンの読みの出典です——推論トークンは medium effort まで 0 にとどまり、ピークも約 1.35、見える出力は 14.0 から 14.8 へ動くだけです——だからこの区間ではリクエストあたりの請求が動きませんでした。
  • [4] Tier 2 — レンダリング済みチャートデータ（control）： 本リポジトリ、docs/blog/data/chart-data/token-composition/benchmark-01/tokens.json がトークン分解の出典です。docs/blog/data/chart-data/cost-curves-effort/benchmark-01/cost-per-request.json、quality.json、latency.json と一緒に読むと、隠れたチャネル、請求、待ち時間がそろって平らだったという対になる根拠になります。
  • [5] Tier 2 — 多段の測定（positive case）： 本リポジトリ、docs/blog/data/chart-data/token-composition/benchmark-02/tokens.json です。ガイドチャートが示す上昇の出典です——隠れた推論は推論努力度の階段で 0, 17.433333, 32.0, 43.55, 109.55 と上がり、見える出力は 5.75 から 117.266667 へ上がります。見えない請求が実際に大きくなるのはここです。
  • [6] 根拠ダッシュボード： レンダリングされた benchmark-01 と benchmark-02 のトークン構成チャートは、同じ成果物を監査できる形です。

この根拠が示すことと、示さないことを分けておきます。隠れた推論チャネルはタスク依存です——短い事実回答の control ではほぼゼロで、多段の区間では見える出力にほぼ並ぶまで上がります。ツールエージェントや統合の作業でも同じ形だとは証明していません。各トピックはそれぞれ固有の測定を持っています。大事なのは大きさではなく、この測り方の習慣です。どちらのケースにいるかは、トークン分解だけが教えてくれます。

実務上のルール

  1. 合計トークンだけでなく、リクエストごとの推論トークンを見える出力の隣に記録してください。
  2. 短い回答でも大きな内部コストを抱えうるため、隠れたトークンの予算にアラートを設定してください。
  3. このワークロードの形で対になる品質チャートが改善されたあとにだけ、より高い推論努力度へ引き上げてください。

見える回答が短いままでも、推論トークンはテレメトリで測定してください——隠れたトークンの予算は、回答が見せない請求の一部です。
