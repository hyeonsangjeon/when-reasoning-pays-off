Short factual work: when extra reasoning buys cost, not quality

When a team first adopts reasoning models, short factual questions feel like the easy place to turn effort up: the answer is short, a mistake is easy to spot, and a little extra thinking feels like cheap insurance. So the instinct is to raise reasoning effort here first. That instinct is a hypothesis worth testing, not a policy worth shipping — and this essay tests it with data.

Why we tested this

The situation is familiar. A migration lands the team on a reasoning model, the configuration exposes a reasoning-effort dial, and short factual questions look like the safest place to turn it up. The output is brief, an error is obvious, and "let it think a bit more" sounds like cheap insurance — so raising the default here feels almost free.

That gives us a clean hypothesis to check: on short factual work, does higher reasoning effort actually make the answer safer? If it does, the higher default earns its place. If it does not, the team is paying for thinking that never reaches the reader.

So we tested it. We held the workload shape fixed — the same short factual slice — and walked the effort ladder one step at a time, comparing cost per request, latency, the visible answer text, the hidden reasoning tokens, and the judge score at each level. In this slice the result was the kind that should move a default: effort bought cost, latency, and hidden tokens, but not a better answer. The one-pager below states that in a single frame, and the sections after it show the measured detail.

Question

If the task mostly asks for short factual answers, does higher reasoning effort improve quality enough to justify the bill?

Evidence

benchmark-01 cost, quality, latency, and token-shape charts, paired with the public data tables.

Finding

On this slice, cost per request climbed about 7.6x, but the mean judge score did not rise — it moved from about 1.88 to about 1.78.

Decision

Default to the lowest effort that already answers correctly. Escalate only after an evaluator shows a real quality lift on this workload shape.

What the data showed

The hypothesis predicted a safer answer at higher effort. The data did not deliver one. The cost bars climb from $0.000663 at minimal effort to $0.005043 at extra-high effort, but the quality bars do not climb with them: the mean judge score is 1.88 at minimal effort and 1.78 at extra-high effort. Latency also stretches from about 1.1s to about 3.1s. The work is not free on the capacity side either: the token-shape throughput factor falls from 0.98 to 0.45.

So the cost bars climbed and the quality bars did not — that is the whole story the chart is trying to tell. The taller cost bar is real, the taller hidden-token budget is real, and the matching quality lift is missing. For this workload shape, higher effort should stay experimental rather than become the default.

Why the hypothesis can fail

The safe-looking default can still disappoint, because short factual work rarely needs a long internal search. When the answer is a single fact, the bottleneck tends to be retrieval, a stable prompt, or simply the lowest effort setting that already lands the correct answer — not extra deliberation. Past that point more thinking has nothing left to find, so the effort ladder keeps adding hidden tokens without adding accuracy.

That is the shape the slice shows. The judge score does not climb with effort; it drifts from 1.88 down to 1.78 while cost, latency, and hidden reasoning all grow. The thinking is real, but it stays inside the model and never reaches the reader — which is exactly why a higher default here becomes a cost the answer never repays.

How to read the chart

The bars are aggregate bar charts, not frequency histograms. Each bar stands for one effort cell in benchmark-01, so the comparison is about how the same workload shape changes as effort rises.

X-axis

The bars move left to right across reasoning effort levels: baseline, minimal, low, medium, high, and extra-high. Treat this as the control knob the operator can change.

Y-axis

In the cost chart, bar height means mean USD per request. In the quality chart, bar height means mean judge score. Read them as a pair, not separately.

Bars and table

Each bar is an aggregate cell. The table below the chart shows the exact value, standard deviation where available, and sample count. Error bars are standard deviation, not confidence intervals.

What the source charts contribute

Each source chart answers a different part of the decision. The cost chart says what the setting costs. The quality chart says whether the spend bought a better answer. Latency and token composition explain the operational side effects. The throughput view translates the same token shape into planning pressure.

What happened

The cost curve rose sharply. Minimal effort averaged $0.000663 per request; extra-high effort averaged $0.005043 per request, a 7.6x bill. The paired quality movement did not justify that spend: the mean judge score moved from 1.88 to 1.78.

That is not a universal claim that reasoning is bad. It is a workload shape claim. In this slice, the added internal computation did not buy a matching answer-quality gain. The dashboard makes the mismatch visible because cost and quality are kept side by side.

The key trap is that the output can still look reasonable. If a reviewer only samples a few answers, extra-high effort may feel safer because the model appears to have thought harder. The chart prevents that intuition from becoming policy: it asks for a measured quality delta before accepting the higher cost, slower latency, and larger hidden-token bill.

What we learned while benchmarking

More thinking is not a default

Effort is a treatment. It should be applied to a slice, measured, and promoted only if the evaluator moves. Treating it as a global default hides the bill until production traffic arrives.

Cost must be paired with quality

A cost-only chart can make the change look obvious but incomplete. A quality-only chart can hide the economic cost. The useful view is the pair: what did we buy, and did it improve the answer?

Short factual work needs a low-effort baseline

The lowest acceptable effort level is the baseline to beat. If a higher level does not beat it on quality, the operator should keep the cheaper setting and spend optimization time elsewhere.

When to revisit the decision

Do not freeze this conclusion forever. Re-test if the task changes from short recall into synthesis, if the judge rubric starts rewarding multi-hop justification, if the prompt begins carrying tool outputs, or if a new model changes the cost-quality shape. The lesson is not “never use reasoning.” The lesson is “do not promote effort without paired evidence.”

A useful follow-up experiment keeps the same X-axis but changes the workload slice: short factual, multi-step, tool-agent, and synthesis tasks should each earn their own effort setting. That routing policy is where reasoning usually pays off.

What this slice does and does not prove: it shows that on this short-factual workload shape, in one tenant and one region under this pricing snapshot, the effort ladder bought cost and hidden tokens without a matching quality lift. It does not prove the same shape holds for synthesis, multi-step, or tool-using work, or under a future pricing snapshot.

The practical rule

The practical rule: keep short factual work at the lowest effort that already answers correctly, and promote a higher effort only after a quality gate moves on this workload shape — read next to its paired cost, latency, and token-composition charts.
