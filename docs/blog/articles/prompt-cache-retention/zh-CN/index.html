运营随笔 · 提示缓存留存

留存是一项请求策略，而非一种假设

提示缓存看起来似乎是自动的，因为受支持的模型会默认缓存符合条件的 前缀。但留存窗口并不是可以想当然认定的东西。 如果某项操作依赖更长时间的复用，请求就应当通过 prompt_cache_retention 把这一点明确说出来。

问题

当操作预期稍后会复用缓存时，请求是否真的申请了那个窗口？

证据

Microsoft Learn 定义了这些留存模式；本仓库补充了稀疏的公开延迟与命中率证据。

决策

把留存设为显式，保持前缀稳定，并把延迟与缓存令牌占比放在一起读。

官方行为 · 两种留存模式

自动缓存与显式留存并不是一回事

Microsoft Learn 描述了两种提示缓存留存策略： in_memory 与 24h。内存中的缓存条目 通常会在停用 5 到 10 分钟内被清除，并且总会在最后一次使用后 一小时内被移除。扩展留存可以让缓存的前缀保持更长时间的活跃， 最长可达 24 小时。

默认可能很短

对于 gpt-5.4 及更早的模型，省略留存意味着 in_memory。

更长的复用需显式声明

如果操作预期稍后会复用，请在受支持的情况下把 prompt_cache_retention 设为 24h。

价格不是区分点

Microsoft Learn 指出，两种留存策略的提示缓存定价是相同的。

运营策略 · 遇到歧义即失败关闭

如果留存很重要，就让这个选择可被观察

公开仓库包含一个小型的留存策略辅助工具，它会对那些 文档默认值为 in_memory 的模型拒绝省略的取值。 这听起来很严格，但它能防止常见的失败模式：设计假设了 一个更长的缓存窗口，而请求体却悄悄沿用了那个较短的默认值。

好

当工作负载依赖稍后复用时，使用 prompt_cache_retention="24h"。

也好

当工作负载只需要短时复用并且明确说明时，使用 prompt_cache_retention="in_memory"。

有风险

在运营手册假设了更长窗口的情况下，却让该取值缺省。

治理说明 · 留存不只关乎延迟

更长的留存还需要一次治理检查

Microsoft Learn 指出，内存中的提示缓存与所有数据驻留 区域兼容。对于扩展留存，它表示缓存数据只有在区域标准 或区域预置模式下才会保持在区域内。这使得留存既是一项 性能决策，也是一项治理决策。

实用规则是：不要把留存埋在默认值里。把预期的取值 写进代码，观察缓存令牌占比与延迟，并为你所使用的 服务模式确认其驻留要求。
