운영 에세이 · 프롬프트 캐시 리텐션

리텐션은 가정이 아니라 요청 정책이다

지원되는 모델은 적격 프리픽스를 기본적으로 캐싱하기 때문에 프롬프트 캐싱은 자동처럼 느껴질 수 있습니다. 하지만 리텐션 윈도는 가정할 대상이 아닙니다. 어떤 작업이 더 긴 재사용에 의존한다면, 요청이 prompt_cache_retention으로 그 의도를 명시해야 합니다.

질문

작업이 나중의 캐시 재사용을 기대할 때, 요청은 실제로 그 윈도를 요구하고 있는가?

근거

Microsoft Learn이 리텐션 모드를 정의하고, 이 저장소는 희소한 공개 지연 시간과 적중률 근거를 더합니다.

결정

리텐션을 명시하고, 프리픽스를 안정적으로 유지하며, 지연 시간을 캐시 토큰 비중과 함께 읽으십시오.

질문별로 읽기: 공식 동작 공개 근거 운영 정책 레지던시 참고 출처

범위 참고: 아래의 공개 측정값은 희소한 소스 실행 근거입니다. 보편적인 지연 시간 주장이 아니라 운영 체크리스트를 뒷받침합니다.

공식 동작 · 두 가지 리텐션 모드

자동 캐싱은 명시적 리텐션과 같지 않다

Microsoft Learn은 두 가지 프롬프트 캐시 리텐션 정책을 설명합니다. in_memory와 24h입니다. 인메모리 캐시 항목은 일반적으로 비활성 상태 5~10분 이내에 제거되며, 마지막 사용으로부터 한 시간 이내에는 항상 제거됩니다. 확장 리텐션은 캐시된 프리픽스를 더 오래, 최대 24시간까지 활성 상태로 유지할 수 있습니다.

기본값은 짧을 수 있다

gpt-5.4 및 이전 모델에서는 리텐션을 생략하면 in_memory를 의미합니다.

더 긴 재사용은 명시적이다

작업이 나중의 재사용을 기대한다면, 지원되는 곳에서 prompt_cache_retention을 24h로 설정하십시오.

가격은 차별화 요소가 아니다

Microsoft Learn은 프롬프트 캐시 가격이 두 리텐션 정책에서 동일하다고 명시합니다.

운영 정책 · 모호하면 닫힘으로 실패

리텐션이 중요하다면, 선택을 관측 가능하게 하라

공개 저장소에는 작은 리텐션 정책 헬퍼가 포함되어 있는데, 문서화된 기본값이 in_memory인 모델에서 값이 생략되면 이를 거부합니다. 엄격하게 들리지만, 흔한 실패 양상을 막아 줍니다. 설계는 더 긴 캐시 윈도를 가정하는데 요청 본문은 조용히 짧은 기본값을 취하는 경우입니다.

좋음

워크로드가 나중의 재사용에 의존할 때 prompt_cache_retention="24h".

이것도 좋음

워크로드가 짧은 재사용만 필요하고 이를 명시할 때 prompt_cache_retention="in_memory".

위험함

운영 런북은 더 긴 윈도를 가정하는데 값을 비워 두는 것.

거버넌스 참고 · 리텐션은 단지 지연 시간만이 아니다

더 긴 리텐션에는 거버넌스 점검도 필요하다

Microsoft Learn은 인메모리 프롬프트 캐싱이 모든 데이터 레지던시 지역과 호환된다고 명시합니다. 확장 리텐션의 경우, 캐시된 데이터가 지역 내에 머무는 것은 Regional Standard 또는 Regional Provisioned 모드에서만 해당한다고 말합니다. 이는 리텐션을 성능 결정뿐 아니라 거버넌스 결정으로 만듭니다.

실용적인 규칙은 이렇습니다. 리텐션을 기본값에 묻어 두지 마십시오. 의도한 값을 코드에 두고, 캐시 토큰 비중과 지연 시간을 관측하며, 사용하는 서빙 모드에 대한 레지던시 요구 사항을 확인하십시오.

출처와 근거 경계

  • 공식 명세, 2026-06-04 접근: Microsoft Learn 프롬프트 캐싱 가이드.
  • 공개 집계 근거: 캐시 키 버케팅 CSV.
  • 공개 운영자 가이드: 프롬프트 캐시 키 정책 런북.

실용적인 규칙은 이렇습니다. 짧은 윈도 이후에도 캐시 재사용이 중요하다면, prompt_cache_retention을 명시하고 관측된 지연 시간 형태를 검증하십시오.
