实验回顾 · 横跨三种任务形态 · 视角：任务形态(task-shape)

推理强度是否值得 — 假设，以及测量推翻了什么

作者 Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

我们曾预先登记一个预测：在多步推理中，更高的推理强度(reasoning_effort)会值得付出。跨三个基准测量 1,080 个单元后，结果推翻了这个预测。无论是短事实、多步，还是工具智能体，答案一次也不是 high 或 xhigh。把强度提到中档以上，质量保持不变，成本上升，吞吐下降。本文像讲故事一样回看这段路。它沿着“曾经预期什么，哪里出了偏差，因此把什么设为默认值”，既按时间顺序(时间线)，也按问题顺序(逐问题回顾)重走一遍。这里不只留下结论，也留下我们走过的路。而且不是到文末才说，你可以现在就用一行命令自己复现。

为什么值得读

那个旋钮，什么时候该调高？

如今的模型里，常有一个叫 推理强度 的旋钮，用来决定模型给出答案前，先在心里多想多久。调高后好像会更聪明，所以拿不准时，很容易先设高一点。但只要调高旋钮，不管答案有没有变好，钱和时间都会实打实多花。 所以“先调高再说”这个习惯，可能只会把每月的账单越推越高。

这篇回顾要用实测、而不是猜测，来分清这个旋钮 什么时候值回成本、什么时候只是浪费。 我们按性质把工作分成三类 — 一次到位的 短事实、要走好几步的 多步、以及会调用工具的 工具智能体。你的服务在做的事，大多也落在这三类里。

如果你要为生产环境挑一个模型和强度，这里能带走 怎么定默认值 的办法。办法很简单 — 先定一条质量 门槛，再在越过这条线的配置里，挑最便宜也最快的。这条规则如何在三场实验里汇成同一个结论，下面会顺着预测和反转，一个一个讲给你看。

问题

在新的生产任务上，提高推理强度是否值得？并且在 PAYG(每美元正确答案)与 PTU(固定容量下每分钟正确答案)两个视角下是否都值得。

证据

三个基准 — 01 短事实(Null) · 02 多步(Ceiling) · 03 工具智能体(Mixed) — 各自以 N=20 样本 × R=3 重复、强度 {none, low, medium, high, xhigh} 加 gpt-4o 基线测量。总计 1,080 个单元。所有成本均按每 1,000 次归一化，并重新引用各基准的 analysis.md。

决定

最佳的(模型, 强度)取决于任务形态和消费模型。选择方法很简单：先定质量门槛，再在通过这条线的配置中，挑最便宜也最快的。于是共同结论就浮出来了 — 答案绝不是 high 或 xhigh。超过中档以后，没有质量收益，只会增加成本、削减吞吐。

建议这样读： 时间线 — 何时、哪里出现偏差 逐问题回顾 — 为什么实验，学到了什么 下一次判断 · 下一项实验

时间线

我们走过的顺序

实验并不是一次就得出结论。按日期顺序看下面五个场景，就能依次看到预测在哪里偏离、默认值在哪里改变。

  1. 2026年 5月以前 — 预先登记。 开始测量前，我们先写下预测：如果是多步任务，更高的推理强度会提高质量，足以证明成本合理。为了避免之后按结果改故事，我们把 gpt-5.2 的强度从 none 到 xhigh 固定为五档，并放入 gpt-4o 基线。正因为有这份预先登记，后面的‘推翻’才有分量。
  2. 2026年 5月 — 短事实案例(01)，触到底部。 我们先用不需要推理的短事实任务确认成本曲面的底部 — 三个基准中，只有这个底部被重新做成实测(360 个单元全是真实 Azure 调用，没有 fixture 标记)。gpt-5.2 在完全不开推理的 none 下，正确率已经以 95% 饱和，反而高于 gpt-4o(90%)。每 1,000 个正确答案成本为 $0.62，比 gpt-4o($0.74)便宜 16%(按每 1,000 次请求也便宜 12%)。所以短事实 PAYG 默认值定为 gpt-5.2 none — 但在固定容量(PTU)视角下，两种模型吞吐在约 1% 内重叠，实质上是平手。这个实验在 exp001 实验笔记中逐项拆解。
  3. 2026年 5月 — 多步案例(02)，转折点。 这一次本该是推理获胜。可打开结果后，gpt-5.2 在完全不开任何推理的默认状态(none)下，把二十道题全答对了。先验假设就在这里倒下。每 1,000 个正确答案成本从 gpt-4o 的 $1.06 降到 $0.62，下降 42%，PTU 下每分钟正确答案增加 32.5%，而继续提高强度并没有推动质量。所以我们把多步默认值设为 gpt-5.2 none，并放弃上调强度。决定胜负的不是‘强度旋钮’，而是‘模型替换’。这个实验在 exp002 实验笔记中逐项拆解。
  4. 2026年 5月 — 工具智能体案例(03)，意外发现。 最后是使用工具的智能体(无工具、单工具、多工具混合)。让我们意外的是 gpt-4o。即使提示是‘用一般知识回答’，它也习惯性地调用计算器，使无工具通过率跌到 83.3%。相对地，gpt-5.2 只用 low 就守住多工具 100%，并达到每 1,000 个正确答案 $2.77(比 gpt-4o 的 $3.65 便宜 24%)。所以工具默认值是 gpt-5.2 low。但超过 low 后，吞吐在 medium 被削 8.5%、在 xhigh 被削 10.8%，把收益又还了回去。这个实验在 exp003 实验笔记中逐项拆解。
  5. 2026年 7月 — 弥合证据与复现之间的缝隙。 测量结束后，剩下的是另一类作业。反馈说：‘大家对部署很感兴趣，但 README 和验证层没能完全接住这种兴趣。’实际中新访客会卡在 editable install 失败(PEP 660)或损坏的运行命令上。于是我们加入无需凭据的一行验证(verify_setup.sh)、逐实验指南卡片，以及拆分的 requirements.txt，弥合‘证据’与‘复现’之间的缝隙。本文开头的 10 秒复现就是结果。

逐问题回顾

为什么实验，学到了什么

同样的结果，这次从问题出发。先放下‘我们好奇什么’，再逐一回答三个问题。

Q1 — 短事实任务需要推理吗？

从最简单的问题开始。对于一次就能答出的短事实任务(抽取·格式·分类·音译·算术)，推理强度看起来没有开启的理由。三项基准中，我们只把这个底部重新做成了实测 — 360 个单元全是真实 Azure Foundry 调用，没有 fixture 标记，评审评分 360/360。

预测没有反转，原样成立。gpt-5.2 在完全不开推理的 none 下，正确率已经以 95% 饱和，反而高于 gpt-4o(90%)。每 1,000 个正确答案 $0.62，比 gpt-4o($0.74)便宜 16%(按请求也便宜 12%)。把强度提高到 xhigh，隐藏推理 token 仍接近 0，所以质量和成本几乎都不动 — 这是强度旋钮没有接到任何地方的位置。所以短事实默认值是 gpt-5.2 none。详细拆解见 exp001 实验笔记。

Q2 — 多步任务上提高强度是否值得？

假设很简单。对于必须经过若干阶段的问题，high 或 xhigh 带来的质量提升会证明成本上升合理。为检查这一点，我们把 gpt-5.2 的五档强度(none 到 xhigh)与 gpt-4o 基线并排比较，二十道题每题重复三次。

结果推翻了假设。gpt-5.2 在 none 就已经 100% 正确，每 1,000 个正确答案 $0.62，比 gpt-4o($1.06)便宜 42%，PTU 下每分钟正确答案多 32.5%。意外的是，gpt-4o 也比我们想得更好 — 超过预先写下的 30–60% 范围，记录为 75%。样本很小(N=20，无置信区间)，所以节省幅度的大小要谨慎解读，但方向很清楚。因此多步默认值定为 gpt-5.2 none，high·xhigh 没有被采用。

Q3 — 对工具智能体来说，推理越多越安全吗？

计划串联的工具越多，更多推理似乎越可能提高可靠性。因此在二十个混合了无工具、单工具、多工具的任务上，我们再次让 gpt-5.2 的各档强度与 gpt-4o 对照。

真正的分界线不是推理的量，而是调用工具的习惯。gpt-4o 即使在‘用一般知识回答’的无工具提示中也调用计算器，通过率降到 83.3%，而 gpt-5.2 即使无工具也保持 100%。成本上，gpt-5.2 low 也领先：每 1,000 个正确答案 $2.77(比 gpt-4o 的 $3.65 便宜 24%)，多工具 100%，PTU +4.3%。一个限制是：这里的 web_search 不是真实网页调用，而是模拟的固定知识库查询。结论再次相同 — 一点点推理就够了，工具默认值是 gpt-5.2 low，超过它就是 token 浪费。

循环的另一侧 — 数字从哪里来

现场规则

不要因为推理强度“看起来更聪明”就提高它。把成本 · 质量 · 延迟 · token 构成放在一起读，只在强度确实值得的位置才多花 token。在已测量的三种任务形态中，high 和 xhigh 一次也不是默认值。

接下来

下一次判断 · 下一项实验

下一次判断。 这个结论只在“已测量的任务形态”内有效。如果链条更长，或真实工具进入，曲线可能再次移动；因此规则是：工作负载形态改变时就重新测量。

下一项实验。 这里的 PTU 数字是基于 token 的估算(不是实时负载)。下一项实验是在真实 PTU 部署上的负载测试 — 限速调节 · 排队 · 并行批处理如何作用于吞吐。

第一份结果已经出来。 exp004 — PTU 溢出策略模拟(Phase 1)把 proactive 溢出策略和 reactive 放到一起，检验饱和负载下谁更能保护缓存。答案接近平手：proactive 的稳态缓存反而低 0.1657 pp，而且一次也没有触发溢出。真正的判决要交给物理分离的双部署负载测试(Phase 2)。

而这个判决已经出来。 exp005 — 双部署溢出测试(Phase 2)在两个拥有物理独立缓存的在线部署上，把同一个问题重新跑了一遍。这一次差距反而拉大了 — proactive 的稳态缓存低 0.9923 pp(约为 Phase 1 的 6 倍)，成本也更高，因为把流量一分为二，会让你原本焐热的那个缓存池重新变冷。两个 Phase 得出了同一个结论 — 当缓存在物理上彼此独立时，reactive 更胜一筹。

然后我们拆的不是部署，而是“键”。 exp006 — 缓存键切得再细，缓存也几乎没变在一个部署内追问：把 prompt_cache_key 从 1 个拆到 8 个，缓存会不会活回来。答案仍是“几乎没变”：即使把文档上限 2 倍的流量(30 requests/min)压到一个键上，稳态缓存命中仍保持 93–96%；拆成 8 个的收益最多只有 2.52pp。真正拉开差距的不是基数，而是 保留策略，24h 保留把尾部延迟(TTFT p95)从 106s→10s。

接着读： 429 不是错误，而是恢复信号 — 当 PTU 容量说“现在不行”时，客户端应该如何决定下一步？

来源 & 证据边界

这篇回顾没有引入新的测量；它重新引用了按每 1,000 次归一化的已发布数字。原始材料与边界如下。

  • 交叉摘要：results/summary.md(§3 headline, §5 decision boundary, §6 limits)。所有成本均重新引用自各基准的 benchmarks/0[123]-*/analysis.md。
  • 公开复现范围：docs/05-methodology.md §7 区分公开证据验证、在新环境中按相同方法重跑，以及仅所有者可审计的原始证据。
