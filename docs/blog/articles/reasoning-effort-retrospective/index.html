Does reasoning effort pay off — the hypothesis, and what measurement overturned

By Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

We pre-registered a prediction: for multi-step reasoning, a higher reasoning effort (reasoning_effort) would pay off. Measuring 1,080 cells across three benchmarks overturned that prediction. Short-factual, multi-step, or tool agent — the answer was never high or xhigh. Raise the effort above the middle and quality holds flat while cost rises and throughput drops. This retrospective retraces that path as a story. It follows “what we expected, what broke, and what we therefore chose as the default” both in time order (a timeline) and by question (a per-question retrospective). It keeps not only the conclusions but the road we walked. And you can reproduce it yourself, right now rather than at the very bottom, with a single command.

Why read this

That dial — when should you turn it up?

Modern models come with a dial called reasoning effort — how much the model mulls things over before it answers. Turning it up feels like it should make the model smarter, so when you’re unsure it’s tempting to just crank it. But raising the dial reliably costs more money and time whether or not the answer improves. So the habit of “just turn it up” can quietly inflate the monthly bill.

This retrospective settles when that dial pays off and when it’s waste — by measurement, not by guessing. We split the work into three shapes by character: short-factual that finishes in one shot, multi-step that walks through stages, and a tool agent that calls out to tools. Whatever your service does, it likely falls into one of these three.

If you have to pick a model and an effort level for production, you can take away how to set the default. The method is simple — set a quality passing bar first, then among the configs that clear it, pick the cheapest and fastest. Below, following each prediction and reversal, we show how all three experiments converged on the same conclusion.

Question

On a new production task, does raising reasoning effort pay off? And under both viewpoints — PAYG (correct answers per dollar) and PTU (correct answers per minute per fixed capacity).

Evidence

Three benchmarks — 01 short-factual (Null) · 02 multi-step (Ceiling) · 03 tool agent (Mixed) — each measured at N=20 samples × R=3 repeats, effort {none, low, medium, high, xhigh} plus a gpt-4o baseline. 1,080 cells total. All costs are normalized per 1,000 and re-cite each benchmark’s analysis.md.

Decision

The best (model, effort) depends on task shape and consumption model. The way to choose is simple: set a quality passing bar first, then among the configs that clear it, pick the cheapest and fastest. The shared conclusion then shows itself — the answer was never high or xhigh. Past the middle, cost rises and throughput is shaved with no quality gain.

Timeline

The order we walked

The experiment didn’t resolve in one shot. Follow the five scenes below in date order, and you see in turn where the prediction went wrong and where the default changed.

  1. Before May 2026 — pre-registration. Before measuring, we wrote the prediction down first: that for multi-step tasks, higher reasoning effort would lift quality enough to justify the cost. So we couldn’t bend the story to the results later, we fixed gpt-5.2’s effort across five steps from none to xhigh and set a gpt-4o baseline alongside. Because this pre-registration existed, the ‘overturning’ that follows carries weight.
  2. May 2026 — short-factual case (01), hitting the floor. First we checked the floor of the cost surface with a short-factual task that needs no reasoning — of the three benchmarks, only this floor was re-measured as real data (all 360 cells real Azure calls, no fixture markers). gpt-5.2 was already saturated at 95% accuracy at none, with no reasoning turned on at all — higher, in fact, than gpt-4o (90%). Cost per 1,000 correct answers was $0.62, 16% cheaper than gpt-4o ($0.74) (and 12% cheaper per 1,000 requests). So the short-factual PAYG default became gpt-5.2 none — though seen through the fixed-capacity (PTU) view the two models’ throughput overlapped within about 1%, effectively a tie. This experiment is taken apart piece by piece in the exp001 experiment note.
  3. May 2026 — multi-step case (02), the turning point. Now reasoning was supposed to win. But when we opened it up, gpt-5.2 got all twenty questions right in its default state (none) with no reasoning turned on. The prior hypothesis collapsed right there. Cost per 1,000 correct answers fell from gpt-4o’s $1.06 to $0.62 (42% down) and PTU correct-per-minute rose 32.5%, while raising the effort didn’t budge quality. So we set the multi-step default to gpt-5.2 none and scrapped the effort increase. What decided it was not the ‘effort dial’ but the ‘model swap.’ This experiment is taken apart piece by piece in the exp002 experiment note.
  4. May 2026 — tool agent case (03), the surprise. Last came a tool-using agent (a mix of no-tool, one-tool, multi-tool). Here the one who surprised us was gpt-4o. Even on a ‘answer from general knowledge’ prompt it reached for the calculator out of habit, dropping no-tool pass rate to 83.3%. gpt-5.2, meanwhile, held multi-tool 100% with just low and reached $2.77 per 1,000 correct answers (24% cheaper than gpt-4o’s $3.65). So the tool default is gpt-5.2 low. But push past low and throughput was shaved 8.5% at medium and 10.8% at xhigh, undoing the gain. This experiment is taken apart piece by piece in the exp003 experiment note.
  5. July 2026 — closing the gap between evidence and reproduction. The homework left after measuring was a different kind. Feedback came that ‘the interest in deploying is high, but the README and validation layer don’t fully catch that interest.’ In practice new visitors stalled on an editable-install failure (PEP 660) or a broken run command. So we added a credential-free one-line validation (verify_setup.sh), per-experiment guide cards, and a split requirements.txt to close the gap between ‘evidence’ and ‘reproduction.’ The 10-second reproduce at the top of this page is the result.

Per-question retrospective

Why we ran it, and what we learned

The same results, this time starting from the question. We put ‘what were we curious about’ first, and answer three questions one by one.

Q1 — does a short-factual task need reasoning?

Start with the simplest question. For a short factual task answered in one shot (extraction · formatting · classification · transliteration · arithmetic), there seemed to be no reason to turn on reasoning effort. Of the three benchmarks, we re-measured this floor as real data — all 360 cells real Azure Foundry calls, no fixture markers, judge scoring 360/360.

The prediction held with no reversal. gpt-5.2 was already saturated at 95% accuracy at none with no reasoning turned on — higher, in fact, than gpt-4o (90%). At $0.62 per 1,000 correct answers it was 16% cheaper than gpt-4o ($0.74) (and 12% cheaper per request). Raising the effort to xhigh kept the hidden reasoning tokens near zero, so neither quality nor cost moved — a place where the effort dial is wired to nothing. So the short-factual default is gpt-5.2 none. The detailed dissection is in the exp001 experiment note.

Q2 — does raising effort pay off on multi-step?

The hypothesis was simple. For a problem that has to pass through several stages, the quality lift of high or xhigh would justify the cost increase. To check it we compared gpt-5.2’s five efforts (none through xhigh) alongside a gpt-4o baseline, twenty questions repeated three times each.

The result overturned the hypothesis. gpt-5.2 already got 100% right at none, at $0.62 per 1,000 correct answers it was 42% cheaper than gpt-4o ($1.06), and PTU correct-per-minute was 32.5% higher. What was unexpected is that gpt-4o did better than we thought too — beyond the 30–60% we’d written down in advance, it recorded 75%. With a small sample (N=20, no confidence intervals) the size of the savings must be read carefully, but the direction was clear. So the multi-step default is gpt-5.2 none, and high·xhigh were not adopted.

Q3 — is more reasoning always safer for a tool agent?

The more tools a plan chains, the more reasoning seemed likely to raise reliability. So across twenty tasks mixing no-tool, one-tool, and multi-tool, we again pitted gpt-5.2’s efforts against gpt-4o.

The dividing line turned out to be not the amount of reasoning but the habit of calling tools. gpt-4o reached for the calculator even on the no-tool ‘answer from general knowledge’ prompt, dropping to 83.3%, whereas gpt-5.2 held 100% even with no tools. On cost too, gpt-5.2 low led at $2.77 per 1,000 correct answers (24% cheaper than gpt-4o’s $3.65), multi-tool 100%, PTU +4.3%. One caveat: here web_search is not a real web call but a mocked fixed knowledge-base lookup. The conclusion was again the same — a little reasoning is enough, the tool default is gpt-5.2 low, and beyond that is wasted tokens.

The field rule

Don’t raise reasoning effort because it “looks smarter.” Read cost · quality · latency · token composition together, and spend more tokens only where effort actually pays off. Across the three task shapes measured, high and xhigh were never the default.

Next

Next call · next experiment

Next call. This conclusion holds only within the “task shapes measured.” If the chain grows longer or real tools come in, the curve can move again, so the rule is to re-measure when the workload shape changes.

Next experiment. The PTU figures here are token-based estimates (not a live load). The next experiment is a load test on a real PTU deployment — how rate-limit control · queuing · parallel batching act on throughput.

And the first result is in. exp004 — the PTU spillover-policy simulation (Phase 1) pitted a proactive spillover policy against a reactive one to see which protects the cache better under saturation load. The answer was close to a tie — the proactive policy's steady-state cache was actually 0.1657 pp lower, and it never engaged spillover once. The real verdict belongs to a physically split two-deployment load test (Phase 2).

And that verdict is in. exp005 — the dual-deployment spillover test (Phase 2) re-ran the same question across two live deployments with physically separate caches. This time the gap widened — the proactive policy's steady-state cache came in 0.9923 pp lower (about 6× the Phase 1 margin), and it cost more too, because splitting the traffic cools the one pool you had kept warm. Both phases reached the same conclusion — when the caches are physically separate, the reactive policy wins.

Sources & evidence boundary

This retrospective introduces no new measurement; it re-cites published figures normalized per 1,000. The raw materials and boundaries are as follows.

  • Cross-summary: results/summary.md (§3 headline, §5 decision boundary, §6 limits). All costs are re-cited from each benchmark’s benchmarks/0[123]-*/analysis.md.
  • Pricing: a single snapshot pricing/azure-openai-payg-2026-05.yaml (Azure, accessed 2026-05-19). If rates change, update the snapshot and re-run the analysis.
  • Sample: N=20 · R=3 per benchmark. Methodology §8 forbids reporting confidence intervals / standard errors at this sample size — directional conclusions are robust, but treat absolute sizes with small-sample caution.
  • Scoring: the judge-model rubric uses gpt-4o as a neutral judge. The judge-prompt SHA-256 is recorded in every scoring JSON to tell later if it changed.
  • PTU: throughput figures are token-count estimates, not a live PTU load test. The tool benchmark’s web_search is a fixed-KB lookup (mocked).
