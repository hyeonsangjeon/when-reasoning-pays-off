exp003 — क्या tool agent में reasoning effort ने लागत वसूल की?

लेखक Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

पिछले दो benchmarks में उत्तर हमेशा “effort मत बढ़ाओ” था। इस बार बात अलग निकली। यहाँ model tools बुलाता है। फिर उनके results देखकर अगला फैसला करता है। यह एक mixed task था। तीनों benchmarks में यही पहली जगह थी जहाँ reasoning ने पहली बार, और वह भी थोड़ा, फ़ायदा दिया।

हमने pre-registration में पहले से लिखा था कि middle effort (low–medium) सबसे अच्छा संतुलन बिंदु होगा। यानी वही जगह जहाँ cost और quality मिलती हैं। हमारी भविष्यवाणी के तीन हिस्से थे। पहला: gpt-4o no-tool·one-tool कर लेगा, पर multi-tool में टूटेगा, जहाँ कई tools जोड़ने पड़ते हैं। दूसरा: gpt-5.2 none के पास पहले से सोचने की जगह नहीं होगी, इसलिए multi-tool में वह gpt-4o जितना weak होगा। तीसरा: high·xhigh में quality पहले से छत पर होगी, इसलिए वे आसान samples पर भी tools ज़्यादा बुलाएँगे।

Measurement आधा सही और आधा चौंकाने वाला था। low सचमुच floor था — इस बार none नहीं। लेकिन gpt-4o सच में multi-tool पर नहीं टूटा। वह वहाँ टूटा जहाँ tool की ज़रूरत न होने पर calculator बुला लिया गया। यह note उस दिन को design → inputs → outputs → prediction versus measurement → tool-overuse map → decision के क्रम में दोबारा देखता है — ताकि अगला व्यक्ति उसी रास्ते में कम भटके।

पढ़ने का क्रम — पहले quality, फिर cost: इस बार tools आते हैं prediction आधा ही सही था floor none नहीं, low था gpt-4o ने tools बहुत बार बुलाए कहाँ तक भरोसा करें तो default क्या रखें

Design

इस बार tools आते हैं

प्रश्न एक है। Tool-using agent task में gpt-5.2 का effort कहाँ तक बढ़ाना पड़ेगा ताकि reasoning अपनी लागत वसूल करे? यह mixed case है और reality के सबसे करीब है। हम इसे दो नज़रियों से देखते हैं। PAYG में पूछा: प्रति सही answer कितने dollar लगे। PTU में पूछा: fixed capacity पर प्रति minute कितने सही answer मिले।

Dataset. Frozen authored samples 20 (tu_01…tu_20). इसमें तीन types मिले हुए हैं — 6 no-tool (सिर्फ knowledge/format), 8 one-tool (एक calculator या एक search), 6 multi-tool (search → calculator से 2–3 steps की chain)। हर sample के पास verify किया जा सकने वाला answer है। साथ में expected_tool_calls answer key भी है, जो बताता है कि कौन-से tools बुलाने चाहिए।

बदलने वाली चीज़ केवल एक है — gpt-5.2 के reasoning.effort को none · low · medium · high · xhigh में एक-एक step चलाया गया। साथ में gpt-4o baseline रखा गया, जिसमें reasoning parameter नहीं है। हर (sample × model × effort) cell को तीन बार (R=3) repeat किया गया। tool loop को maximum 4 iterations (max_tool_iterations: 4) पर काटा गया।

Pre-registered prediction

Middle effort (low–medium) mixed task में cost और quality का सबसे अच्छा संतुलन बिंदु है। gpt-4o no-tool·one-tool कर लेगा, पर multi-tool में टूटेगा। gpt-5.2 none multi-tool में gpt-4o जितना weak होगा। high·xhigh में quality पहले से पूरी होगी, इसलिए tools ज़्यादा बुलेंगे।

इस experiment की भूमिका

Short-factual के floor (01) और multi-step के ceiling (02) दोनों “effort मत बढ़ाओ” पर खत्म हुए। उसके बाद यह mixed reference case देखता है कि क्या ऐसा सबसे छोटा point है जहाँ थोड़ी reasoning सच में चाहिए।

Prediction versus measurement

prediction आधा ही सही था

क्या predict किया

Middle effort cost और quality का संतुलन बिंदु है। gpt-4o multi-tool में टूटेगा। gpt-5.2 none multi-tool में weak होगा। छोटा सार: “mixed task को थोड़ी reasoning चाहिए।”

क्या निकला

low सचमुच cost और quality का संतुलन बिंदु था — इस बार none नहीं। लेकिन gpt-4o जहाँ टूटा, वह केवल multi-tool नहीं बल्कि no-tool (83.3%) था। Tool की ज़रूरत नहीं थी, फिर भी calculator बुला लिया।

Decision: दिशा सही थी, पर failure का तरीका उल्टा निकला। “mixed task को कम से कम थोड़ी reasoning चाहिए” वाली pre-registration supported हुई — low (not none) हर सही answer पर सबसे कम लागत वाला point है। पर gpt-4o की weakness केवल कई tools जोड़ना नहीं थी। कमजोरी यह भी थी कि जब tool नहीं बुलाना चाहिए तब बुला लेना। Prediction का आधा हिस्सा सही था। आधे को data ने अधिक interesting story से ठीक किया।

पहला signal

floor none नहीं, low था

नीचे की table के dollars pricing snapshot pricing/azure-openai-payg-2026-05.yaml (accessed 2026-05-19) पर methodology का PAYG formula लगाकर निकले हैं। इन्हें analysis.md §5 से re-cite किया गया है और per 1,000 रखा गया है।

मॉडल      प्रयास   1,000अनुरोध   पास दर         1,000सही
gpt-4o    —        $3.29         90.0% (54/60)   $3.65   ← baseline
gpt-5.2   none     $2.76         98.3% (59/60)   $2.81
gpt-5.2   low      $2.77         100%  (60/60)   $2.77   ← Pareto-optimal
gpt-5.2   medium   $2.89         98.3% (59/60)   $2.94
gpt-5.2   high     $3.18         98.3% (59/60)   $3.23
gpt-5.2   xhigh    $3.50         100%  (60/60)   $3.50

प्रति 1,000 correct answers low $2.77 — gpt-4o ($3.65) से 24% सस्ता। और gpt-4o unit price के नीचे 100% pass तक पहुँचने वाला यह अकेला cell है। none पहले से per request gpt-4o से लगभग 16% सस्ता है (input price $1.75/1M versus $2.50/1M; tool loop में बार-बार input आने से bill mostly input से बनता है), पर multi-tool में एक problem छोड़कर 98.3% पर रहता है। low ने average में केवल 4 tokens की थोड़ी-सी reasoning जोड़ी। उसी छोटी चीज़ ने pass rate 100% कर दिया (per 1,000 requests +$0.011)।

पिछले दो benchmarks में none floor और सबसे अच्छा point दोनों था। यहाँ पहली बार floor एक step ऊपर गया। Real tool work में effort थोड़ा बढ़ाना पड़ता है — reasoning ने आखिरकार, थोड़ा ही सही, फ़ायदा दिया।

Tool-overuse map

gpt-4o ने tools बहुत बार बुलाए

90% जैसा एक कुल number “कहाँ” नहीं दिखाता। Type-wise तोड़ने पर इस benchmark का core evidence सामने आता है।

मॉडल      प्रयास   no-tool(18)   1-tool(24)   multi-tool(18)
gpt-4o    —        83.3%      100%      83.3%
gpt-5.2   none     100%       100%      94.4%
gpt-5.2   low      100%       100%      100%    ← Pareto-optimal
  • No-tool — जहाँ gpt-4o चूका। gpt-4o ने tool की ज़रूरत न होने पर भी calculator बुलाया और 83.3% पर रुका। Judge ने तीन cases को fail किया। वजह थी: “rubric tool calls 0 माँगता है, पर model ने tool बुलाया”। “1+1” जैसे prompts पर भी calculator ज़्यादा इस्तेमाल हुआ। gpt-5.2 सभी efforts पर 100%।
  • One-tool — पूरा हल. हर (model×effort) cell 100%। एक tool बुलाना दोनों families के लिए solved problem है।
  • Multi-tool — जहाँ reasoning मदद करती है। gpt-4o 83.3%, gpt-5.2 none 94.4%, low 100%। 2–3 steps की chain में थोड़ी-सी reasoning “plan and execute” को अधिक stable बनाती है। gpt-4o → gpt-5.2 low का 16.7%p lift वही real-work signal है जिसे यह benchmark पकड़ना चाहता था।

Tool-efficiency score भी उसी direction में है। यह answer scoring से अलग है। यह tool-use path को 0–1 पर देखता है। gpt-4o 0.950 पर सबसे कम है, क्योंकि no-tool में calculator ज़्यादा इस्तेमाल हुआ और answer सही होने पर भी score कटता है। gpt-5.2 low पर 0.988 peak है — ठीक वही cell जिसने pass rate 100% किया।

दूसरा signal

low से ऊपर वही quality ज़्यादा महँगी

low से ऊपर फिर पिछले benchmarks की कहानी दोहरती है। medium per 1,000 requests लगभग $0.13 extra खर्च करता है। फिर भी pass rate उल्टे 98.3% पर गिरता है। इसलिए वह low से cost और quality दोनों में पिछड़ता है। high low की तुलना में per request +14%, xhigh +26% है, पर pass rate वही है (xhigh 100% है, पर per correct low से 26% महँगा)।

Latency भी वही कहानी है। none gpt-4o से उल्टे 5% तेज है (2,902ms versus 3,044ms)। low +0.7% पर लगभग flat है। लेकिन high +20.0%, xhigh +23.9% तक बढ़ जाता है। Latency-sensitive workload में medium practical ceiling है।

Tokens तोड़ने पर इस benchmark की बनावट दिखती है। Per-request input लगभग 1,200–1,300 tokens है और bill का बड़ा हिस्सा बनाता है। वजह यह है कि system prompt और tool definitions loop की हर iteration में फिर load होते हैं। Hidden reasoning tokens 0 (none) से लगभग 52 (xhigh) तक बढ़ते हैं, पर input की तुलना में छोटे हैं। Multi-step benchmark (02) में xhigh cost को reasoning tokens चलाते थे। यहाँ बात उल्टी है — input bill को चलाता है। यह short-factual benchmark (01) जैसा है।

PTU से देखें तो भी बात low पर आकर मिलती है। low की throughput gpt-4o की 0.939 गुना है, लेकिन 100% pass rate इसे उलटकर per-minute correct +4.3% देता है (gpt-4o 90%)। Throughput loss (−6.1% req/min) से pass-rate gain (+10.0%p) बड़ा है। Effort और बढ़ाएँ तो throughput ही कटता है (medium −8.5%, xhigh −10.8%)। PAYG (हर सही answer पर सबसे कम cost) और PTU (per minute सबसे अधिक सही answers), दोनों नज़रिये same low की ओर इशारा करते हैं।

Transparency

numbers पर लगे धब्बे भी जस के तस

कोई measurement पूरी तरह साफ़ नहीं होता। यह benchmark जो निशान छोड़ता है, उन्हें हम मिटाते नहीं। क्योंकि छिपाने से अगला व्यक्ति उसी जगह चूकेगा।

  • Outlier 1. tu_18 का low first repeat tokens में 3σ से आगे गया। इसका मतलब सामान्य दायरे से बहुत बाहर का मान है। उस पर संचालन-समस्या का निशान भी लगा, इसलिए aggregate से excluded हुआ (360 cells में 1 = 0.3%, methodology alert line 10% से बहुत नीचे)। Raw JSON tree में वह जस का तस है — सिर्फ़ कुल जोड़ से छिपाया गया, deletion नहीं।
  • Loop cap 12 cases. 360 cells में से 12 (3.3%) tool loop 4-iteration cap पर पहुँचे और answer बिना tool के force-return हुआ। हर row में iteration_cap marker है। इससे trace किया जा सकता है कि कौन-से cells cap की वजह से रुके।
  • Partial scores correct से बाहर. Judge score 1 (partial correct) §7 में अलग report है। लेकिन जब हमने हर सही answer की cost गिनी, तब इसे निकाला गया — production scale पर tool task का partial answer correct answer नहीं होता। हम सिर्फ़ पास/फेल के रूप में गिनने की यह choice साफ लिखते हैं, ताकि सबसे ऊपर का number कैसे निकला यह दिखे।

Limits

कहाँ तक भरोसा करें

यह result एक mixed tool task set, एक pricing snapshot, और specific model combination व rubric से निकला small aggregate है। Numbers से अधिक method को साथ ले जाना सुरक्षित है।

  • Search मॉक है. इस benchmark का web_search real web search नहीं है। यह mock है: एक fixed knowledge-base lookup। Live search uncontrolled बदलाव लाता, इसलिए उसे scope से बाहर रखा। मुख्य बात यह है कि थोड़ी-सी reasoning multi-tool reliability बढ़ाती है, और low से ऊपर tokens waste हैं। यह बात इस simplification के बाद भी बनी रहती है। यह perfect reproduction नहीं है। यह सिर्फ़ उन चीज़ों को control करने वाली जगह है जिन्हें control किया जा सकता था — boundary नहीं छिपाते।
  • Sample. N=20 · R=3. इस sample size पर confidence intervals या statistical significance claim नहीं करते — direction साफ है, पर absolute size को small-sample caution के साथ पढ़ें।
  • Pricing. Single snapshot. Rates या billing का तरीका बदलें तो same raw material से cost फिर calculate करनी होगी।
  • Scoring. Judge model (gpt-4o). Judge prompt SHA-256 scoring JSON में recorded है, ताकि बाद में पता चले कि वह बदला या नहीं।
  • PTU. Throughput token-based estimate है। यह live PTU load test नहीं।

तो default क्या रखें

Tool-using agent का default gpt-5.2 effort=low है — PAYG और PTU दोनों में। Per correct 24% सस्ता (gpt-4o के मुकाबले), per-minute correct +4.3%, और multi-tool pass rate को 83.3% से 100% तक उठाने वाला quality bonus भी। इस बार none नहीं, low floor है। लेकिन low से ऊपर फिर quality नहीं बढ़ती। सिर्फ cost·latency जुड़ते हैं।
