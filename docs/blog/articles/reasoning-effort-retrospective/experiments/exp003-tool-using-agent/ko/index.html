exp003 — 툴 에이전트에서 추론 강도는 값을 했는가

글 Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

앞선 두 벤치마크에서 답은 늘 “강도를 올리지 말라”였다. 이번엔 달랐다. 도구를 부르고, 그 결과를 받아 다시 판단하는 혼합 작업 — 세 벤치마크를 통틀어 추론이 처음으로, 그것도 아주 조금 값을 한 자리다.

우리는 사전 등록에서 중간 강도(low–medium)가 파레토 무릎일 거라 적었다. gpt-4o는 무툴·1툴은 되지만 멀티툴 시퀀싱에서 무너지고, gpt-5.2 none은 계획할 추론 표면이 없어 멀티툴에서 gpt-4o만큼 약하며, high·xhigh는 품질은 포화된 채 사소한 샘플에 도구를 과하게 부를 거라고.

측정은 절반은 맞고 절반은 놀라웠다. low가 정말 바닥이었다 — 이번만은 none이 아니라. 그런데 gpt-4o가 무너진 진짜 자리는 멀티툴이 아니라, 도구가 필요 없는 문제에 계산기를 부른 곳이었다. 이 노트는 그 하루를 설계 → 입력 → 산출물 → 예측 대 실측 → 도구 남용 지도 → 결정으로 되짚는다 — 다음 사람이 같은 길에서 덜 헤매도록.

먼저, 10초

결론을 믿지 말고 이 실험만 직접 돌려보세요

토큰 소비는 0입니다. 아래 두 줄이 이 실험의 입력·변수·산출물을 그대로 출력하고, 툴 루프 러너 배선을 dry-run으로 검증합니다.

# 이 실험의 입력 → 변수 → 산출물 카드를 출력 (네트워크 없음)
python -c "import experiments; print(experiments.describe('exp003_benchmark03_gpt5_2.yaml').summary())"

# 툴 루프 러너를 dry-run으로 배선만 검증 (토큰 소비 0)
python -c "import experiments; print(experiments.run('exp003_benchmark03_gpt5_2.yaml', dry_run=True, extra_args=['--max-samples','1']).ok)"

GitHub에서 레포 열기 & ⭐

실제 유료 측정과 집계·도표 재생성 커맨드는 benchmarks/03-tool-using-agent/analysis.md의 재현 푸터에 정리되어 있습니다.

읽는 순서 — 품질을 먼저, 비용은 그다음: 이번엔 도구가 등장한다 예측은 절반만 맞았다 바닥이 none이 아니라 low였다 gpt-4o는 도구를 너무 자주 불렀다 어디까지 믿을 수 있나 그래서 무엇을 기본값으로

설계

이번엔 도구가 등장한다

질문은 하나다. 도구를 쓰는 에이전트 작업 — 현실에 가장 가까운 혼합 케이스 — 에서, gpt-5.2의 강도를 어디까지 올려야 추론이 청구서 값을 하는가? PAYG(정답당 달러)와 PTU(고정 용량당 분당 정답) 두 렌즈로 동시에 본다.

데이터셋. 얼려 둔 저작 샘플 20개(tu_01…tu_20). 세 유형이 섞여 있다 — 무툴 6개(지식/형식만), 1툴 8개(계산기 하나 또는 검색 하나), 멀티툴 6개(검색 → 계산기로 2–3번 이어지는 사슬). 모든 샘플은 검증 가능한 정답과, 어떤 도구를 불러야 하는지에 대한 expected_tool_calls 정답표를 함께 갖는다.

변하는 축은 딱 하나 — gpt-5.2의 reasoning.effort를 none · low · medium · high · xhigh로 스윕한다. 여기에 추론 파라미터가 없는 gpt-4o 기준선을 나란히 둔다. 각 (샘플 × 모델 × 강도) 셀은 세 번씩(R=3) 반복하고, 툴 루프는 최대 4회 반복(max_tool_iterations: 4)으로 잘린다.

사전 등록 예측

중간 강도(low–medium)가 혼합 작업의 파레토 무릎이다. gpt-4o는 무툴·1툴은 되지만 멀티툴에서 깨지고, gpt-5.2 none은 멀티툴에서 gpt-4o만큼 약하며, high·xhigh는 품질이 포화된 채 도구만 과하게 부른다.

이 실험의 역할

단답의 바닥(01)과 다단계의 천장(02)이 모두 “강도를 올리지 말라”로 끝난 뒤, 추론 표면이 실제로 필요한 최소 지점이 있는지를 확인하는 혼합 앵커.

입력과 산출물

무엇을 먹고 무엇을 남겼나

이 실험이 먹은 것도 남긴 것도 손으로 쓴 요약이 아니라 레포의 실제 파일입니다. 그래서 인풋에서 아웃풋까지 한 줄로 되짚을 수 있습니다.

입력 (in)

실험 정의: experiments/exp003_benchmark03_gpt5_2.yaml, …_gpt4o.yaml.
데이터셋: benchmarks/03-tool-using-agent/dataset.json (SHA-256으로 고정).
프롬프트·도구: 시스템 프롬프트와 도구 설정을 각각 SHA-256으로 지문화 — 360셀 전체에 단일한 시스템 프롬프트와 도구 설정이 쓰였음을 보증.

산출물 (out)

원시 호출: runs/*.json (Foundry v1 페이로드 + 반복별 tool_calls 궤적 원문).
채점: judge_runs/*.json (정답 채점 + 별도 도구효율 점수).
집계: analysis.json.
도표/표: results/cost-curves/benchmark-03-*.png·.csv.

측정 표면은 360셀(gpt-4o 60 + gpt-5.2 300, 강도 다섯 단계). 이상치로 제외된 셀은 1개(tu_18/low/r0). 채점은 중립 심판 gpt-4o가 셀당 한 번, 360/360 성공. 모든 JSON은 실제 Azure Foundry v1 호출로 "fixture": true 마커가 하나도 없다. 다만 360셀 중 12개(3.3%)가 툴 루프 4회 한도에 걸려 도구 없이 최종 답을 강제 반환했고, 각 행에 tool_loop_terminated="iteration_cap" 플래그가 남아 있다.

예측 대 실측

예측은 절반만 맞았다

무엇을 예측했나

중간 강도가 무릎이다. gpt-4o는 멀티툴에서 깨진다. gpt-5.2 none은 멀티툴에서 약하다. 요약하면 “혼합 작업엔 약간의 추론이 필요하다.”

무엇이 나왔나

low가 정말 파레토 무릎이었다 — 이번만은 none이 아니라. 그런데 gpt-4o가 무너진 곳은 멀티툴만이 아니라 무툴(83.3%)이었다. 도구가 필요 없는데 계산기를 불렀다.

판정: 방향은 확증, 실패 모드는 반전. “혼합 작업엔 최소한의 추론 표면이 있어야 한다”는 사전 등록은 지지되었다 — low(none이 아니라)가 정답당 파레토 최적이다. 다만 gpt-4o의 약점은 멀티툴 시퀀싱만이 아니라, 도구를 부르지 말아야 할 때 부르는 습관이었다. 예측의 절반은 맞았고, 절반은 데이터가 더 흥미로운 이야기로 바로잡았다.

첫 번째 신호

바닥이 none이 아니라 low였다

아래 표의 달러는 가격 스냅샷 pricing/azure-openai-payg-2026-05.yaml(접근일 2026-05-19)에 방법론의 PAYG 공식을 적용한 값으로, analysis.md §5에서 재인용하며 1,000건당으로 정규화했다.

모델      강도     1,000요청당    통과율          1,000정답당
gpt-4o    —        $3.29         90.0% (54/60)   $3.65   ← 기준선
gpt-5.2   none     $2.76         98.3% (59/60)   $2.81
gpt-5.2   low      $2.77         100%  (60/60)   $2.77   ← 파레토 최적
gpt-5.2   medium   $2.89         98.3% (59/60)   $2.94
gpt-5.2   high     $3.18         98.3% (59/60)   $3.23
gpt-5.2   xhigh    $3.50         100%  (60/60)   $3.50

정답 1,000건당 low는 $2.77 — gpt-4o($3.65)보다 24% 싸다. 그리고 gpt-4o 단가 아래에서 유일하게 100% 통과에 닿은 셀이다. none도 이미 요청당으로는 gpt-4o보다 약 16% 싸지만(입력 단가 $1.75/1M 대 $2.50/1M, 툴 루프에선 입력이 청구서를 지배), 멀티툴에서 한 문제를 놓쳐 98.3%에 머문다. low가 더한 것은 평균 4토큰의 추론 표면뿐인데, 그 작은 표면이 통과율을 100%로 끌어올렸다(1,000요청당 +$0.011).

앞선 두 벤치마크에선 none이 바닥이자 최적이었다. 여기서 처음으로 바닥이 한 칸 올라갔다. 혼합 실작업에는 양의 최소 강도 바닥이 있다 — 추론이 마침내, 아주 조금 값을 했다.

도구 남용 지도

gpt-4o는 도구를 너무 자주 불렀다

90%라는 집계 숫자 하나로는 “어디서”가 보이지 않는다. 유형별로 쪼개면 이 벤치마크의 핵심 근거가 드러난다.

모델      강도     무툴(18)   1툴(24)   멀티툴(18)
gpt-4o    —        83.3%      100%      83.3%
gpt-5.2   none     100%       100%      94.4%
gpt-5.2   low      100%       100%      100%    ← 파레토 최적
  • 무툴 — gpt-4o가 발을 헛디딘 곳. gpt-4o는 도구가 필요 없는데도 계산기를 불러 83.3%에 그쳤다. 심판은 세 건을 “루브릭이 도구 호출 0을 요구하는데 모델이 도구를 불렀다”로 실패 처리했다 — “1+1” 같은 프롬프트에도 계산기를 남용한 것이다. gpt-5.2는 전 강도에서 100%.
  • 1툴 — 완전 포화. 모든 (모델×강도) 셀이 100%. 단일 도구 디스패치는 두 계열 모두에게 풀린 문제다.
  • 멀티툴 — 추론이 돕는 자리. gpt-4o 83.3%, gpt-5.2 none 94.4%, low 100%. 2–3번 이어지는 사슬에서 작은 추론 표면이 “계획하고 실행”을 더 안정적으로 만든다. gpt-4o → gpt-5.2 low의 16.7%p 상승이 이 벤치마크가 잡아내려던 실작업 신호다.

도구 효율 점수(정답 채점과 별개로, 궤적을 0–1로 평가)도 같은 방향이다. gpt-4o는 0.950으로 가장 낮은데, 무툴에서 계산기를 남용해 정답을 맞히고도 점수가 깎였다. gpt-5.2는 low에서 0.988로 정점 — 통과율 100%를 찍은 바로 그 셀이다.

두 번째 신호

low를 넘기면 같은 품질을 더 비싸게

low 위로는 다시 앞선 벤치마크의 이야기가 반복된다. medium은 1,000요청당 약 $0.13을 더 쓰고도 통과율이 98.3%로 오히려 내려가 low에 파레토 열세다. high는 low 대비 요청당 +14%, xhigh는 +26%인데 통과율은 그대로다(xhigh는 100%지만 정답당으로 low보다 26% 비싸다).

지연도 같은 이야기다. none은 gpt-4o보다 오히려 5% 빠르고(2,902ms 대 3,044ms), low는 +0.7%로 사실상 평평하다. 그런데 high는 +20.0%, xhigh는 +23.9%로 벌어진다. 지연에 민감한 워크로드라면 medium이 현실적 천장이다.

토큰을 분해하면 이 벤치마크만의 구조가 보인다. 요청당 입력이 약 1,200–1,300토큰으로 청구서를 지배한다 — 시스템 프롬프트와 도구 정의가 루프의 매 반복마다 다시 실린 탓이다. 숨은 추론 토큰은 0(none)에서 약 52(xhigh)로 늘지만, 입력에 견주면 작다. 추론 토큰이 xhigh 비용을 지배하던 단발 벤치마크(01·02)와는 구조가 반대다.

PTU 렌즈에서도 결론은 low로 모인다. low는 gpt-4o의 0.939배 처리량이지만 통과율 100%가 이를 뒤집어 분당 정답 +4.3%다(gpt-4o는 90%). 처리량 손실(−6.1% req/min)보다 통과율 상승(+10.0%p)이 크다. 반면 강도를 더 올리면 처리량만 깎인다(medium −8.5%, xhigh −10.8%). PAYG(정답당 최저)와 PTU(분당 정답 최고)가 같은 low를 가리키는 두 렌즈의 수렴이다.

투명성

숫자에 남긴 얼룩까지 그대로

  • 이상치 1건. tu_18의 low 첫 반복이 토큰에서 3σ를 넘고 운영 플래그를 함께 달아 집계에서 제외됐다(360셀 중 1건 = 0.3%, 방법론 경보선 10%보다 한참 아래). 원시 JSON 트리에는 그대로 남아 있다 — 이상치 제외는 집계 마스크일 뿐 삭제가 아니다.
  • 루프 한도 12건. 360셀 중 12개(3.3%)가 툴 루프 4회 한도에 걸려 도구 없이 답을 강제 반환했다. 각 행에 iteration_cap 플래그가 남아, 어떤 셀이 한도에 눌렸는지 추적할 수 있다.
  • 부분 점수는 정답에서 제외. 심판 점수 1(부분 정답)은 §7에 따로 보고하되 정답당 비용의 분모에서는 뺐다 — 프로덕션 규모에서 툴 작업의 부분 정답은 정답이 아니기 때문이다. 이 이진화 선택을 명시해 두어 헤드라인이 어떻게 계산됐는지 드러낸다.

한계

어디까지 믿을 수 있나

이 결과는 하나의 혼합 툴 작업 세트, 하나의 가격 스냅샷, 특정 모델 조합과 루브릭에서 나온 소규모 집계값입니다. 숫자 자체보다 방법을 가져가는 편이 안전합니다.

  • 검색은 모킹이다. 이 벤치마크의 web_search는 실제 웹 검색이 아니라 고정 지식베이스 조회다. 라이브 검색은 통제 불가능한 분산을 들여와 범위 밖으로 두었다. 헤드라인(작은 추론 표면이 멀티툴 신뢰성을 올린다, low 초과는 토큰 낭비)은 이 단순화에 견고하다.
  • 표본. N=20 · R=3. 이 표본 크기에서는 신뢰구간이나 통계적 유의성을 주장하지 않는다 — 방향성 결론은 견고하나 절대 크기는 소표본 주의.
  • 가격. 단일 스냅샷. 요율이나 사용량 스키마가 바뀌면 같은 원자료에서 비용을 다시 계산해야 한다.
  • 채점. LLM-as-judge(gpt-4o). 심판 프롬프트 SHA-256을 채점 JSON에 기록해 드리프트를 감시한다.
  • PTU. 처리량은 토큰 기반 추정이며 라이브 PTU 부하 테스트가 아니다.

그래서 무엇을 기본값으로

툴 사용 에이전트의 기본값은 gpt-5.2 강도=low다 — PAYG와 PTU 양쪽에서. 정답당 24% 저렴(gpt-4o 대비), 분당 정답 +4.3%, 그리고 멀티툴 통과율을 83.3%에서 100%로 끌어올리는 품질 보너스까지. 이번만은 none이 아니라 low가 바닥이다. 그러나 low 위로는 다시 품질 없이 비용·지연만 더할 뿐이다.
