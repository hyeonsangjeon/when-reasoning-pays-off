exp003 — ツールエージェントで推論努力度は割に合ったのか

文 Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

前の二つのベンチマークでは、答えはいつも “努力度を上げるな” だった。今回は違った。ツールを呼ぶ。結果を受けて、もう一度判断する。そんな混合タスクである。三つのベンチマークの中で、推論が初めて、それもごく少し役に立った場所だった。

私たちは事前登録で、こう書いた。中間の努力度(low–medium)が、費用と品質がいちばんよく出会う地点になるはずだ。予測は三つだった。gpt-4o は no-tool と one-tool(1ツール) はできるが、multi-tool、つまり道具をいくつか続けて使う問題では崩れるだろう。gpt-5.2 none は前もって考える余地がなく、multi-tool では gpt-4o くらい弱いだろう。high·xhigh は品質がもう上限に近く、小さな問題にもツールを呼びすぎるだろう、と。

測定は半分は当たり、半分は驚きだった。low が本当に床だった。今回だけは none ではなかった。ところが gpt-4o が本当に崩れた場所は multi-tool ではなかった。ツールが要らない問題で計算機を呼んだところだった。このノートはその一日を設計 → 入力 → 成果物 → 予測対実測 → ツールを呼びすぎた地図 → 判断として振り返る。次の人が同じ道で迷いにくいように。

なぜ読むのか

ツールが入ると、何か変わるのか

前の二つの実験で、答えはいつも “努力度を上げるな” だった。短いタスク(01)でも、多段階タスク(02)でも同じだった。けれど現実のエージェントはたいていツールを呼ぶ — 検索し、計算機を回し、結果を受け取ってまた判断する。ツールが入れば、今度こそ推論努力度は割に合うのではないか。

それを確かめるため、現実にいちばん近い混合タスクを選んだ。ツールが要らない問題、ツール一つで足りる問題、いくつものツールを順につなぐ問題が混ざっている。三つのベンチマークを通して、推論が初めて割に合うのか、もしそうならどの強さからなのかをここで切り分ける。

あなたがツールを使うエージェントを作っているなら — 検索、計算、API 呼び出しを組み合わせて答えを作る種類なら — このノートがいちばん近い。ツールをちょうどよく使い、ムダも出さないためにつまみをどこに置くべきか、そして床がなぜ none ではなかったのかを実測で示す。

設計

今回はツールが登場する

問いは一つだ。 ツールを使うエージェントタスクで、gpt-5.2 の努力度をどこまで上げれば推論が請求に見合うのか。これは現実に近い混合ケースである。PAYG(正答当たりのドル)と PTU(固定容量当たりの分当たり正答)の二つの見方で同時に見る。

データセット。 凍結した著作サンプル 20個(tu_01…tu_20)。三つの型が混ざっている。no-tool 6個(知識/形式のみ)、one-tool(1ツール) 8個(計算機一つ、または検索一つ)、multi-tool 6個(検索 → 計算機へ 2–3回つながる鎖)である。すべてのサンプルには、検証できる正答がある。どのツールを呼ぶべきかを示す expected_tool_calls の正答表もある。

変えるものは一つだけ — gpt-5.2 の reasoning.effort を none · low · medium · high · xhigh の五段階で動かす。横には、推論努力度の設定がない gpt-4o を基準線として置く。各 (サンプル × モデル × 努力度) セルは三回ずつ(R=3)繰り返す。ツールループは最大 4回反復(max_tool_iterations: 4)で止める。

事前登録予測

中間の努力度(low–medium)が、混合タスクで費用と品質がいちばんよく出会う地点である。gpt-4o は no-tool·one-tool(1ツール) はできるが multi-tool で壊れる。gpt-5.2 none は multi-tool で gpt-4o と同じくらい弱い。high·xhigh は品質がもう上限に近く、ツールだけを呼びすぎる。

この実験の役割

短い事実回答の床(01)と多段階の天井(02)は、どちらも “努力度を上げるな” で終わった。そのあとで、わずかな推論が本当に必要になる最小地点があるかを確かめる。これが混合ケースの基準になる。

予測対実測

予測は半分だけ当たった

何を予測したか

中間の努力度が、費用と品質が出会う地点である。gpt-4o はmulti-tool で壊れる。gpt-5.2 none は multi-tool で弱い。要するに “混合タスクには少しの推論が必要だ。”

何が出たか

low が本当に費用と品質が出会う地点だった。今回だけは none ではない。ところが gpt-4o が崩れた場所は multi-tool だけでなくno-tool(83.3%)だった。ツールが要らないのに計算機を呼んだ。

判定: 方向は合っていたが、失敗のしかたは逆だった。 “混合タスクには最低限の推論が必要だ”という事前登録は合っていた。low(none ではなく)が、正答あたりの費用が最も安かった。ただし gpt-4o の弱点は、multi-tool を順番につなぐことだけではなかった。ツールを呼んではいけないときに呼ぶ習慣も弱点だった。予測の半分は当たり、半分はデータがよりおもしろい話に直した。

第一の合図

床は none ではなく low だった

下の表のドルは、価格スナップショット pricing/azure-openai-payg-2026-05.yaml(アクセス日 2026-05-19)に方法論の PAYG 式を当てた値だ。analysis.md §5 から再引用し、1,000件当たりにそろえた。

モデル      努力度   1,000リクエスト当たり 通過率          正答1,000件当たり
gpt-4o    —        $3.29         90.0% (54/60)   $3.65   ← ベースライン
gpt-5.2   none     $2.76         98.3% (59/60)   $2.81
gpt-5.2   low      $2.77         100%  (60/60)   $2.77   ← パレート最適
gpt-5.2   medium   $2.89         98.3% (59/60)   $2.94
gpt-5.2   high     $3.18         98.3% (59/60)   $3.23
gpt-5.2   xhigh    $3.50         100%  (60/60)   $3.50

正答 1,000件当たり low は $2.77 — gpt-4o($3.65) より 24% 安い。 そして gpt-4o の単価を下回る中で、唯一 100% 通過に届いたセルである。none も、リクエスト当たりではすでに gpt-4o より約 16% 安い(入力単価 $1.75/1M 対 $2.50/1M、ツールループでは入力が請求を左右する)。それでも multi-tool で一問を落とし、98.3% にとどまる。low が足したのは平均4トークンのわずかな推論だけだった。その小さな差が、通過率を 100% へ引き上げた(1,000リクエスト当たり +$0.011)。

前の二つのベンチマークでは none が床であり、最適でもあった。ここで初めて床が一段上がった。ツールを使う実作業には、少しだけ努力度を上げる必要がある床がある。推論がついに、ごく少し役に立った。

ツールを呼びすぎた地図

gpt-4o はツールを呼びすぎた

90% という合計の数字だけでは、“どこで”が見えない。型別に分けると、このベンチマークの中心となる根拠が見えてくる。

モデル      努力度   無ツール(18) 1ツール(24) マルチツール(18)
gpt-4o    —        83.3%      100%      83.3%
gpt-5.2   none     100%       100%      94.4%
gpt-5.2   low      100%       100%      100%    ← パレート最適
  • no-tool — gpt-4o が足を踏み外した場所。 gpt-4o はツールが要らないのに計算機を呼び、83.3% にとどまった。審判は三件を “採点基準はツール呼び出し 0 を求めているのに、モデルがツールを呼んだ” として失敗にした。“1+1” のような問いでも計算機を使いすぎたのである。gpt-5.2 は全努力度で 100%。
  • one-tool(1ツール) — 完全に解けた。 すべての (モデル×努力度) セルが 100%。ツールを一つだけ呼ぶ仕事は、どちらの系列にも解けた問題である。
  • multi-tool — 推論が助ける場所。 gpt-4o 83.3%、gpt-5.2 none 94.4%、low 100%。2–3回つながる鎖では、わずかな推論が “計画して実行する” ことを安定させる。gpt-4o → gpt-5.2 low の 16.7%p 上昇が、このベンチマークで見たかった実作業の合図である。

ツール効率スコアも同じ方向だ。これは正答採点とは別に、ツール使用の過程を 0–1 で見る点数である。gpt-4o は 0.950 で最も低い。no-tool で計算機を使いすぎ、答えが合っていても点を削られた。gpt-5.2 は low で 0.988 といちばん高い。通過率 100% を出した、まさにそのセルである。

第二の合図

low を超えると同じ品質をより高く

low の上では、また前のベンチマークと同じ話になる。medium は 1,000リクエスト当たり約 $0.13 を余分に使う。それでも通過率は 98.3% へむしろ下がり、費用でも品質でも low に負ける。high は low 比でリクエスト当たり +14%、xhigh は +26% だが、通過率はほぼ変わらない(xhigh は 100% だが、正答当たりでは low より 26% 高い)。

待ち時間も同じ話だ。 none は gpt-4o よりむしろ 5% 速い(2,902ms 対 3,044ms)。low は +0.7% で、ほとんど変わらない。ところが high は +20.0%、xhigh は +23.9% へ開く。待ち時間に敏感な仕事なら medium が現実的な上限である。

トークンを分けて見ると、このベンチマークの形が見える。 リクエスト当たりの入力は約 1,200–1,300トークンで、請求を左右する。システムプロンプトとツール定義が、ループの各反復でまた入るためだ。隠れた推論トークンは 0(none)から約 52(xhigh)へ増える。だが入力に比べれば小さい。推論トークンが xhigh コストを左右した多段階ベンチマーク(02)とは逆である。入力が請求を左右する点は、むしろ短い事実回答ベンチマーク(01)に似ている。

PTU で見ても結論は low に集まる。 low は gpt-4o の 0.939倍の処理量だ。けれど通過率 100% がこれをひっくり返し、分当たり正答 +4.3% になる(gpt-4o は 90%)。処理量の損失(−6.1% req/min)より、通過率の上昇(+10.0%p)が大きい。努力度をさらに上げると、処理量だけが削られる(medium −8.5%、xhigh −10.8%)。PAYG(正答当たり最安)と PTU(分当たり正答最高)という二つの見方が、同じ low へ集まる。

透明性

数字に残った汚れまでそのまま

どんな測定も完全にきれいではない。このベンチマークが残した跡を、消さずにそのまま書いておく。隠すと、次の人が同じ場所でつまずくからだ。

  • 外れ値 1件。 tu_18 の low 1回目の反復は、トークンで 3σ を超えた。これは、正常範囲を大きく外れた値という意味である。さらに運用上の問題を示す印も付いていたため、集計から除外された(360セル中 1件 = 0.3%、方法論の警告線 10% を大きく下回る)。生 JSON ツリーにはそのまま残っている。集計から隠すだけで、削除ではない。
  • ループ上限 12件。 360セル中 12個(3.3%)がツールループ 4回の上限にかかった。そのため、ツールなしで回答を返すしかなかった。各行に iteration_cap マーカーが残る。どのセルが上限に当たったかを追える。
  • 部分点は正答から除外。 審判スコア 1(部分正答)は §7 に別に報告する。だが正答あたり費用を数えるときは、正答から外した。本番規模では、ツールタスクの部分正答は正答ではないからだ。通過・失敗だけで数える選択を明示し、一番上の数字がどう計算されたかを示す。

限界

どこまで信じられるか

この結果は、一つの混合ツールタスクセット、一つの価格スナップショット、特定のモデルと採点基準から出た小さな集計値です。数字そのものより、方法を持ち帰るほうが安全です。

  • 検索はモックである。 このベンチマークの web_search は実際のウェブ検索ではない。モック(固定の知識ベース参照)である。ライブ検索は、こちらで制御できない揺れを持ち込むため、範囲外に置いた。代表値(わずかな推論が multi-tool の信頼性を上げる、low 超過はトークンの無駄)は、この単純化でも大きくは揺れない。完全な再現ではない。制御できるものだけを制御した場所である。その境界を隠さない。
  • 標本。 N=20 · R=3。この大きさでは、信頼区間や統計的有意性は主張しない。どちらに向くかという結論は堅いが、絶対値の大きさは小標本として見る。
  • 価格。 価格表は一つだけを基準にした。料金や課金方式が変われば、同じ原資料からコストを再計算する必要がある。
  • 採点。 審判モデル(gpt-4o)が行った。審判に渡したプロンプトの SHA-256 を採点 JSON に記録した。あとで変わったか分かるようにするためだ。
  • PTU。 処理量はトークンで計算した推定であり、ライブ PTU 負荷テストではない。

だから何をデフォルトにするか

ツール使用エージェントのデフォルトは gpt-5.2 effort=low である。PAYG と PTU の両方でそうだ。正答当たり 24% 安い(gpt-4o 比)。分当たり正答は +4.3%。さらに multi-tool 通過率を 83.3% から 100% へ引き上げる品質の上乗せもある。今回だけは none ではなく low が床である。しかし low の上では、また品質は増えず、コストと待ち時間だけが増える。
