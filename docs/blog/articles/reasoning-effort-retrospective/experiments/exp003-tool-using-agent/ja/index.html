exp003 — ツールエージェントで推論強度は割に合ったのか

執筆: Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

前の二つのベンチマークでは、強度を上げても効果はありませんでした。今回は、ツールを呼び出し、結果を受けて再び判断する混合タスクです。三つのベンチマークで初めて、少量の推論が効果を示しました。

私たちは、中間の強度(low–medium)でコストと品質のバランスが最良になると事前登録した予測に記しました。gpt-4o は no-tool と one-tool には対応できても multi-tool で失敗し、gpt-5.2 none も multi-tool では gpt-4o と同程度、high·xhigh は品質が頭打ちとなり、不要なツール呼び出しが増えると予測しました。

実測では、low が下限になるという予測は当たり、none より優位でした。一方、gpt-4o の主な失敗は multi-tool ではなく、ツール不要の問題で計算機を呼び出したことでした。本ノートでは、設計 → 入力 → 成果物 → 予測と実測 → ツールの過剰使用 → 判断の順に結果を振り返ります。

この記事で分かること

ツールが加わると結果は変わるか

短い事実回答(01)と多段階推論(02)では、推論強度を上げても品質は改善しませんでした。しかし、実際のエージェントは検索や計算機などのツールを呼び出し、結果を受けて再び判断します。この処理では、少量の推論が効果を持つ可能性があります。

そこで、ツール不要、1ツール、複数ツールを順につなぐタスクを含む混合タスクを選びました。推論が初めて費用に見合うか、見合うならどの強度からかを実測で切り分けます。

検索、計算、API 呼び出しを組み合わせるエージェントに近いケースです。ツールを適切に使い、不要なコストを避けるための強度と、下限が none ではなかった理由を示します。

設計

ツールを含む混合タスク

ツールを加えた理由。 前の二つは、最も易しいタスク(01)と純粋な多段階タスク(02)でした。実際のサービスでは、検索結果を計算機に渡して再び判断するように、ツールを選び、順につなぐ処理があります。モデルがツールと順序を選ぶ際に、推論強度が品質を高め、そのコストに見合うかを検証しました。

「中間で十分」を仮説にしました。 ツールを組み合わせるタスクでは、中間の強度でコストと品質のバランスが最良となり、それ以上では品質が頭打ちとなってツール呼び出しだけが増えるという仮説です。強度を上げるほど正答率が伸び、最も高い強度が最良なら、この仮説は崩れます。 一方、none で multi-tool に失敗し、中間の強度で安定すれば仮説は残ります。

混合ケースとしての役割。 下限(01)と上限(02)はいずれも「強度を上げない」という結論でした。本ノートでは、現実に近い混合タスクで、推論が実際に必要になる最小の強度を探します。

問いは一つです。 ツールを使うエージェントで、gpt-5.2 の推論強度をどこまで上げればコストに見合うのでしょうか。PAYG(正答当たりのドル)と PTU(固定容量当たりの分当たり正答)の両方で評価します。

データセット。 凍結した著作サンプル 20個(tu_01…tu_20)を使用しました。no-tool 6個(知識/形式のみ)、one-tool 8個(計算機または検索を 1つ)、multi-tool 6個(検索 → 計算機を 2–3回つなぐ処理)です。すべてのサンプルに検証可能な正答と expected_tool_calls があります。

変更する変数は一つです。 gpt-5.2 の reasoning.effort を none · low · medium · high · xhigh の五段階で比較し、推論強度の設定がない gpt-4o を基準としました。各 (サンプル × モデル × 強度) セルを三回ずつ(R=3)実行し、ツールループは最大 4回(上限値 4)(max_tool_iterations: 4)で停止します。

事前登録した予測

中間の強度(low–medium)でコストと品質のバランスが最良になります。gpt-4o は no-tool·one-tool には対応できても multi-tool で失敗し、gpt-5.2 none も multi-tool で弱く、high·xhigh では品質が頭打ちとなり、ツールを過剰に呼び出すと予測しました。

この実験の役割

短い事実回答の下限(01)と上限(02)の後に、少量の推論が実際に必要になる最小の強度があるかを確かめる混合ケースです。

入力と出力

測定したのは 360セル(gpt-4o 60 + gpt-5.2 300、強度五段階)です。外れ値として1個(tu_18/low/r0)を除外しました。評価モデル gpt-4o による採点はセルごとに 1回で、360/360 成功しました。すべて実際の Azure Foundry v1 呼び出しで、"fixture": true マーカーはありません。ただし、360セル中 12個(3.3%)がツールループの上限 4回(設定値 4)に達し、ツールなしで最終回答を返しました。各行に tool_loop_terminated="iteration_cap" マーカーを記録しています。

予測と実測

予測は一部だけ一致

事前登録した予測

中間の強度でコストと品質のバランスが最良になります。gpt-4o は multi-tool で失敗し、gpt-5.2 none も multi-tool で弱いと予測しました。

実測結果

low でコストと品質のバランスが最良となり、今回は none が下限ではありませんでした。一方、gpt-4o は multi-tool だけでなく、no-tool(83.3%) でも失敗しました。ツールが不要なのに計算機を呼び出したためです。

判定: 方向は一致し、失敗箇所は予測と異なりました。 「混合タスクには最低限の推論が必要」という予測どおり、low が正答当たりで最安でした。ただし、none との比較に加え、gpt-4o はツールをつなぐ処理だけでなく、呼び出す必要がない場面でツールを呼ぶことにも失敗しました。

第一のシグナル

下限は none ではなく low

表のドル額は、価格スナップショット pricing/azure-openai-payg-2026-05.yaml(アクセス日 2026-05-19)に方法論の PAYG 式を適用した値です。analysis.md §5 から再引用し、1,000件当たりに正規化しています。

モデル      推論強度  1,000リクエスト当たり 通過率          正答1,000件当たり
gpt-4o    —        $3.29         90.0% (54/60)   $3.65   ← ベースライン
gpt-5.2   none     $2.76         98.3% (59/60)   $2.81
gpt-5.2   low      $2.77         100%  (60/60)   $2.77   ← パレート最適
gpt-5.2   medium   $2.89         98.3% (59/60)   $2.94
gpt-5.2   high     $3.18         98.3% (59/60)   $3.23
gpt-5.2   xhigh    $3.50         100%  (60/60)   $3.50

正答 1,000件当たりで low は $2.77、gpt-4o($3.65)より 24% 安い結果でした。gpt-4o より低コストの設定で唯一、通過率 100% を達成しました。none もリクエスト当たりでは約 16% 安い一方(入力単価 $1.75/1M 対 $2.50/1M)、multi-tool で一問を落として 98.3% でした。low では平均4トークンの推論が増え、1,000リクエスト当たり +$0.011 で通過率が 100% になりました。

短い事実回答の下限(01)を含む前の二つのベンチマークでは none が下限かつ最適でした。この実験では、下限が low へ一段上がりました。ツールを使うタスクでは、少量の推論が品質を改善する場合があることを実測で確認しました。

ツール使用の内訳

gpt-4o の過剰なツール呼び出し

1つの合計通過率 90% だけでは失敗箇所は分かりません。型別に分けると、このベンチマークの主要な根拠が見えます。

モデル      推論強度  無ツール(18) 1ツール(24) マルチツール(18)
gpt-4o    —        83.3%      100%      83.3%
gpt-5.2   none     100%       100%      94.4%
gpt-5.2   low      100%       100%      100%    ← パレート最適
  • no-tool — gpt-4o の失敗箇所。 gpt-4o はツールが不要でも計算機を呼び出し、83.3% にとどまりました。評価モデルは 三件を「採点基準はツール呼び出し 0 を求めているのに、モデルがツールを呼んだ」と判定しました。gpt-5.2 は全強度で 100% でした。
  • one-tool — 全設定で通過。 すべての (モデル×強度) セルが 100% でした。ツールを 1つ呼び出すタスクは、どちらのモデルでも解けました。
  • multi-tool — 少量の推論が改善。 gpt-4o は 83.3%、gpt-5.2 none は 94.4%、low は 100% でした。2–3回ツールをつなぐ処理で、少量の推論が計画と実行を安定させました。gpt-4o から gpt-5.2 low への 16.7%p 上昇が、実作業に近い品質差です。

正答とは別にツール使用過程を 0–1 で評価するツール効率スコアも、同じ傾向でした。gpt-4o は 0.950 で最も低く、no-tool での過剰な計算機使用が影響しました。gpt-5.2 low は 0.988 で最も高く、通過率も 100% でした。

第二の合図

low を超えるとコストだけが増えた

low を基準にすると、medium は low より 1,000リクエスト当たり約 $0.13 高く、通過率は 98.3% に低下しました。high は low 比でリクエスト当たり +14%、xhigh は +26% でした。xhigh の通過率は 100% ですが、正答当たりでは low より 26% 高い結果です。

レイテンシも同じ傾向です。 none は gpt-4o より 5% 速く(2,902ms 対 3,044ms)、low は +0.7% でした。一方、high は +20.0%、xhigh は +23.9% でした。レイテンシに敏感なタスクでは、medium が現実的な上限です。

コストは入力トークンに左右されました。 リクエスト当たりの入力は約 1,200–1,300トークンで、システムプロンプトとツール定義がループの各反復で再送されます。隠れた推論トークンは 0(none)から約 52(xhigh)に増えますが、入力に比べれば小さい値です。推論トークンが xhigh のコストを左右した多段階(02)とは異なる構造でした。

PTU でも low が最適でした。 low のスループットは gpt-4o の 0.939倍ですが、通過率 100% により分当たり正答は +4.3% でした(gpt-4o は 90%)。スループット損失(−6.1% req/min)より、通過率の上昇(+10.0%p)が大きい結果です。さらに強度を上げると、スループットは medium で −8.5%、xhigh で −10.8% となりました。PAYG と PTU のどちらでも low が最適でした。

透明性

測定上の例外も開示する

どの測定にも例外やノイズはあります。このベンチマークで生じた事象を、再検証できるように省略せず記録します。

  • 外れ値 1件。 tu_18 の low 1回目はトークン数で 3σ を超え、運用上の問題を示すマーカーもあったため、集計から除外しました(360セル中 1件 = 0.3%、方法論の警告線 10% を大きく下回ります)。生 JSON には残しています。
  • ループ上限 12件。 360セル中 12個(3.3%)がツールループ 4回の上限に達し、ツールなしで回答を返しました。各行に iteration_cap マーカーを記録しています。
  • 部分点は正答から除外。 評価スコア 1(部分正答)は §7 に報告しますが、正答当たりのコストでは正答に含めません。ツールタスクの部分正答を本番で正答と見なさないためです。

限界

どこまで信じられるか

この結果は、一つの混合ツールタスクセット、一つの価格スナップショット、特定のモデルと採点基準に基づく小規模な集計です。絶対値をそのまま一般化するより、方法を再利用するほうが安全です。

  • 検索はモックです。 このベンチマークの web_search は実際のウェブ検索ではなく、固定知識ベースを参照するモックです。ライブ検索に伴う制御不能な変動は範囲外としました。少量の推論が multi-tool の信頼性を高め、low を超えるとトークンが無駄になるという結果は、この単純化の範囲での実測です。
  • 標本。 N=20 · R=3 で、信頼区間や統計的有意性は主張しません。方向性は明確ですが、絶対値は小標本の結果として慎重に解釈します。
  • 価格。 価格表は一つだけを基準にしました。料金や課金方式が変われば、同じ原資料からコストを再計算する必要があります。
  • 採点。 評価モデル(gpt-4o)を使用し、評価プロンプトの SHA-256 を採点 JSON に記録しました。
  • PTU。 スループットはトークンベースの推定であり、ライブ PTU 負荷テストの実測ではありません。

デフォルト

ツール使用エージェントのデフォルトは gpt-5.2 effort=low です。PAYG では正答当たり 24% 安く(gpt-4o 比)、PTU では分当たり正答が +4.3% でした。multi-tool 通過率も 83.3% から 100% に上がりました。この実験では none ではなく low が下限で、1段上の設定です。ただし、low を超えると品質は改善せず、コストとレイテンシが増えました。
