exp003 — Did reasoning effort pay off in a tool-using agent?

By Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

In the previous two benchmarks the answer was always “don't raise the effort.” This time was different. A mixed task that calls a tool, takes the result, and decides again — across all three benchmarks, the first place where reasoning finally paid off, if only a little.

In pre-registration we wrote that a middle effort (low–medium) would be the Pareto knee. gpt-4o would handle no-tool·one-tool but break down on multi-tool sequencing; gpt-5.2 none, with no reasoning surface to plan over, would be as weak as gpt-4o on multi-tool; and high·xhigh would, with quality saturated, over-call tools on trivial samples.

The measurement was half right, half surprising. low really was the floor — this once, not none. But the real place gpt-4o broke down was not multi-tool; it was calling a calculator on problems that needed no tool. This note retraces that day as design → inputs → artifacts → prediction vs. measurement → the tool-overuse map → decision — so the next person wanders less on the same road.

Design

This time, tools enter

One question. On tool-using agent work — the mixed case closest to reality — how far do you have to raise gpt-5.2's effort before reasoning is worth the bill? We look through two lenses at once: PAYG (dollars per correct answer) and PTU (correct answers per minute per fixed capacity).

Dataset. Twenty frozen authored samples (tu_01…tu_20). Three types are mixed — 6 no-tool (knowledge/format only), 8 one-tool (a single calculator or a single search), 6 multi-tool (a chain of 2–3 steps from search → calculator). Every sample has a verifiable answer and an expected_tool_calls answer key for which tools should be called.

Exactly one axis moves — we sweep gpt-5.2's reasoning.effort across none · low · medium · high · xhigh, and set a gpt-4o baseline (which has no reasoning parameter) alongside it. Each (sample × model × effort) cell is repeated three times (R=3), and the tool loop is cut at a maximum of four iterations (max_tool_iterations: 4).

Pre-registered prediction

A middle effort (low–medium) is the Pareto knee for mixed work. gpt-4o handles no-tool·one-tool but breaks on multi-tool; gpt-5.2 none is as weak as gpt-4o on multi-tool; and high·xhigh, with quality saturated, only over-call tools.

This experiment's role

After the short-answer floor (01) and the multi-step ceiling (02) both ended in “don't raise the effort,” the mixed anchor that checks whether there is a minimum point where a reasoning surface is actually needed.

Inputs and artifacts

What it consumed, what it left behind

What this experiment consumed and what it left behind are not hand-written summaries but actual files in the repo. So you can trace it from input to output in a single line.

Input (in)

Dataset: benchmarks/03-tool-using-agent/dataset.json (pinned by SHA-256).
Prompts·tools: the system prompt and the tool configuration are each fingerprinted by SHA-256 — guaranteeing a single system prompt and tool configuration were used across all 360 cells.

Artifacts (out)

Raw calls: runs/*.json (Foundry v1 payloads + raw per-iteration tool_calls trajectories).
Grading: judge_runs/*.json (correctness grading + a separate tool-efficiency score).

Charts/tables: results/cost-curves/benchmark-03-*.png·.csv.

The measurement surface is 360 cells (gpt-4o 60 + gpt-5.2 300, five effort steps). Cells excluded as outliers: 1 (tu_18/low/r0). Grading was one pass per cell by the neutral judge gpt-4o, 360/360 successful. Every JSON is a real Azure Foundry v1 call with not one "fixture": true marker. That said, 12 of the 360 cells (3.3%) hit the 4-iteration tool-loop cap and were forced to return a final answer without a tool, each row carrying a tool_loop_terminated="iteration_cap" flag.

Prediction vs. measurement

The prediction was only half right

What we predicted

A middle effort is the knee. gpt-4o breaks on multi-tool. gpt-5.2 none is weak on multi-tool. In short: “mixed work needs a little reasoning.”

What came out

low really was the Pareto knee — this once, not none. But where gpt-4o broke down was not only multi-tool but no-tool (83.3%). It called a calculator when no tool was needed.

Verdict: direction confirmed, failure mode reversed. The pre-registration that “mixed work needs a minimum reasoning surface” was supported — low (not none) is Pareto-optimal per correct answer. But gpt-4o's weakness was not only multi-tool sequencing; it was the habit of calling a tool when it shouldn't. Half the prediction held, and half was corrected by the data into a more interesting story.

First signal

The floor was low, not none

The dollars in the table below apply the methodology's PAYG formula to the price snapshot pricing/azure-openai-payg-2026-05.yaml (accessed 2026-05-19); they are re-cited from analysis.md §5 and normalized per 1,000.

Model     Effort   Per 1,000 req   Pass rate       Per 1,000 correct
gpt-4o    —        $3.29           90.0% (54/60)   $3.65   ← baseline
gpt-5.2   none     $2.76           98.3% (59/60)   $2.81
gpt-5.2   low      $2.77           100%  (60/60)   $2.77   ← Pareto-optimal
gpt-5.2   medium   $2.89           98.3% (59/60)   $2.94
gpt-5.2   high     $3.18           98.3% (59/60)   $3.23
gpt-5.2   xhigh    $3.50           100%  (60/60)   $3.50

Per 1,000 correct, low is $2.77 — 24% cheaper than gpt-4o ($3.65). And it is the only cell under gpt-4o's unit price to reach 100% pass. none is already about 16% cheaper than gpt-4o per request too (input price $1.75/1M vs. $2.50/1M; in a tool loop the input dominates the bill), but it misses one multi-tool problem and stays at 98.3%. What low added was only an average 4 tokens of reasoning surface, and that small surface pulled the pass rate up to 100% (+$0.011 per 1,000 requests).

In the previous two benchmarks none was both floor and optimum. Here, for the first time, the floor rose by one notch. Mixed real work has a positive minimum-effort floor — reasoning finally, if only a little, paid off.

Tool-overuse map

gpt-4o called tools too often

The single aggregate number 90% doesn't show “where.” Split by type, the core evidence of this benchmark appears.

Model     Effort   No-tool(18)  One-tool(24)  Multi-tool(18)
gpt-4o    —        83.3%        100%          83.3%
gpt-5.2   none     100%         100%          94.4%
gpt-5.2   low      100%         100%          100%      ← Pareto-optimal
  • No-tool — where gpt-4o tripped. gpt-4o called a calculator even when no tool was needed, stalling at 83.3%. The judge failed three items as “the rubric requires 0 tool calls but the model called a tool” — it overused the calculator even on prompts like “1+1.” gpt-5.2 is 100% at every effort.
  • One-tool — fully saturated. Every (model×effort) cell is 100%. Single-tool dispatch is a solved problem for both families.
  • Multi-tool — where reasoning helps. gpt-4o 83.3%, gpt-5.2 none 94.4%, low 100%. On chains of 2–3 steps, a small reasoning surface makes “plan and execute” more reliable. The 16.7pp rise from gpt-4o to gpt-5.2 low is the real-work signal this benchmark was built to catch.

The tool-efficiency score (separate from correctness grading, rating the trajectory 0–1) points the same way. gpt-4o is lowest at 0.950 — even when it got the answer right, it lost points for overusing the calculator on no-tool items. gpt-5.2 peaks at low with 0.988 — the very cell that hit 100% pass.

Second signal

Past low, the same quality costs more

Above low, the earlier benchmarks' story repeats. medium spends about $0.13 more per 1,000 requests yet its pass rate falls to 98.3%, Pareto-inferior to low. high is +14% per request vs. low, xhigh +26%, while the pass rate is unchanged (xhigh is 100% but 26% more expensive than low per correct answer).

Latency tells the same story. none is actually 5% faster than gpt-4o (2,902ms vs. 3,044ms), and low is +0.7%, effectively flat. But high widens to +20.0% and xhigh to +23.9%. For a latency-sensitive workload, medium is the realistic ceiling.

Break down the tokens and this benchmark's own structure shows. Input per request dominates the bill at about 1,200–1,300 tokens — because the system prompt and tool definitions are reloaded on every loop iteration. Hidden reasoning tokens grow from 0 (none) to about 52 (xhigh), but against the input they are small. This is the opposite of the multi-step benchmark (02), where reasoning tokens dominated the xhigh cost — the way input dominates the bill here instead resembles the short-answer benchmark (01).

The PTU lens converges on low too. low is 0.939× gpt-4o's throughput, but its 100% pass rate flips that into +4.3% correct answers per minute (gpt-4o is 90%). The pass-rate gain (+10.0pp) outweighs the throughput loss (−6.1% req/min). Raise effort further and only throughput is trimmed (medium −8.5%, xhigh −10.8%). It is a convergence of two lenses — PAYG (lowest per correct answer) and PTU (highest correct answers per minute) — both pointing at the same low.

Transparency

Even the smudges left on the numbers, as they are

No measurement is perfectly clean. We write down the marks this benchmark left without erasing them — because hidden away, they'd trip the next person at the same spot.

  • One outlier. tu_18's first low repetition crossed 3σ in tokens with an operational flag attached, so it was excluded from the aggregate (1 of 360 cells = 0.3%, well under the methodology's 10% alert line). It remains in the raw JSON tree — an outlier exclusion is only an aggregation mask, not a deletion.
  • Twelve loop-cap cells. 12 of 360 cells (3.3%) hit the 4-iteration tool-loop cap and were forced to return an answer without a tool. Each row carries an iteration_cap flag, so you can trace which cells were pressed against the cap.
  • Partial credit excluded from correct. Judge score 1 (partial) is reported separately in §7 but removed from the denominator of per-correct cost — because at production scale a partial answer on tool work is not a correct answer. We state this binarization choice to reveal how the headline was computed.

Limits

How far can you trust this

These results are small-sample aggregates from one mixed tool-task set, one price snapshot, and a particular model-and-rubric combination. It is safer to take the method than the numbers themselves.

  • Search is mocked. This benchmark's web_search is not a real web search but a fixed knowledge-base lookup. Live search would import uncontrollable variance, so we placed it out of scope. The headline (a small reasoning surface raises multi-tool reliability; past low is token waste) is robust to this simplification. It is not a perfect reproduction but a place where we controlled only what we could control — and we don't hide that boundary.
  • Sample. N=20 · R=3. At this sample size we claim no confidence intervals or statistical significance — the directional conclusion is robust, but treat absolute magnitudes with small-sample caution.
  • Price. A single snapshot. If rates or the usage schema change, cost must be recomputed from the same raw data.
  • Grading. LLM-as-judge (gpt-4o). We record the judge prompt's SHA-256 in the grading JSON to watch for drift.
  • PTU. Throughput is a token-based estimate, not a live PTU load test.

So what becomes the default

The default for a tool-using agent is gpt-5.2 effort=low — in both PAYG and PTU. 24% cheaper per correct answer (vs. gpt-4o), +4.3% correct answers per minute, and a quality bonus that lifts multi-tool pass rate from 83.3% to 100%. This once, the floor is low, not none. But above low, once again, only cost and latency are added without quality.
