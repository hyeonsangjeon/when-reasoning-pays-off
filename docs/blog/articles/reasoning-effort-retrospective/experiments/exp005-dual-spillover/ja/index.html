exp005 — キャッシュプールを本当に分けたら、賢いポリシーがさらに大きく負けた

執筆 Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

前のノート(exp004)では、デプロイ一つの上でスピルオーバー(あふれへの備え)を模擬しました。二つのポリシーは事実上引き分けで(−0.1657%p)、そのとき私たちはこう書いた — “最終的な判定はフェーズ 2 で行う。” 今回がそのフェーズ 2 です。今度はデプロイが二つあり、実際にスロットルが発生し、元デプロイと予備デプロイのキャッシュプールも物理的に分かれます。

だから、こんな予測が自然でした — キャッシュプールが本当に分かれるなら、元デプロイを先に守る先回り(proactive)ポリシーが、今度は有効かもしれません。事前登録した読みは二つでした。差が大きくなれば‘キャッシュ再構築コスト’が実際に生じ、似たままならキャッシュプール分離は大きな要因ではない、ということです。

今回の実測は、予測とさらに大きく異なりました。飽和定常状態キャッシュヒットは reactive 99.2337%, proactive 98.2414% — 先回りした側がむしろ 0.9923%p 低い結果でした(フェーズ 1 の差の約 6倍)。さらに proactive はスロットルされた元デプロイにこだわって実 429(“今はだめ”の信号)を 167回受け(reactive は 0回)、費用も $0.91 高くなりました。このノートでは、その 22分間を設計 → 入力 → 予測対実測 → 二つの曲線 → 判断の順にたどります — キャッシュプールを分けると、賢いポリシーはさらに大きく負けました。

なぜ読むのか

元デプロイと予備デプロイを本当に分けて使うと何が起きるのか

PTU(固定容量)デプロイが上限に近づくと、トラフィックの一部を予備デプロイへ流します。これがスピルオーバーです。フェーズ 1 はこの予備経路を、デプロイ一つの中でラベルとしてまねただけでした — 元経路でも予備経路でも同じキャッシュ(プロンプトを再利用して節約する仕組み)を参照していました。だからポリシー差がキャッシュにほとんど刻まれませんでした。

フェーズ 2 では、この不確実性を取り除きます。元デプロイと予備デプロイを実際に別のデプロイにすると、Azure の設計上、キャッシュプールも分かれます。これにより、‘どのデプロイへ送ったか’がキャッシュの状態に直接反映されます。一方に集約すればそのプールだけが温かく保たれ、二つに分ければ両方が冷えやすくなります。

元デプロイ + 予備デプロイを物理的に分けて運用しているなら、このノートが参考になります。“元デプロイを守るためにトラフィックを先に少しずつ分ければ、キャッシュをもっと守れるのか?” という問いに、この実験は一つの実測の答えを示します — そして結果は、むやみに分けない方がよいことを示しています。

設計

今回はキャッシュプールを本当に分ける

なぜこれを測ったのか。 フェーズ 1 の引き分けには解釈上の制約が一つありました — デプロイが一つなのでキャッシュプールが共有でした。つまり ‘ポリシー差がもともと刻まれない’ のか、‘共有キャッシュだから刻まれない’ のかを切り分けられませんでした。フェーズ 2 はこの不確実性を解消します。キャッシュプールを実際に分けて、それでも判定が同じかを確認します。

そこで、仮説の判定基準を‘差の大きさ’に置きました。 事前登録した読みは二つです — フェーズ 2 の差がフェーズ 1 よりはっきり大きくなれば、キャッシュプールが分かれるときにトラフィックを分けるコスト(キャッシュ再構築コスト)が実際に生じると判断します。似ていれば、キャッシュプール分離はポリシーのタイミングより影響の小さい要因だと判断します。 どちらにせよ実測で判定します。

原因究明ではなく、緩和策の比較です。 ‘スピルオーバーがキャッシュ低下の根本原因だ’ という強い主張は、すでに現場観察で支持を失っていました。この実験は原因を掘る場ではなく、二つの緩和ポリシーのうちどちらがよいかだけを競わせる場です。

なぜ二重デプロイか。 元デプロイ(ptu-deploy-throttled)に 60,000 TPM(分あたりトークン上限)という低い上限をあえてかけ、約 30K トークン負荷が実 429を返すようにしました。予備デプロイ(gpt-5.2)には 500,000 TPM の十分な余裕を与えました。デプロイ名が異なればキャッシュプールも分かれます — フェーズ 1 では模擬にとどまった ‘物理分離’ が、ここでは実際に分離されています。

問いは一つです。 キャッシュプールが物理的に分かれた上で、先回りするスピルオーバーは事後対応よりキャッシュを守るのか。

設計(負荷)。 フェーズ 1 とバイトまで同じ 22分の負荷を、二つのポリシーへ同じように流す — ウォームアップ 2分(0.3 TPS) → ランプ 10分(0.5→2.5 TPS) → 持続 10分(2.5 TPS)。effort=low、システムプロンプトは約 30K トークン(二つの実行がバイトまで同一になるよう SHA-256 98d3a5…088a で固定、corpus_seed 4242)。予定リクエストはポリシーごとに 2,136件(ウォームアップ 36 · ランプ 900 · 持続 1,200)。

変える軸は一つだけ — policy.type を reactive と proactive で切り替える。プロンプト·負荷·モデル·推論強度·二つのデプロイ上限はすべて固定なので、二つの成果物の差はポリシーだけに起因します。

事前登録予測

キャッシュプールが本当に分かれれば proactive が割に合うかもしれない。事前登録した判定線は差の大きさ — フェーズ 1 より大きくなればキャッシュ再構築コストが実際に生じ、似ていれば分離の影響は小さいと判定します。

この実験の役割

フェーズ 1(共有キャッシュでの基準値)に続く高忠実度の再測定。元/予備キャッシュプールが物理的に分かれるとき、ポリシー差がキャッシュ·費用·429に実際に現れるかを確認します。

予測対実測

予測はまた外れた — もっと強く

何を予測したか

キャッシュプールが本当に分かれるなら、先回りする(proactive)ポリシーが今度は有効かもしれないと予測しました。少なくとも差の向きが反転しうる場所でした。

何が出たか

飽和キャッシュヒットは reactive 99.2337% vs proactive 98.2414% — 先回りした側が 0.9923%p 低い結果でした(フェーズ 1 の −0.1657%p より約 6倍大きい差)。実 429 は 0 対 167。

判定: キャッシュプールを分けると、先回りの不利がより明確になりました。 事前登録した二つの読みのうち、実測は‘差が大きくなる’を選んだ — つまりキャッシュプールが分かれるとき、トラフィックを先に分けるコスト(キャッシュ再構築コスト)は実際に発生し、そのコストは proactive 側に現れました。フェーズ 1 で “共有キャッシュだから差が現れなかったのか?” という疑問には、この実測が答えを示しました — キャッシュを本当に分けると、分けるポリシーが不利になりました。

第一の合図

二つの曲線はいずれもおおむね 99.2% 付近を通ります。reactive は標準偏差 0.0026%p で岩のように安定しています — 予備デプロイ一つへ寄せ、そのプールがずっと熱かったためです。逆に proactive は標準偏差が 4.3726%p と大きく変動します。原因は二つあります。スロットルされた元デプロイが返した持続区間 429 154件(トークン 0 の失敗行)と、トラフィックを二つのプールへ分けて生じたキャッシュミス 12件(元デプロイ 7 · 予備デプロイ 5)が分ごとに谷を作り、その谷が集計平均を 98.2414% まで引き下げました。

全区間(ウォームアップ+ランプ+持続)へ広げても向きは同じです — reactive 99.0479% vs proactive 98.2112% で、reactive が 0.8367%p 高い。フェーズ 1 では集計区間を広げると向きが反転しましたが、フェーズ 2 ではどの区間でも reactive が上回りました。

第二の合図

なぜ分かれたのか — 分けると両方が冷める

今回は二つのポリシーがキャッシュに明確に異なる結果を残しました — ここがフェーズ 1 との違いです。reactive はウォームアップ最初のリクエストから予備デプロイへ移り、飽和のあいだずっとトラフィックの 98.75% をその一つのプールへ寄せました。一つのプールだけを温め続けたので、持続キャッシュミスは 0件、プールは 99.2336% に熱く保たれました。実 429 も 0件 — スロットルされた元デプロイにほとんど触れなかったためです。

proactive は異なる動きを示し、それが不利に働きました。 元デプロイを守ろうとしてトラフィックを分け、飽和スピルオーバー率は 67.95% にとどまりました — 残りの約 32.05%はスロットルされた元デプロイへ送られ続けました。そのデプロイは 30K トークン負荷に耐えられず実 429 を 167回返しました。さらに、トラフィックが二つのプールへ散ったため、どちらも reactive の単一プールほど温まりませんでした — 持続キャッシュは元デプロイ 96.7534%、予備デプロイ 98.6942% で、どちらも reactive の 99.2336% より低い値でした。

費用とレイテンシも同じ向きです。 二つの実行は総トークンがほぼ同じなのに(reactive 45,850,205 · proactive 45,851,851)、全区間費用は reactive $17.895660 vs proactive $18.806026 — proactive が $0.910366 高くなりました。理由は純粋にキャッシュ温度です。proactive の低いキャッシュヒットが、入力トークン約 38万個をキャッシュ料金($0.175/1M)から定価($1.75/1M)へ押し出しました。持続の最初のトークンレイテンシ(TTFT)も reactive のほうが速く(p50 7,153.9ms 対 7,926.6ms)、全区間 p95 は proactive が 34,631.71ms まで跳ね上がる — 429 バックオフが実レイテンシの上に積み上がったためです。

まとめると: キャッシュプールが本当に分かれると、‘元デプロイを守るためにトラフィックを分ける’ という賢い発想は、二つのキャッシュを温め直すことになり、スロットルによる 429 まで受ける結果になりました。むしろ有効だったのは単純な運用でした — 一つのプールへ寄せ、熱く保った reactive です。

透明性

数値に残る不規則なデータもそのまま示します

どんな測定も完全にきれいではありません。この実験が残した跡を、消さずにそのまま書いておく — 隠すと次の人が同じ場所でつまずくためです。

  • 除外した外れ値 0件。 外れ値規則は、‘飽和区間でレイテンシが平均+3σを超え、同時に実 429·リトライ·経路切り替えのようなログイベントが重なったとき’に限り除外します。候補は reactive 6件·proactive 18件あり、その一部はイベントと重なったが、候補を外しても持続 TTFT は 1% 未満しか変化しなかったため、すべて残しました。
  • 残した異常行。 proactive には 0トークンの持続行 154件(実 429 の失敗試行)とキャッシュミス行 12件があり、reactive にはどちらも 0件です。これは測定誤りではなく、このベンチマークが測ろうとした現象そのものなので、生データのまま集計に反映した — proactive の低い持続平均は、まさにこの 429 とキャッシュミスから来た。隠しません。
  • 見出しは持続定常状態です。 ランプ·ウォームアップの過渡期を混ぜるとポリシー効果がぼやけるため、仮説が生きる持続 10分を代表値にした。全区間の数字も併記し、どの窓でも reactive が前にいることを確認できるようにしました。

限界

どこまで信じられるか

この結果は、一つの Foundry リソース内の二つのデプロイ、それぞれ一つの容量等級、一つの負荷プロファイル、一回の実行から出た値です。数字そのものより、方法と向きを持ち帰るほうが安全です。

  • 絶対値は移植できない。 二つのデプロイは一つのリソース内、それぞれ一つの容量等級です。キャッシュヒットやドル値は、別のテナント·リージョン·容量計画へそのまま移らない — ポリシー間の差の向きを読むべきです。
  • カスタムルーターです。 スピルオーバーは Python クライアントのルーターで実行しました。Azure のネイティブスピルオーバー(spilloverDeploymentName方式)とは違う可能性があるため、応答ごとのスピルオーバーヘッダーを残し、後でネイティブ方式と照合できるようにしました。
  • 緩和策の比較であり、原因究明ではありません。 この実験は、ある現場キャッシュ低下の根本原因を指し示すものではありません。強い形の仮説は、すでに現場測定で棄却されている。
  • 負荷と標本。 22分の一回、ポリシーごとに 2,136 予定リクエスト。この大きさでは信頼区間や統計的有意性は主張しません — 向きは堅いが、絶対値は小標本として注意する。
  • 範囲外。 応答品質は採点しておらず、max_output_tokens を PTU 予約のように使う効果(別仮説)も、この実験では扱わない。

だから何をデフォルトにするか

元デプロイがスロットルされ、余裕のある予備プールがあるなら、単純な事後対応(reactive)をデフォルトにする。失敗したリクエストと続く数件を予備プールへ寄せ、その一つのプールを熱く保つこの単純な規則が、元デプロイを守ろうとしてトラフィックを先に分ける proactive に勝った — キャッシュは 0.9923%p 余計に守り(持続)、費用は $0.910366 安く、実 429 は 167件ではなく 0件でした。キャッシュプールが物理的に分かれる場合、トラフィックの分散には両方のプールが冷えるという不利益があります。ワークロードの形が変わった場合は、改めて測定してください。
