实验笔记 · exp005 · PTU 双部署溢出测量(Phase 2) · 当缓存池真的被拆开

exp005 — 真正拆分缓存池后，聪明策略输得更明显

作者 Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

上一篇笔记(exp004)在一个部署上模拟了溢出(提前防溢)。两种策略几乎平手(−0.1657 pp)，我们当时写下：“真正的判决要交给 Phase 2。” 现在就是 Phase 2。部署变成了两个，限流是真实的，主部署与备用部署的缓存池也物理分离。

所以，一个预测很自然 — 如果缓存池真的分开，提前保护主部署的预先准备(proactive)策略，这次也许会值回成本。预先登记的读法有两条：如果差距变大，说明“缓存重建成本”是真的；如果差不多，说明缓存池分离不是主要因素。

这次测量把直觉推翻得更重。饱和稳态缓存命中率是 reactive 99.2337%, proactive 98.2414% — 提前行动的一侧反而低了 0.9923 pp(约为 Phase 1 差距的 6 倍)。而且 proactive 还执着于 throttled 主部署，实际遭遇了 167 次 429(“现在不行”信号)(reactive 为 0)，成本也多花 $0.910366。本文按设计 → 输入 → 预测对实测 → 两条曲线 → 决定回看这 22 分钟 — 一旦拆开缓存池，聪明策略输得更明显。

为什么值得读

主部署和备用部署真的分开用，会发生什么？

PTU(固定容量)部署接近上限时，把一部分流量导向备用部署，这就是溢出。Phase 1 只是在一个部署里用标签模拟这条备用路径 — 无论走主路径还是备用路径，看到的都是同一个缓存(重复利用提示、节省计算的存储池)。所以策略差异几乎没有写进缓存。

Phase 2 去掉这个疑点。把主部署和备用部署放成真正不同的部署时，按 Azure 设计，缓存池也会分开。现在“送到哪个部署”会直接写进缓存温度。只往一边打，那一个池会保持热；分成两边打，两边都会变温。

如果你在物理上分开运营主部署 + 备用部署，这篇就很贴近你的场景。“为了保护主部署，提前把流量一点点分出去，会不会更保护缓存？”这个问题，实验给出一个实测答案 — 而答案更接近“别分”。

设计

这次真的拆分缓存池

为什么测这个。 Phase 1 的平手有一个缺口 — 只有一个部署，所以缓存池是共享的。于是我们无法分辨，究竟是“策略差异本来就写不进去”，还是“因为共享缓存才写不进去”。Phase 2 堵上这个缺口。把缓存池真正拆开，再看判决是否相同。

所以假设押在“差距大小”上。 预先登记的读法分两条 — 如果 Phase 2 的差距明显大于 Phase 1，说明缓存池分开时分流的代价(缓存重建成本)是真的。如果差不多，说明缓存池分离小于策略时机这个因素。 无论哪边，实测来选答案。

这是缓解策略比较，不是根因追捕。 “溢出是缓存下降根因”这个强说法，已经在现场观察里失去力量。本实验不是挖根因，而只是比较两种缓解策略哪一个更好。

为什么双部署。 我们有意给主部署(ptu-deploy-throttled)设下 60,000 TPM(每分钟 token 上限)的低上限，让约 30K token 的负载真的吐出 429。备用部署(gpt-5.2)则给足 500,000 TPM 的余量。部署名不同，缓存池也不同 — Phase 1 只是模拟的“物理分离”，这里是真的。

问题只有一个。 在缓存池物理分离之上，提前准备的溢出是否比事后反应更保护缓存？

设计(负载)。 与 Phase 1 字节级相同的 22 分钟负载，原样流过两种策略 — warmup 2 分钟(0.3 TPS) → ramp 10 分钟(0.5→2.5 TPS) → sustain 10 分钟(2.5 TPS)。effort=low，系统提示约 30K token(为保证两次运行字节级一致，用 SHA-256 98d3a5…088a 固定，corpus_seed 4242)。计划请求为每种策略 2,136 个(warmup 36 · ramp 900 · sustain 1,200)。

只改一条轴线 — 把 policy.type 在 reactive 与 proactive 之间切换。提示、负载、模型、强度、两个部署上限全部固定，因此两个产物的差异只来自策略。

预先登记预测

缓存池真的分开后，proactive 也许会值回成本。预先登记的判定线是差距大小 — 大于 Phase 1 说明缓存重建成本是真的；差不多说明分离只是小因素。

本实验的作用

继 Phase 1(共享缓存地板)之后的高保真重测。当主/备用缓存池物理分离时，确认策略差异是否真的写进缓存、成本与 429。

预测对实测

预测又落空了 — 而且更重

预测了什么

如果缓存池真的分开，提前准备的(proactive)策略这次也许会值回成本。至少，这是一个可能让差距方向反转的位置。

结果是什么

饱和缓存命中率是 reactive 99.2337% vs proactive 98.2414% — 提前行动的一侧低了 0.9923 pp(约为 Phase 1 的 −0.1657 pp 的 6 倍)。实际 429 是 0 对 167。

判定：缓存池一分开，提前准备更明显地没有值回成本。 预先登记的两条读法里，实测选择了“差距变大” — 也就是说，缓存池分开时提前分流的代价(缓存重建成本)是真的，而且这笔账记在了 proactive 头上。Phase 1 里“是不是因为共享缓存所以写不进去？”的疑问，现在有了答案 — 缓存真的一分开，分流策略就吃亏。

第一个信号

聪明策略输得更明显

下表看的是持续(sustain) 10 分钟稳态 — 负载已经压到目标上、假设真正成立或失败的区间。数字从已发布汇总 analysis.md §5 与 §7 重新引用。

策略        饱和溢出       饱和缓存命中(每分钟均值 ± 标准差)   实际 429   备注
reactive    98.75% 触发    99.2337%  (±0.0026 pp)           0         基线 · 集中到一个备用池并保持热
proactive   67.95% 触发    98.2414%  (±4.3726 pp)           167       主+备用分流，两边都变冷
差值(pro−re)  —            −0.9923 pp                        +167      约为 Phase 1(−0.1657 pp)的 6 倍

两条曲线大体都经过 99.2% 附近。reactive 的标准差只有 0.0026 pp，稳得像石头 — 因为流量被集中到一个备用部署，那个池始终保持热。相反，proactive 的标准差高达 4.3726 pp，明显摇晃。原因有两个：throttled 主部署吐出的持续阶段 429 共 154 条(token 为 0 的失败行)，以及流量拆到两个池后形成的缓存 miss 12 条(主部署 7 · 备用部署 5)，逐分钟挖出凹口，这些凹口把汇总均值拉到 98.2414%。

把窗口扩到全程(warmup+ramp+sustain)，方向也一样 — reactive 99.0479% vs proactive 98.2112%，reactive 高 0.8367 pp。Phase 1 中窗口放大后方向会反转，但 Phase 2 中无论看哪个窗口，reactive 都领先。

第二个信号

为什么分叉 — 一分流，两边都变冷

这一次，两种策略在缓存上留下了真正不同的痕迹 — 这正是它和 Phase 1 分开的地方。reactive 从 warmup 第一个请求开始就转到备用部署，在整个饱和阶段把 98.75% 的流量集中到那一个池里。只持续加热一个池，所以持续阶段缓存 miss 为 0，池也保持在 99.2336% 的热度。实际 429 也是 0 — 因为几乎不碰 throttled 主部署。

proactive 的动作正相反，也正是这里绊倒了它。 为了保护主部署，它把流量拆开，饱和阶段溢出比例只有 67.95% — 剩下约 43%仍然走 throttled 主部署。那个部署扛不住 30K token 负载，实际吐出 167 次 429；流量散进两个池后，哪一边都没有 reactive 的单一池那么热 — 持续缓存为主部署 96.7534%、备用部署 98.6942%，两边都低于 reactive 的 99.2336%。

成本与延迟也指向同一边。 两次运行总 token 几乎相同(reactive 45,850,205 · proactive 45,851,851)，但全程成本是 reactive $17.895660 vs proactive $18.806026 — proactive 多出 $0.910366。原因纯粹是缓存温度：proactive 更低的缓存命中，把约 38 万输入 token 从缓存费率($0.175/1M)推到正价($1.75/1M)。持续阶段首 token 延迟(TTFT)也是 reactive 更快(p50 7,153.9ms 对 7,926.6ms)，全程 p95 则让 proactive 飙到 34,631.71ms — 因为 429 backoff 叠在了真实延迟之上。

总结起来： 缓存池真的分开后，“为了保护主部署而分流”这个聪明想法，结果变成缓存要重新加热两次，还要吃 throttle 罚分(429)。真正值回成本的是简单 — 集中到一个池、保持热的 reactive。

透明度

连数字上的污点也原样留下

任何测量都不可能完全干净。这个实验留下的痕迹，我们不擦掉，而是写出来；藏起来，只会让后来的人在同一个地方踩空。

  • 排除异常值 0 个。 异常规则只有在“持续阶段延迟超过均值+3σ，并且同时出现实际 429、重试、路径切换等日志事件”时，才排除一行。候选有 reactive 6 条、proactive 18 条，其中一部分与事件重合，但即使去掉这些候选，持续 TTFT 的变化也小于 1%，所以全部保留。
  • 保留异常行。 proactive 有 0 token 持续行 154 条(实际 429 的失败尝试)和缓存 miss 行 12 条，reactive 两者都是 0 条。这不是测量错误，而是这个基准本来要测的现象本身，所以按原始数据进入汇总 — proactive 较低的持续均值，正是来自这些 429 和缓存 miss。不隐藏。
  • 头部数字采用持续稳态。 如果把 ramp、warmup 的过渡期混进去，策略效果会被冲淡，所以本文把假设所在的持续 10 分钟作为代表数字。全程数字也放在旁边，方便确认无论哪个窗口，reactive 都领先。

限制

可以相信到哪里

这个结果来自一个 Foundry 资源内的两个部署、各自一种容量等级、一条负载曲线和一次运行。比起直接拿走数字，更稳妥的是带走方法和方向。

  • 绝对数值不能迁移。 两个部署在同一个资源内，各自只有一个容量等级。缓存命中和美元数不会原样迁移到其他租户、区域或容量计划 — 应该读策略之间差异的方向。
  • 这是自定义路由器。 溢出由 Python 客户端路由器执行。它可能不同于 Azure 原生溢出(spilloverDeploymentName 方式)，所以我们保留了每个响应的溢出 header，方便之后与原生方式对照。
  • 这是缓解策略比较，不是根因追捕。 本实验不能指认某个现场缓存下降的根因。强形式假设已经被现场测量否定。
  • 负载与样本。 一次 22 分钟运行，每种策略 2,136 个计划请求。在这个规模下不主张置信区间或统计显著性 — 方向稳健，但绝对幅度要按小样本谨慎解读。
  • 范围之外。 没有给响应质量打分，也没有触碰把 max_output_tokens 当作 PTU 预留来用的效果(另一个假设)。

所以默认值是什么

如果主部署会 throttle，而你有一个余量充足的备用池，就把简单的事后反应(reactive)作为默认值。把失败请求及后续几次请求集中送到备用池，并让那一个池保持热，这条简单规则胜过了为了保护主部署而提前分流的 proactive — 它多保护了 0.9923 pp 的缓存(持续阶段)，少花 $0.910366，实际 429 是 0 次而不是 167 次。缓存池物理分离时，分流就是让两边池一起变冷的罚分。工作负载形态变了，就重新测。
