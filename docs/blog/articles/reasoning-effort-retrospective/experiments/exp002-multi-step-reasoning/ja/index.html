exp002 — 多段階推論で推論努力度は割に合ったのか

文 Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

この実験は、推論が勝つ番だった。少なくとも二段階を経なければ答えが出ない二十問 — 推論努力度(reasoning_effort)、つまりモデルが答えを出す前にどれだけ長く考え込むかを決めるつまみを一段上げるほど答えがより安全になりそうな場所である。

私たちはそう事前登録した。gpt-4o は半分余りを間違え(30–60% 通過)、gpt-5.2 は努力度を上げてようやく 80% を超える、と。測定は二つの予測をどちらも外した。gpt-5.2 は最も低い努力度ですでに満点を取り、gpt-4o は予想よりずっとよくできた。

このノートはその一日を設計 → 入力 → 成果物 → 予測対実測 → 外れ値 → 判断として振り返る。数字だけでなく、その数字が出た道筋と読み方まで一緒に — 次の人が同じ道で迷いにくいように。

設計

推論が勝つ番だった

検証する問いは一つに絞った。 少なくとも二段階を踏まないと答えが出ない問題だ。三つのベンチマークの中で、推論がいちばん値打ちを出しそうな場所である。ここで gpt-5.2 に考える力(推論の努力度)を足すと、答えは良くなるのか。請求に見合うのか。確かめることは二つだけだ。努力度を上げると(1) 品質は上がるか、(2) コストは上がるか。 お金は二つの見方で読む。使った分だけ払う PAYG では ‘正答一つ当たりいくら’ を見る。容量を先に借りる PTU では ‘同じ容量で分当たり何個当てるか’ を見る。

何で測るか — データセット。 凍結した合成サンプル 20個(mr_01…mr_20)。算術文章題、制約充足(複数の条件を同時に守る)、日付/時刻、因果の鎖、コードトレース(プログラムの実行順序を読む)、ブール論理、数え上げ。七つの型に均等に広げた。肝心なのは一目では答えが出ない点だ。途中結果を持ったまま、もう一歩進む必要がある。たとえば先に求めた値を、条件にもう一度当てはめる。そうして初めて正答に届く。だから ‘少なくとも二段階’ なのだ。すべてのサンプルには、機械で確かめられる正答がある。

変えるものは一つだけだ。 gpt-5.2 の reasoning.effort を none · low · medium · high · xhigh の五段階で動かす。横には、推論努力度の設定がない gpt-4o を基準線として置く。各 (サンプル × モデル × 努力度) セルは三回ずつ(R=3)繰り返す。

事前登録予測

多段階の形なら、短い事実回答ベンチマークの結論はひっくり返る。gpt-4o は30–60%しか通過しない。gpt-5.2 は十分な努力度で80% 以上通過する。だから推論は割に合うはずだ。

この実験の役割

短い事実回答ベンチマークの床(推論が不要な場所)と対になる。“推論が請求書に見合う”コスト曲面の天井を固定する目印だ。

データセット: benchmarks/02-multi-step-reasoning/dataset.json (SHA-256 で固定)。
プロンプト: システム/ユーザーテンプレートをそれぞれ SHA-256 で指紋化 — すべてのセルで、バイトまで同じプロンプトを使ったことを保証。

成果物 (out)

採点: judge_runs/*.json.
集計: analysis.json.
図表/表: results/cost-curves/benchmark-02-*.png·.csv.

測定表面は 360セル(gpt-4o 60 + gpt-5.2 300、努力度五段階)。外れ値として除外したセルは0個。採点は中立の審判 gpt-4o が、セルごとに一回行った。結果は360/360 成功(失敗 0、再試行 0)。審判は失敗に 0点、部分通過に 1点、完全通過に 2点を与える。だから平均 2.00 は 60個すべてが通過したという意味だ。gpt-4o の 1.50 は 45個の通過と 15個の失敗が混ざった平均である。すべての JSON は実際の Foundry v1 呼び出しだ。"fixture": true マーカーは一つもない(360行中 159行が reasoning_tokens > 0)。

予測対実測

予測は二度外れた

何を予測したか

gpt-4o は 30–60% で崩れる。gpt-5.2 は努力度を上げてようやく 80% を超える。要するに “高い努力度が品質を買い、コストに見合う。”

何が出たか

gpt-4o は 75%(45/60)で予想より強かった。gpt-5.2 は最も低い none ですでに 100%(60/60)。平均評価スコアで見ると gpt-4o 1.50 対 gpt-5.2 2.00 である。

判定: 予想が外れた。 “多段階では努力度を上げてこそ見合う”という予測は二つの場所で外れた。gpt-4o は予想より解けた。gpt-5.2 は努力度を上げる前からすでに満点だった。だから本当の分かれ目は努力度ダイヤルではない。gpt-4o を gpt-5.2 に入れ替えたことそのものだった。gpt-5.2 の基本設定(none、推論を切った状態)だけで、すでに十分だったからだ。

第一の逆転

モデルを変えると品質は上がり、コストは下がった

下の表のドルは、価格スナップショット pricing/azure-openai-payg-2026-05.yaml(アクセス日 2026-05-19)に方法論の PAYG 式を当てた値だ。analysis.md §5 から再引用している。

モデル      努力度   1,000リクエスト当たり 通過率          正答1,000件当たり
gpt-4o    —        $0.80         75.0% (45/60)   $1.06   ← ベースライン
gpt-5.2   none     $0.62         100%  (60/60)   $0.62   ← パレート最適
gpt-5.2   low      $0.86         96.7% (58/60)   $0.89
gpt-5.2   medium   $1.08         100%  (60/60)   $1.08
gpt-5.2   high     $1.25         100%  (60/60)   $1.25
gpt-5.2   xhigh    $2.18         100%  (60/60)   $2.18

この表は、連載本文と同じ目盛り(1,000件当たり)で読む。モデルを変えると、品質は上がり、コストはむしろ下がった。 正答 1,000件当たりで none は $0.62。gpt-4o($1.06) より42% 安い。

low はリクエスト当たり単価が 7.6% 高い。だが通過率も高い(96.7% 対 75%)ので、その上乗せ分を埋める。正答 1,000件当たりでは gpt-4o より16% 安い。最初の最適化は、努力度を上げることではなかった。モデルと努力度を一つの組み合わせとして見て、合格線を越えた最も安い地点を選ぶことだった。

第二の逆転

より高い努力度は同じ品質をより高く買った

ここで二つ目の事実が見えてくる。gpt-5.2 の none と xhigh は品質が同じ満点(平均 2.00、通過率 100%)である。ところが正答 1,000件当たりのコストは none($0.62)を底に、medium 1.75倍、high 2.02倍、xhigh 3.53倍($2.18)まで上がる。同じ答えを、だんだん高く買っているわけだ。

待ち時間も同じ話だ。 none は呼び出し当たり約 1.6秒(1,589ms)、xhigh は約 3.3秒(3,265ms)。gpt-4o(1,382ms) と比べると、none は約 15%遅いだけだ。だが xhigh は 2.4倍遅い。この区間の高い努力度は、より良い答えを買っていない。同じ答えをより高く、より遅く買っただけだ。

トークンを分けて見ると理由ははっきりする。 同じ皿でも、厨房での下ごしらえが長ければ原価は上がる。画面に見える答えが同じでも、モデルが内部で多く計算していれば請求は膨らむ。目に見える答えは none で約 5.8トークン、xhigh で約 7.7トークン。二トークン余り増えただけだ。ところが隠れた推論トークンは 0 から約 109.5 へ膨らむ。xhigh では、推論だけでリクエストサイズの約 26% を占める。品質はそのままなのに、請求されるトークンだけが膨らんだ。

この結果は、推論トークンが役に立たないという意味ではない。複雑な計画やツール選択のように、まだ踏むべき段階が残っているときにだけ推論は割に合う。 ただしこの問題の束は、最も低い組み合わせですでに採点基準の満点に届いてしまった。これ以上取れる点がない。天井に届いた場所で努力度だけを上げれば、追加で燃やす推論トークンは投資ではなくムダになる。要するに、努力度ダイヤルは ‘まだ上がる品質が残っているときにだけ’ 入れるスイッチだ。

PTU で見ても結論は同じだ。 gpt-5.2 none は gpt-4o の 0.994倍スループットで、通過率は 100% だ。同じ PTU 支出では、分当たり正答が +32.5% 多い(gpt-4o は 75%)。努力度を上げるとスループットだけが削られる。品質は良くならない。

品質マップ

gpt-4o はどこで崩れたか

gpt-4o の 75% という数字だけでは、“どこで”間違えたかが見えない。そこで作業の型別にスコアを分けた。すると失敗は一か所に集まっていた。戻って計算したり、逆向きに追跡したりする必要のある型だ。

  • 多く間違えた場所: 算術文章題(平均 1.20)、日付/時刻(1.00)、コードトレース(1.33)、制約充足(1.33) — 戻って計算したり、順序をさかのぼったりする型。
  • すべて正解した場所: 数え上げ、ブール論理、因果の鎖(各 2.00) — 前から後ろへ一度読むだけで足りる型。
  • gpt-5.2 は low を除く全努力度で全型満点(2.00)。low だけで 2セルが 0点だった — mr_05(制約充足)の安全フィルター拒否と、mr_15(コードトレース)の誤答「cba a」(正答「cbaa」)。そのため low ではこの 2型が各 1.78(±0.67)。

言い換えると、このデータセットは gpt-4o にこういう地図を描かせた。段階が短く、前に進むだけなら通過。戻ってたどる必要があるなら失敗。gpt-5.2 はその地図を丸ごと平らにした。どこでも正解した。

透明性

数字に残った汚れまでそのまま

どんな測定も完全にきれいではない。このベンチマークが残した跡を、消さずにそのまま書いておく。隠すと、次の人が同じ場所でつまずくからだ。

  • gpt-4o には予想より易しかった。 75% は事前登録した 30–60% を超えた。データセットが、そもそも gpt-4o にそれほど厳しくなかったということだ。だから “gpt-4o 比の削減幅” の大きさは、もっと難しいデータセットだった場合より小さくなった(期待 1.7–3.3倍の差 → 実現 1.7倍)。予測が外れた側を数字に合わせて消さない。小さくなった削減幅をそのまま残す。結論の方向(gpt-5.2 none は費用と品質の両方で上)は変わらない。
  • 安全フィルター拒否 1件。 mr_05 の low 1回目の反復で、Azure コンテンツフィルターがリクエストを止めた。入力·出力トークンは 0 で、定型の拒否が返った。このセルには運用上の問題を示す印(コールドスタート/再試行/切断)がない。だから外れ値として外す対象ではない。上書きせず、集計にそのまま残した(ジャッジは正確に 0/失敗と採点)。同じ問題の他の反復は正常に正解した。続けて起きる問題ではなく、一回限りだった。この 1セルが low 行の入力トークン分散を大きくした。
  • コードトレース誤答 1件。 mr_15 の low 3回目の反復(r2)で、g("abc") の出力を「cba a」と返した — 正答は「cbaa」(反転した「cba」に先頭文字「a」を連結)だ。ジャッジは 0/失敗と採点した。これは安全フィルターとは関係のない、純粋な推論エラーだ。このセルと mr_05 の拒否が、low の通過率を 96.7%(58/60)にした 2件の失敗である。
  • 部分点 0件。 360セル全体でジャッジの score == 1 は一つもなかった。正答がはっきり出るように作っているので、“672 を出した” と “576 を出した” の間に中間はない。だから合格・不合格だけで見ても、結論は変わらない。

限界

どこまで信じられるか

この結果は、一つの多段階タスクセット、一つの価格スナップショット、特定のモデルと採点基準から出た小さな集計値です。数字そのものより、方法を持ち帰るほうが安全です。

  • 標本。 N=20 · R=3。この大きさでは、信頼区間や統計的有意性は主張しない。どちらが有利かという方向は堅いが、絶対値の大きさは小標本として見る。
  • 価格。 価格表は一つだけを基準にした。料金や課金方式が変われば、同じ原資料からコストを再計算する必要がある。
  • 採点。 採点は審判モデル(gpt-4o)が行った。審判に渡した指示のデジタル指紋(SHA-256)を採点 JSON に残した。あとで変わったか分かるようにするためだ。
  • 予想よりよく解けた余波。 gpt-4o の通過率(0.75)が予想(0.30–0.60)より大きく、ドル削減幅はその分小さくなった。だからこの実験では、gpt-4o 通過率にあまり揺れない PTU スループットで見るほうが安定している。

だから何をデフォルトにするか

多段階推論のデフォルトは gpt-5.2 effort=none である — PAYG でも PTU でも。none はいちばん安く、同時にいちばん良い。その上のどの努力度も、品質は変えずにコストと待ち時間だけを足す。より高い努力度は “追加品質を実際に買うとき” にだけ試す候補であり、この種類の仕事のデフォルトではない。
