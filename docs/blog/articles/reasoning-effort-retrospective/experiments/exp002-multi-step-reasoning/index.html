exp002 — Did reasoning effort pay off in multi-step reasoning?

By Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

This experiment was reasoning's turn to win. Twenty problems that require at least two steps to answer — the kind of place where every notch up in reasoning effort (reasoning_effort), the dial for how much the model mulls a question over before it answers, feels like it should make the answer safer.

That is what we pre-registered. gpt-4o would miss more than half (30–60% pass), and gpt-5.2 would clear 80% only by raising effort. Both predictions missed the mark. gpt-5.2 already scored full marks at the lowest effort, and gpt-4o did far better than expected.

This note retraces that day as design → inputs → artifacts → prediction vs. measurement → outliers → decision. Not just the numbers, but how we reached them and how to read them — so the next person wanders less on the same road.

Why read this

Do harder problems need more thinking?

In the previous note (01) the reasoning-effort dial spun for nothing. But that was on the easiest task. When a problem takes several steps to solve — when you have to hold an intermediate value and take one more step — it feels like the story should change. Here, wouldn’t every notch up make the answer safer?

It is a plausible expectation. So this time we picked a place where reasoning ought to win and tested the same dial. Problems that answer only after at least two steps — word problems with arithmetic, holding several constraints at once, date math. Here we test whether the received wisdom that ‘hard work needs more thinking’ actually earns its bill.

If your service handles problems that don’t finish in one pass — combining conditions, chaining intermediate values, following logic — this is your case. Should you raise the dial, or is there a cheaper, faster road? The two ways our prediction missed answer that for you.

Design

It was reasoning's turn to win

Why measure the hard side now? In the note just before (01), thinking harder on the easiest task didn’t make the answers any better. That raises a question — is the reasoning dial just decoration that always costs money? It can’t be. Some problems plainly don’t answer in one pass; you have to hold an intermediate result and take one more step to reach the answer. If reasoning is wasted even there, the dial really is useless; if it pays there, that is where ‘when should I turn it up’ gets decided. That is what we wanted to see, so this time we picked the hard side.

So we set the opposite hypothesis. It reads: on problems that take at least two steps, raising reasoning effort lifts accuracy enough to earn its cost. And the baseline model with no reasoning setting hits a ceiling here that it cannot cross. This hypothesis, too, carries a line that says ‘if this happens, I was wrong.’ If accuracy stays flat as effort rises, or the baseline keeps pace to the end, the hypothesis breaks on the spot. If accuracy climbs clearly and the baseline runs into a wall it can’t pass, it holds. We built this experiment to settle that by measurement, not by guessing.

Why this note is the ‘ceiling.’ If 01 pinned down, by measurement, the floor where reasoning doesn’t pay, this note pins the opposite end — the ceiling where reasoning pays most. Only with both floor and ceiling standing can the tool note that follows (03) be placed somewhere in between. That is why, in the series, this note takes reasoning’s turn to win.

We boiled the question down to one. The task requires at least two steps to answer. Across the three benchmarks, this is where reasoning is most likely to pay. So here: if we give gpt-5.2 more thinking power (reasoning effort), do the answers get better, and does the improvement justify the bill? There are only two things to check. As effort rises, does (1) quality go up, and (2) cost go up? We read cost two ways. Under pay-as-you-go pricing (PAYG), ‘dollars per correct answer’; under the provisioned throughput unit (PTU) model, where you rent capacity in advance, ‘how many you get right per minute on the same capacity.’

What we measure with — the dataset. Twenty frozen synthetic samples (mr_01…mr_20). Arithmetic word problems, constraint satisfaction (following several conditions at once), date/time, causal chains, code tracing (reading the order a program runs in), boolean logic, counting — spread evenly across seven types. The key is that you can't answer at a glance. You have to hold an intermediate result and take one more step — say, feed a value you computed first back into a condition — to reach the answer. That is why it takes ‘at least two steps.’ Every sample has a machine-verifiable answer.

Only one thing changes. We move gpt-5.2's reasoning effort through five steps — none · low · medium · high · xhigh. Beside it we set gpt-4o, which has no reasoning-effort setting, as the baseline. For each problem-model-effort combination we ask three times (R=3).

Pre-registered prediction

The multi-step shape overturns the short-answer benchmark's conclusion. gpt-4o passes only 30–60%, and gpt-5.2 passes 80% or more at sufficient effort, so reasoning pays.

This experiment's role

Paired with the short-answer benchmark's floor (a place that needs no reasoning), this experiment anchors the ceiling of the cost surface where “reasoning is worth the bill.”

Inputs and artifacts

What it consumed, what it left behind

What this experiment consumed and what it left behind are not hand-written summaries but actual files in the repo. So you can trace it from input to output in a single line.

Input (in)

Dataset: benchmarks/02-multi-step-reasoning/dataset.json (pinned by SHA-256).
Prompts: the system and user templates are each fingerprinted by SHA-256 — guaranteeing a byte-identical prompt was used across all cells.

Artifacts (out)

The measurement surface is 360 cells (gpt-4o 60 + gpt-5.2 300, five effort steps). Cells excluded as outliers: 0. Grading was one pass per cell by the neutral judge gpt-4o, 360/360 successful (0 failures, 0 retries). The judge gives 0 for a miss, 1 for a partial pass, and 2 for a full pass — so a mean of 2.00 means all 60 passed, while gpt-4o's 1.50 is the average of 45 passes and 15 misses. Every JSON is a real Foundry v1 call with not one "fixture": true marker (159 of the 360 rows have reasoning_tokens > 0).

Prediction vs. measurement

The prediction missed twice

What we predicted

gpt-4o breaks down at 30–60%. gpt-5.2 clears 80% only by raising effort. In short: “higher effort buys quality and justifies the cost.”

What came out

gpt-4o was stronger than expected at 75% (45/60). gpt-5.2 was already 100% at the lowest none (60/60). By mean rating score, gpt-4o 1.50 vs. gpt-5.2 2.00.

Verdict: the prediction missed. We had predicted that “in multi-step you must raise effort to pay.” It was wrong in two places. gpt-4o solved more than expected. And gpt-5.2 was already at full marks before effort was raised at all. So the real fork was not the effort dial but swapping gpt-4o for gpt-5.2. gpt-5.2 was already enough on its default setting (none), with reasoning off.

First reversal

Swap the model and quality rose while cost fell

The dollars in the table below apply the methodology's PAYG formula to the price snapshot pricing/azure-openai-payg-2026-05.yaml (accessed 2026-05-19); they are re-cited from analysis.md §5.

Model     Effort   Per 1,000 req   Pass rate       Per 1,000 correct
gpt-4o    —        $0.80           75.0% (45/60)   $1.06   ← baseline
gpt-5.2   none     $0.62           100%  (60/60)   $0.62   ← Pareto-optimal
gpt-5.2   low      $0.86           96.7% (58/60)   $0.89
gpt-5.2   medium   $1.08           100%  (60/60)   $1.08
gpt-5.2   high     $1.25           100%  (60/60)   $1.25
gpt-5.2   xhigh    $2.18           100%  (60/60)   $2.18

Read this table on the same basis (per 1,000) as the narrative essay. Swap the model and quality rose while cost actually fell. Per 1,000 correct, none at $0.62 is 42% cheaper than gpt-4o ($1.06).

low costs 7.6% more per request. But its higher pass rate (96.7% vs. 75%) makes up that premium, so per 1,000 correct it is 16% cheaper than gpt-4o. So the first optimization was not to raise effort. It was to treat model and effort as one bundle and pick the cheapest point that clears the passing bar.

Second reversal

Higher effort bought the same quality at a higher price

Here the second fact surfaces. gpt-5.2's none and xhigh are equal in quality — both full marks (mean 2.00, 100% pass rate). Yet the cost per 1,000 correct rises from the none floor ($0.62) to 1.75× at medium, 2.02× at high, and 3.53× at xhigh ($2.18). You buy the same answer at a steadily higher price.

The waiting time tells the same story. none takes about 1.6 seconds per call (1,589ms), xhigh about 3.3 seconds (3,265ms). Next to gpt-4o (1,382ms), none is only about 15% slower, but xhigh is 2.4× slower. In this band, higher effort did not buy a better answer. It only bought the same answer more expensively and more slowly.

Break down the tokens and the reason is clear. Just as a kitchen that spends longer prepping runs up the cost even when the same dish reaches the table, an answer that looks identical still costs more when the model computed more under the hood. The visible answer is about 5.8 tokens at none and about 7.7 at xhigh — barely two tokens more. Yet the hidden reasoning tokens swell from 0 to about 109.5, and at xhigh reasoning alone accounts for about 26% of the request size. Quality stays the same while only the billed tokens balloon.

This does not mean reasoning tokens are useless. Reasoning pays only when there are still steps left to work through — like planning something complex or choosing among tools. It's just that this set of problems already reached the top score at the lowest setting. There is no score left to gain. Once you've hit the ceiling, the extra reasoning tokens you burn by raising effort become waste, not investment. In short, the effort dial is a switch you flip ‘only when there is quality still left to climb.’

Seen through PTU, the conclusion is the same. gpt-5.2 none runs at 0.994× gpt-4o's throughput and passes 100%, so on the same PTU spend it gets +32.5% more correct answers per minute (gpt-4o is 75%). Raising effort only trims throughput, with no gain in quality.

Quality map

Where did gpt-4o break down

gpt-4o's single number, 75%, doesn't show “where” it went wrong. So we split the score by task type. The failures clustered in one place: the types where you have to compute backward or trace the order in reverse.

  • Where it missed most: arithmetic word problems (mean 1.20), date/time (1.00), code tracing (1.33), constraint satisfaction (1.33) — the types where you compute backward or trace the order in reverse.
  • Where it got them all: counting, boolean logic, causal chains (2.00 each) — the types where reading once from front to back is enough.
  • gpt-5.2 earns full marks (2.00) across every type at every effort except low. Only low has two zero cells — mr_05 (constraint satisfaction), a safety-filter refusal, and mr_15 (code tracing), a wrong answer “cba a” (correct: “cbaa”). So those two types score 1.78 (±0.67) each at low.

In other words, for gpt-4o this problem set draws a map: pass when the steps are short and go forward, fail when you must trace back. gpt-5.2 flattened that map entirely — it got them right everywhere.

Transparency

Even the smudges left on the numbers, as they are

No measurement is perfectly clean. We write down the marks this benchmark left without erasing them — because hiding them would trip up the next person at the same spot.

  • gpt-4o was easier than expected. 75% exceeded the pre-registered 30–60%. It means the dataset was less harsh on gpt-4o to begin with. So the size of the “savings vs. gpt-4o” came out smaller than it would have on a harder dataset (expected 1.7–3.3× gap → realized 1.7×). Rather than erasing where the prediction missed to fit the numbers, we leave the shrunken savings as they are. The direction of the conclusion (gpt-5.2 none wins on both cost and quality) is unchanged.
  • One safety-filter refusal. On mr_05's first low repetition, the Azure content filter blocked the request. Input and output tokens were 0, and it returned a refusal in the fixed format. This cell shows no operational flag (cold start, retry, truncation), so it is not something to drop as an outlier. We left it in the aggregate without overwriting it (the judge scored it 0/fail). Other repetitions of the same problem answered correctly. It was a one-off, not a recurring problem, and this single cell is what widened the low row's input-token spread.
  • One code-trace wrong answer. On mr_15's third low repetition (r2), the model returned “cba a” for the output of g("abc") — the correct answer is “cbaa” (reversed “cba” plus the first character “a”). The judge scored it 0/fail; this is a pure reasoning error, unrelated to the safety filter. This cell and the mr_05 refusal are the two failures that make the low pass rate 96.7% (58/60).
  • Zero partial scores. Across all 360 cells, not one score of 1 (partial pass) occurred. With answers designed to land exactly, there is no middle ground between “672” and “576.” So even reading the scores as just pass/fail, the conclusion doesn't change.

Limits

How far can you trust this

These results are small-sample aggregates from one set of multi-step problems, one price sheet, and a particular model and scoring setup. So it is safer to take the method than the numbers themselves.

  • Sample. Twenty problems asked three times each (N=20 · R=3). At this size we claim no confidence intervals or statistical significance. The direction (which side is better) is solid, but treat the absolute magnitudes as small-sample.
  • Price. One price sheet as the basis. If rates or the billing model change, cost must be recomputed from the same raw data.
  • Grading. A judge model (gpt-4o) did the scoring. We kept the digital fingerprint (SHA-256) of the judge's instructions in the grading records, so we can tell later if they changed.
  • Fallout from beating the prediction. Because gpt-4o did better than expected (pass rate 0.75 vs. an expected 0.30–0.60), the dollar savings shrank accordingly. So for this experiment, the steadier view is PTU throughput, which is less swayed by gpt-4o's pass rate.

So what becomes the default

The default for multi-step reasoning is gpt-5.2 effort=none — in PAYG and in PTU alike. none is at once the cheapest and the best. Any effort above it leaves quality unchanged while adding only cost and delay. Higher effort is only a candidate to try “when it actually buys extra quality,” not the default for this kind of task.
