exp004 — 先回りするスピルオーバーは割に合ったのか

執筆 Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

前の三つのベンチマークは、どれも “推論強度の設定をどこまで上げるか” の話でした。今回は軸を変え、推論強度ではなくデプロイを扱います。この実験は、PTU(固定容量)デプロイが飽和に近づく状況をシミュレートします。トラフィックの一部を予備経路へ逃がす二つのスピルオーバーポリシーを、同じ負荷で比較しました。

私たちは事前登録した予測を残していました。遅延が上がる気配を見て先回りする(proactive)ポリシーは、タイムアウトや 429 が起きてから逃がす事後対応(reactive)ポリシーより、飽和区間でのキャッシュ低下が小さいはずだと予測しました。早めに手を打つほうがよい、という自然な直感です。

実測は、その直感と異なる結果を示しました。飽和区間の定常状態キャッシュヒットは reactive 99.2337%, proactive 99.0680% — 先回りした側がむしろ 0.1657 pp 低い結果でした。しかも reactive は持続区間をずっとスピルオーバーで走った一方、proactive は一度も発動しませんでした。このノートでは、その 22分間を設計 → 入力 → 予測対実測 → 二つの曲線 → 判断としてたどります。exp001 が “易しい仕事では推論は割に合わない” だったように、ここでは “この条件では賢いポリシーは有効ではありません”という結果です。

なぜ読むのか

PTU が飽和に近づくと何が起きるのか

固定容量(PTU)でモデルをデプロイすると、トラフィックがその容量上限に近づく瞬間が訪れます。そこでプロンプトキャッシュが揺らぐと、固定料金そのものは変わらなくても、同じプレフィックスの再計算が容量の余裕を消費し、レイテンシとスループットを悪化させます。

その揺らぎに対する緩衝材がスピルオーバーです。あふれそうな場合は、トラフィックの一部を予備経路へ逃がします。方法は二つあります。事後対応(reactive)はタイムアウトや 429 が出てから逃がし、先回り(proactive)は p95 遅延が徐々に上がる兆候を見て、早めに少しずつ逃がします。

PTU デプロイを運用していて、トラフィックが飽和にたびたび触れるなら、このノートは関連するポリシー上の問いを検証します。その答えは、単一エンドポイントの従量課金(ペイアズユーゴー)シミュレーション内で測っており、ライブの PTU 容量そのもので測ったものではありません。そしてその答えは、おそらく予想と異なります。

設計

今回は推論強度ではなくデプロイです

なぜこれを測ったのか。 前の三つのノートでは、推論強度をどこまで上げるかを検討しました。推論強度を決めると、次の壁が訪れます。その設定にトラフィックが集まったとき、デプロイが持つのかです。シミュレートした PTU パターンでは、飽和近傍でプロンプトキャッシュが不安定になることがあり、スピルオーバーがその緩衝材になります。“先回りするポリシーは事後対応よりよい”という一般的な直感が正しいかを、推測ではなく実測で確かめました。

そこで、‘先回りのほうがよい’という仮説を立てました。 文にすると次のとおりです — 持続的な飽和負荷では、先回りする(proactive)ポリシーは事後対応(reactive)より、飽和区間のキャッシュヒット低下が小さいと予測しました。 この仮説には判定条件も設けました。proactive が飽和キャッシュで reactive をはっきり上回れば ‘先回りがよい’ は支持されます。勝てないか、むしろ低ければ、少なくともこの条件ではその直感は有効ではないと判断します。

原因究明ではなく、緩和策の比較です。 “スピルオーバー自体がキャッシュ低下の根本原因だ” という強い主張は、すでに現場観察で弱まっていました。だからこの実験は原因を掘る場ではありません。二つの緩和ポリシーのうち、どちらがよいかだけを競わせる場です。検証範囲を絞ったため、得られる結論も限定的ですが明確です。

なぜシミュレーションから始めるのか。 Phase 1 では、gpt-5.2 デプロイ一つの上でスピルオーバー状態だけを内部的に模擬します。物理的に分かれたキャッシュプールではありません。そのため、絶対値ではなくポリシー間の差の向きを確認します。プライマリ/予備のキャッシュプールが本当に分かれる 2デプロイ負荷テストは Phase 2 の仕事です。このノートは、その基準値を先に確認します。

問いは一つです。 持続的な飽和近傍の ReAct 負荷で、先回りするスピルオーバーは事後対応よりキャッシュを守るのか。

設計(負荷)。 同じ 22分の負荷を、二つのポリシーに同じように流しました(原資料ラベルでは 22-min / 2-min / 10-min / 10-min) — ウォームアップ 2-min(0.3 リクエスト毎秒) → ランプ 10-min(0.5→2.5 リクエスト毎秒) → 持続 10-min(2.0 リクエスト毎秒)。gpt-5.2 の 1デプロイ、effort=low、約 30K tokens のシステムプロンプト(二つの実行がバイトまで同一になるよう SHA-256 で固定、corpus_seed 4242)。内部スロットルしきい値は 90,000 TPM。各ポリシーで 2,136 リクエスト(warmup 36 / ramp 900 / sustain 1,200)を実行しました。

変える軸は一つだけ — policy.type を reactive と proactive で切り替える。プロンプト·負荷·モデル·推論強度·しきい値はすべて固定なので、二つの成果物の差はポリシーだけに起因します。

事前登録予測

先回りする(proactive)ポリシーは飽和区間のキャッシュ低下が小さく、事後対応(reactive)より定常状態キャッシュヒットが高いはずです。

この実験の役割

推論強度を扱った三つの実験(01·02·03)のあと、決めた設定が飽和負荷で持つのかを確かめる最初の運用実験です。ただし、物理的なキャッシュ分離のない Phase 1 の基準値です。

予測対実測

予測は外れた

何を予測したか

先回りする(proactive)ポリシーは飽和区間のキャッシュ低下が小さいと予測しました。要するに、“先回りは事後対応よりよい”という予測です。

何が出たか

飽和キャッシュヒットは reactive 99.2337% vs proactive 99.0680% — 先回りした側がむしろ 0.1657 pp 低い結果でした。しかも reactive は持続区間をずっとスピルオーバーで走った(99.9%)一方、proactive は一度も発動しませんでした(0%)。

判定: この条件では、先回りは割に合いませんでした。 事前登録した仮説(proactive 優位)は、この単一エンドポイントシミュレーターでは支えられませんでした。ただし差はとても小さく、技術的なものです。曲線がはっきり分かれたのではなく、proactive 側のキャッシュミス二件が平均を押し下げた結果です。exp001 で “易しい仕事では推論は割に合わない” と分かったように、ここでは “この条件では賢いポリシーは割に合わない”という結果でした。予測が外れた実験も、根拠として残します。

第一の合図

賢いポリシーは勝てませんでした

下の表は持続(sustain) 10分の定常状態です。負荷が目標に張りつき、仮説を検証する区間です。数値は公開済み集計 analysis.md §7 から再引用しています。

ポリシー     飽和時スピルオーバー   飽和時キャッシュヒット(分あたり平均 ± 標準偏差)   備考
reactive    99.9% 有効             99.2337%  (±0.0033%p)                        基準値 · 飽和区間を通してスピルオーバー

差(pro−re)    —                     −0.1657%p                                   実質的に横ばい、方向のみ逆

二つの曲線はどちらも 99.23% 付近でほぼ平らです。reactive は標準偏差 0.0033 pp と安定しており、proactive もほとんどの分(minute)で同程度でした。ただし持続区間のリクエスト 1307 と 1959の二件がキャッシュを外し(入力 21,153 トークンが全額課金)、該当する分に目立つ谷が生じました。これにより標準偏差が 1.2802 pp へ広がり、集計平均が押し下げられました。つまり proactive が継続的に負けたのではありません。二回のミスが数値の差を生みました。

全区間(ウォームアップ + ランプ + 持続)へ広げると、向きはむしろ反転します — reactive 99.0478% vs proactive 99.0942% で、proactive が 0.0464 pp 高い。どの窓で見ても、差はごくわずかです。

第二の合図

なぜ引き分けたのか — 片方は逃がす必要すらありませんでした

表面上、二つのポリシーは正反対に動いたにもかかわらず、結果はほぼ同じでした。ここがこの実験の核心です。reactive はウォームアップ最初のリクエストからスピルオーバーを発動し、持続区間のあいだずっと(99.9%)予備経路を使用しました。状態遷移五回はすべて reactive 側で発生しました — requests 1/91/92/1478/1479 であり、リクエスト 1 で介入し、91/92 のあたりで一瞬プライマリへ戻って再介入し、1478/1479 で持続中にもう一度切り替わりました。対して proactive は p95 遅延がしきい値を超えず、スピルオーバーを一度も発動しませんでした(0%)。逃がす必要がなかったためです。

それでもキャッシュはほぼ同じでした。 理由は設計にあります。Phase 1 は一つのデプロイ上で、スピルオーバーを状態ラベルとして模擬するだけです。プライマリ経路でも予備経路でも、見ているのは同じキャッシュです。そのため、“どの経路に送ったか”はキャッシュヒットにほとんど反映されません。実際、キャッシュ済みトークンは二つのポリシーで正確に 44,733,952 と同じでした。

遅延·費用·処理量も引き分けです。 持続 TTFT は proactive のほうがむしろ少し速い(p50 7,620.9ms 対 8,490.6ms、p95 12,107.8ms 対 13,617.5ms)。しかしこれは事前登録したキャッシュ指標ではなく、予備経路に乗らなかった proactive の遅延分布が狭かったという副次的な観察です。全区間費用は reactive $17.883347 vs proactive $17.924671 — proactive が $0.041324 高くなりました。総トークンは proactive のほうが少し少ないのに(45,812,897 対 45,828,455)高いのは、出力·推論トークンの比率が少し高かったためです。PTU トークン圧力に換算した処理量利得係数は 1.000340× — 事実上平らです。

まとめると: 二つのポリシーは正反対に振る舞いましたが、共有キャッシュの上ではその差がキャッシュ·費用·処理量のどこにも明確な差としては刻まれませんでした。この条件では、複雑なポリシーによる費用差は現れませんでした。

透明性

数値に残る不規則なデータもそのまま示します

どんな測定も完全にきれいではありません。この実験が残した跡を、消さずにそのまま記録します。隠すと、次の人が同じ場所でつまずくためです。

  • 除外した外れ値 0件。 外れ値規則は、持続区間でレイテンシが平均+3σを超え、同時に実 429·リトライ·経路遷移·スピルオーバー介入のようなログイベントが重なった場合にのみ除外します。候補は reactive 1件·proactive 8件ありましたが、どれもそのログイベントと重ならなかったため、すべて残しました。
  • 残した異常行 5件。 reactive に 0トークンの持続行 1件(リクエスト 1276)、proactive に 0トークン行 2件(1306·1934)とキャッシュミス行 2件(1307·1959)があります。除外規則を満たさないため生データのまま集計に含めました。proactive の低い持続平均は、まさにこのキャッシュミス二件から来た。隠しません。
  • 見出しは持続定常状態です。 ランプ·ウォームアップの過渡期を混ぜるとポリシー効果がぼやけるため、仮説を検証する持続 10分を代表値にしました。全区間の数字も §7 に併記し、どの窓でも差がごく小さいことを確認できるようにしています。

限界

どこまで信じられるか

この結果は、単一エンドポイントシミュレーター、一つの負荷プロファイル、一回の実行から出た小さな比較値です。数字そのものより、方法と向きを持ち帰るほうが安全です。

  • スピルオーバーはシミュレーションです。 プライマリ/予備経路は一つのデプロイ上のルーティングラベルにすぎず、物理的に分かれたキャッシュプールではありません。だから絶対キャッシュ値は実際の 2デプロイ環境へそのまま移らない — ポリシー間の差の向きだけを読むべきです。
  • Phase 1 の基準値。 このシミュレーターはポリシー層だけを切り出して見る場所です。物理的に分離されたキャッシュプールでの高忠実度の再測定は Phase 2 で扱います。容量·費用計画にこの数値を使う前に、Phase 2 を先に確認する必要があります。
  • 負荷と標本。 22分の一回、ポリシーごとに 2,136 リクエスト。この数値では信頼区間や統計的有意性は主張しません。方向性は明確ですが、絶対値は小標本として慎重に扱ってください。
  • 実際の 429 は 0。 スロットルは内部しきい値(90,000 TPM)でまねた。実 429 が混ざる環境では、違う動きをする可能性があります。
  • 課金は PAYG スナップショット。 処理量はトークンで計算した推定であり、実際の PTU スロットルーティングや PTU 課金をモデル化していない。

だから何をデフォルトにするか

現時点の根拠では、複雑な先回り(proactive)スピルオーバーを導入する理由はない。この単一エンドポイント条件では、先回りは事後対応よりキャッシュを守れず(−0.1657 pp)、費用も少し高かった(+$0.041324)。差はごくわずかで、共有キャッシュ設計に縛られている。だから単純な事後対応(reactive)で十分です。最終的な判定は、プライマリ/予備キャッシュプールが物理的に分かれる環境で、Phase 2 が下す。

つなぐ

次の人が迷いにくいように

  • 回顧本文 → ハブの 次の判断 · 次の実験が予告した “live PTU 負荷テスト”。Phase 1 は、トークンベースの PTU 推定の後に、そのパターンを従量課金(ペイアズユーゴー)で実測したシミュレーションです。

  • 原資料 → 二つのポリシー定義は experiments/exp004_spillover_*.yaml、分析は benchmarks/04-spillover-simulation/analysis.md にある。
