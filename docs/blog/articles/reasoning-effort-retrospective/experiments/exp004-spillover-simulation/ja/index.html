exp004 — スピルオーバーは先回りすれば割に合ったのか

文 Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

前の三つのベンチマークは、どれも “推論努力度のつまみをどこまで上げるか” の話だった。今回は軸が変わる。モデルではなく、デプロイである。PTU(固定容量)デプロイが飽和に近づくとき、トラフィックの一部を予備経路へ逃がすスピルオーバーポリシー二つを、同じ負荷で競わせた。

私たちは予測を事前に書いておいた。遅延が上がる気配を見て先回りする(proactive)ポリシーは、タイムアウトや 429 が起きてから逃がす事後対応(reactive)ポリシーより、飽和区間でのキャッシュ低下が小さいはずだ。誰もが抱く直感である。早めに手を打つほうがよいはずだ、と。

測定は、その直感を静かにひっくり返した。飽和区間の定常状態キャッシュヒットは reactive 99.2337%, proactive 99.0680% — 先回りした側がむしろ 0.1657 pp 低かった。しかも reactive は持続区間をずっとスピルオーバーで走った一方、proactive は一度も発動しなかった。このノートでは、その 22分を設計 → 入力 → 予測対実測 → 二つの曲線 → 判断としてたどる。exp001 が “易しい仕事では推論は割に合わない” だったように、ここでは “この条件では賢いポリシーは割に合わない” である。

なぜ読むのか

PTU が飽和に近づくと何が起きるのか

固定容量(PTU)でモデルをデプロイすると、トラフィックがその容量上限に近づく瞬間が来る。そこでプロンプトキャッシュが揺らぐと、応答は遅くなり、費用も漏れる。同じプロンプトをもう一度計算するぶん、請求が増えるからだ。

その揺らぎに対する緩衝材がスピルオーバーである。あふれそうなら、トラフィックの一部を予備経路へ逃がす。やり方は二つある。事後対応(reactive)はタイムアウトや 429 が出てから逃がす。先回り(proactive)は p95 遅延がじわじわ上がる気配を見て、早めに少しずつ逃がす。

PTU デプロイを運用していて、トラフィックが飽和にたびたび触れるなら、このノートは近い。“より賢いポリシーを入れれば、キャッシュをもっと守れるのか?” という、運用者なら一度は持つ問いに、この実験は一つの実測の答えを返す。そしてその答えは、おそらく予想と違う。

読む順序 — 正直な結論を先に、メカニズムはその次: 今回は努力度ではなくデプロイである 予測は外れた 賢いポリシーは勝たなかった なぜ引き分けたのか — 片方は逃がす必要すらなかった どこまで信じられるか だから何をデフォルトにするか

設計

今回は努力度ではなくデプロイである

なぜこれを測ったのか。 前の三つのノートは、推論努力度をどこまで上げるかを問うていた。だが努力度を決めると、次の壁が来る。その設定にトラフィックが集まったとき、デプロイが持つのかである。PTU デプロイが飽和に近づくとプロンプトキャッシュが揺らぐことがあり、その緩衝材がスピルオーバーだ。よくある直感は “先回りするポリシーは事後対応よりよい” だが、本当にそうかを勘ではなく実測で切り分けたかった。

だから ‘先回りのほうがよい’ を仮説にした。 文にするとこうだ — 持続的な飽和負荷では、先回りする(proactive)ポリシーは事後対応(reactive)より、飽和区間のキャッシュヒット低下が小さい。 この仮説にも壊れる線がある。proactive が飽和キャッシュで reactive をはっきり上回れば ‘先回りがよい’ は支えられる。勝てないか、むしろ低ければ、少なくともこの条件ではその直感は割に合わない。

原因究明ではなく、緩和策の比較である。 “スピルオーバー自体がキャッシュ低下の根本原因だ” という強い主張は、すでに現場観察で弱くなっていた。だからこの実験は原因を掘る場ではない。二つの緩和ポリシーのうち、どちらがよいかだけを競わせる場である。野心を狭めたぶん、答えも狭く、はっきりしている。

なぜシミュレーションから始めるのか。 Phase 1 は gpt-5.2 デプロイ一つの上で、スピルオーバー状態だけを内部的にまねる。物理的に分かれたキャッシュプールではない。だから絶対値ではなく、ポリシー間の差の向きを見る。プライマリ/予備のキャッシュプールが本当に分かれる 2デプロイ負荷テストは Phase 2 の仕事である。このノートは、その床を先に作る。

問いは一つだ。 持続的な飽和近傍の ReAct 負荷で、先回りするスピルオーバーは事後対応よりキャッシュを守るのか。

設計(負荷)。 同じ 22分の負荷を、二つのポリシーに同じように流す(原資料ラベルでは 22-min / 2-min / 10-min / 10-min) — ウォームアップ 2-min(0.3 TPS) → ランプ 10-min(0.5→2.5 TPS) → 持続 10-min(2.0 TPS)。gpt-5.2 の 1デプロイ、effort=low、約 30K tokens のシステムプロンプト(二つの実行がバイトまで同一になるよう SHA-256 で固定、corpus_seed 4242)。内部スロットルしきい値は 90,000 TPM。各ポリシーが 2,136 リクエスト(warmup 36 / ramp 900 / sustain 1,200)を走らせる。

変える軸は一つだけ — policy.type を reactive と proactive で切り替える。プロンプト·負荷·モデル·努力度·しきい値はすべて固定なので、二つの成果物の差はポリシーだけから来る。

事前登録予測

先回りする(proactive)ポリシーは飽和区間のキャッシュ低下が小さく、事後対応(reactive)より定常状態キャッシュヒットが高いはずである。

この実験の役割

努力度三部作(01·02·03)のあと、決めた設定が飽和負荷で持つのかを確かめる最初の運用実験。ただし、物理的なキャッシュ分離のない Phase 1 の床である。

予測対実測

予測は外れた

何を予測したか

先回りする(proactive)ポリシーは飽和区間のキャッシュ低下が小さい。要するに、“先回りは事後対応よりよい” である。

何が出たか

飽和キャッシュヒットは reactive 99.2337% vs proactive 99.0680% — 先回りした側がむしろ 0.1657 pp 低かった。しかも reactive は持続区間をずっとスピルオーバーで走った(99.9%)一方、proactive は一度も発動しなかった(0%)。

判定: この条件では、先回りは割に合わなかった。 事前登録した仮説(proactive 優位)は、この単一エンドポイントシミュレーターでは支えられなかった。ただし差はとても小さく、技術的なものだ。曲線がはっきり分かれたのではなく、proactive 側のキャッシュミス二件が平均を押し下げた結果である。exp001 で “易しい仕事では推論は割に合わない” と分かったように、ここでは “この条件では賢いポリシーは割に合わない”。予測が外れた実験も、根拠として残す。

第一の合図

賢いポリシーは勝たなかった

정책        포화 스필오버   포화 캐시 히트(분당 평균 ± 표준편차)   비고

二つの曲線はどちらも 99.23% 付近でほぼ平らである。reactive は標準偏差 0.0033 pp で岩のように安定し、proactive もほとんどの分(minute)で同じ高さにいる。ただし持続区間のリクエスト 1307 と 1959の二件がキャッシュを外し(入力 21,153 トークンが全額課金)、その分に目立つ谷を作った。これが標準偏差を 1.2802 pp へ膨らませ、集計平均を下へ引いた。つまり proactive が継続的に負けたのではない。ちょうど二回のミスが数字を分けた。

全区間(ウォームアップ + ランプ + 持続)へ広げると、向きはむしろ反転する — reactive 99.0478% vs proactive 99.0942% で、proactive が 0.0464 pp 高い。どの窓で見ても、差は爪の先ほどである。

第二の合図

なぜ引き分けたのか — 片方は逃がす必要すらなかった

表面上、二つのポリシーは正反対に動いたのに、結果は同じ場所へ着地した。ここがこの実験の核心である。reactive はウォームアップ最初のリクエストからスピルオーバーを発動し、持続区間のあいだずっと(99.9%)予備経路にいた。状態遷移五回はすべて reactive 側で起きた — requests 1/91/92/1478/1479 であり、リクエスト 1 で介入し、91/92 のあたりで一瞬プライマリへ戻って再介入し、1478/1479 で持続中にもう一度切り替わった。対して proactive は p95 遅延がしきい値を超えず、スピルオーバーを一度も発動しなかった(0%)。逃がす必要がなかったのである。

それでもキャッシュはほぼ同じだった。 理由は設計にある。Phase 1 は一つのデプロイ上で、スピルオーバーを状態ラベルとしてまねるだけだ。プライマリ経路でも予備経路でも、見ているのは同じキャッシュである。だから “どの経路に送ったか” はキャッシュヒットにほとんど刻まれない。実際、キャッシュ済みトークンは二つのポリシーで正確に 44,733,952 と同じだった。

遅延·費用·処理量も引き分けである。 持続 TTFT は proactive のほうがむしろ少し速い(p50 7,620.9ms 対 8,490.6ms、p95 12,107.8ms 対 13,617.5ms)。しかしこれは事前登録したキャッシュ指標ではなく、予備経路に乗らなかった proactive の遅延分布が狭かったという副次観察に近い。全区間費用は reactive $17.883347 vs proactive $17.924671 — proactive が $0.041324 高い。総トークンは proactive のほうが少し少ないのに(45,812,897 対 45,828,455)高いのは、出力·推論トークンの比率が少し高かったためだ。PTU トークン圧力に換算した処理量利得係数は 1.000340× — 事実上平らである。

まとめると: 二つのポリシーは正反対に振る舞ったが、共有キャッシュの上ではその差がキャッシュ·費用·処理量のどこにも意味のある形では刻まれなかった。この条件では、ポリシーを賢くした代金は請求書に現れなかった。

透明性

数字に残った汚れまでそのまま

どんな測定も完全にきれいではない。この実験が残した跡を、消さずにそのまま書いておく。隠すと、次の人が同じ場所でつまずくからだ。

  • 除外した外れ値 0件。 外れ値規則は、持続区間でレイテンシが平均+3σを超え、同時に実 429·リトライ·経路遷移·スピルオーバー介入のようなログイベントが重なったときだけ除外する。候補は reactive 1件·proactive 8件あったが、どれもそのログイベントと重ならなかったため、全て残した。
  • 残した異常行 5件。 reactive に 0トークンの持続行 1件(リクエスト 1276)、proactive に 0トークン行 2件(1306·1934)とキャッシュミス行 2件(1307·1959)がある。除外規則を満たさないため生データのまま集計に入れた。proactive の低い持続平均は、まさにこのキャッシュミス二件から来た。隠さない。
  • 見出しは持続定常状態である。 ランプ·ウォームアップの過渡期を混ぜるとポリシー効果がぼやけるため、仮説が生きる持続 10分を代表値にした。全区間の数字も §7 に併記し、どの窓でも差が爪の先ほどだと確認できるようにした。

限界

どこまで信じられるか

この結果は、単一エンドポイントシミュレーター、一つの負荷プロファイル、一回の実行から出た小さな比較値である。数字そのものより、方法と向きを持ち帰るほうが安全である。

  • スピルオーバーはシミュレーションである。 プライマリ/予備経路は一つのデプロイ上のルーティングラベルにすぎず、物理的に分かれたキャッシュプールではない。だから絶対キャッシュ値は本物の 2デプロイ環境へそのまま移らない — ポリシー間の差の向きだけを読むべきである。
  • Phase 1 の床。 このシミュレーターはポリシー層だけを切り出して見る場所である。物理的に分離されたキャッシュプールでの高忠実度の再測定は Phase 2 の仕事だ。容量·費用計画にこの大きさを使う前に、Phase 2 を先に見る必要がある。
  • 負荷と標本。 22分の一回、ポリシーごとに 2,136 リクエスト。この大きさでは信頼区間や統計的有意性は主張しない。向きは堅いが、絶対値は小標本として注意する。
  • 実際の 429 は 0。 スロットルは内部しきい値(90,000 TPM)でまねた。実 429 が混ざる環境では、違う動きをする可能性がある。
  • 課金は PAYG スナップショット。 処理量はトークンで計算した推定であり、実際の PTU スロットルーティングや PTU 課金をモデル化していない。

だから何をデフォルトにするか

現時点の根拠では、複雑な先回り(proactive)スピルオーバーを導入する理由はない。この単一エンドポイント条件では、先回りは事後対応よりキャッシュを守れず(−0.1657 pp)、費用も少し高かった(+$0.041324)。差は爪の先ほどで、共有キャッシュ設計に縛られている。だから単純な事後対応(reactive)で十分である。本当の審判は、プライマリ/予備キャッシュプールが物理的に分かれる環境で、Phase 2 が下す。

つなぐ

次の人が迷いにくいように

  • 回顧本文 → ハブの 次の判断 · 次の実験が予告した “live PTU 負荷テスト” が、この実験である。トークンベースの PTU 推定の後に来た、最初の実測負荷結果。
  • 予告したノート → exp003 — ツールエージェントは最後に “次はライブ検索と実際の PTU 負荷テスト” と書いた。このノートが、その負荷テストの Phase 1 である。
  • 原資料 → 二つのポリシー定義は experiments/exp004_spillover_*.yaml、分析は benchmarks/04-spillover-simulation/analysis.md にある。

次の実験。 Phase 1 は一つのデプロイ上でスピルオーバーをまねた。次は物理的に分離された二つのデプロイに実際の TPM スロットルをかけ、同じ負荷を流す高忠実度の再測定である。プライマリ/予備キャッシュプールが本当に分かれたときも、ポリシー差はなお爪の先ほどなのかを見る。
