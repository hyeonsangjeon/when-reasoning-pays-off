実験回顧 · 三つのタスク形状を横断して · 視点: task-shape

推論努力度は割に合うのか — 仮説、そして測定がひっくり返したこと

文 Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

私たちは、多段階推論なら高い推論努力度(reasoning_effort)が割に合うはずだと事前登録した。三つのベンチマークにわたり 1,080 セルを測定した結果は、その予測をひっくり返した。短い事実回答でも、多段階でも、ツールエージェントでも、答えは一度も high や xhigh ではなかった。努力度を中間より上に上げると、品質は変わらないまま、コストだけが上がり、スループットだけが落ちた。本稿はその道のりを物語としてたどる回顧である。「何を予想し、何が外れ、だから何をデフォルトにしたのか」を時間順(タイムライン)と問い順(問いごとの回顧)でたどる。結論だけでなく歩いてきた道まで残す。そして最後ではなく今すぐ、コマンド一行で直接再現できる。

なぜ読むのか

そのつまみ、いつ上げるべきか

最近のモデルには 推論努力度 というつまみがある。答えを出す前に、モデルが内側でどれだけ考え込むかを決める値だ。上げるほど賢くなりそうで、迷うとつい高めに置きたくなる。でもつまみを上げれば、答えが良くなるかどうかに関係なく、お金と時間は確実に増える。 だから ‘とりあえず上げておく’ という癖は、毎月の請求書だけを大きくしかねない。

この回顧は、そのつまみが いつ費用に見合い、いつムダになるのか を、勘ではなく実測で切り分ける。仕事を性質で三つに分けて扱った — 一度で終わる 短い事実回答、段階を踏む 多段階、道具を呼ぶ ツールエージェント。あなたのサービスがやることも、たいていこの三つのどれかに入る。

モデルと努力度を選んで本番に載せる人なら、ここから デフォルトの決め方 を持ち帰れる。方法は単純だ — まず品質の 合格線 を決め、その線を越えた設定の中から最も安く速いものを選ぶ。その規則が三つの実験でどう同じ結論に集まったのかを、予測と反転をたどりながら下で一つずつ見せる。

問い

新しい本番タスクで、推論努力度を上げることは割に合うのか。それも PAYG(ドル当たりの正答)と PTU(固定容量当たりの分当たり正答)の両方の視点で。

根拠

三つのベンチマーク — 01 短い事実回答(Null) · 02 多段階(Ceiling) · 03 ツールエージェント(Mixed) — をそれぞれ N=20 サンプル × R=3 反復、努力度 {none, low, medium, high, xhigh} + gpt-4o ベースラインで測定。合計 1,080セル。すべてのコストは 1,000件当たりに正規化し、ベンチマークごとの analysis.md を再引用します。

判断

最適な (モデル, 努力度) はタスク形状と消費モデルによって異なります。選び方は単純です。まず品質の合格線を決めます。その線を越えた設定の中から、最も安く速いものを選びます。すると共通の結論が見えてきます — 答えは決して high や xhigh ではない。 中間を超えると、品質は変わらないのにコストだけが増え、スループットだけが削られます。

この順に読んでください: タイムライン — いつ何が外れたのか 問いごとの回顧 — なぜ実験し、何を学んだのか 次の判断 · 次の実験

タイムライン

私たちが歩いた順序

実験は一度で結論に至ったわけではありません。下の五つの場面を日付順に追うと、予測がどこで外れ、デフォルトがどこで変わったのかが順に見えてきます。

  1. 2026年 5月以前 — 事前登録。 測定を始める前に、まず予測を書き留めておいた。多段階タスクなら、高い推論努力度が品質を引き上げ、コストを正当化するはずだと。あとから結果に合わせて物語を変えられないように、gpt-5.2 の努力度を none から xhigh まで五段階に固定し、gpt-4o ベースラインを横に置いた。この事前登録があったからこそ、後に続く ‘ひっくり返り’ には意味がある。
  2. 2026年 5月 — 短い事実回答ケース(01)、床を測る。 まず、推論を必要としない短い事実回答タスクでコスト曲面の床を確認した — 三つのベンチマークのうち、この床だけは実測で測り直した(360セルすべて実 Azure 呼び出し、フィクスチャマーカーなし)。gpt-5.2 は推論を一切有効にしない none で正答率がすでに 95% に飽和し、むしろ gpt-4o(90%) より高かった。正答 1,000件当たりのコストは $0.62 で gpt-4o($0.74) より 16% 安かった(リクエスト 1,000件当たりでも 12% 安い)。そのため短い事実回答の PAYG デフォルトは gpt-5.2 none にした — ただし固定容量(PTU)の視点では二つのモデルのスループットが約 1% 内で重なり、実質引き分けだった。この実験は exp001 実験ノートで一つずつ分解する。
  3. 2026年 5月 — 多段階ケース(02)、転換点。 ここで推論が勝つはずだった。ところが蓋を開けると、gpt-5.2 は何の推論も有効にしない基本状態(none)で二十問すべてを正解した。事前仮説はその場で崩れた。正答 1,000件当たりのコストは gpt-4o の $1.06 から $0.62 へ 42% 下がり、PTU では分当たり正答が 32.5% 増えたが、努力度をさらに上げても品質は動かなかった。だから多段階のデフォルトを gpt-5.2 none とし、努力度の引き上げは捨てた。勝負を分けたのは ‘努力度ダイヤル’ ではなく ‘モデルの入れ替え’ だった。この実験は exp002 実験ノートで一つずつ分解する。
  4. 2026年 5月 — ツールエージェントケース(03)、意外な発見。 最後はツールを使うエージェントだった(無ツール・1ツール・マルチツールの混合)。ここで驚かせたのは gpt-4o だった。‘一般知識で答えよ’ というプロンプトでも計算機を習慣のように呼び、無ツール通過率が 83.3% まで落ちたのである。一方 gpt-5.2 は low だけでマルチツール 100% を保ち、正答 1,000件当たり $2.77(gpt-4o $3.65 比 24% 安い) に到達した。だからツールのデフォルトは gpt-5.2 low。ただし low を超えると、スループットは medium で 8.5%、xhigh で 10.8% ずつ削られ、利得を戻してしまった。この実験は exp003 実験ノートで一つずつ分解する。
  5. 2026年 7月 — 根拠と再現のあいだの隙間を埋める。 測定が終わったあとに残った宿題は、性質が違っていた。‘デプロイへの関心は高いのに、README と検証層がその関心を受け止めきれていない’ というフィードバックが来た。実際、新しい訪問者は編集可能インストールの失敗(PEP 660)や壊れた実行コマンドで止まった。そこで資格情報なしに一行で終わる検証(verify_setup.sh)、実験ごとのガイドカード、requirements.txt の分離を加え、‘根拠’ と ‘再現’ のあいだの隙間を埋めた。このページ冒頭の 10秒再現がその結果である。

問いごとの回顧

なぜ実験し、何を学んだのか

同じ結果を、今度は問いから出発してみます。‘何が気になっていたのか’を先に置き、三つの問いに一つずつ答えます。

Q1 — 短い事実回答に推論は必要か?

最も単純な問いから。一度で答えが出る短い事実タスク(抽出·整形·分類·音訳·算術)なら、推論努力度は有効にする理由がないように見えた。この床を三つのベンチマークのうち唯一実測で測り直した — 360セルすべて実 Azure Foundry 呼び出し、フィクスチャマーカーなし、審判採点 360/360。

予測は反転せず、そのまま当たった。gpt-5.2 は推論を一切有効にしない none で正答率 95% にすでに飽和し、むしろ gpt-4o(90%) より高かった。正答 1,000件当たり $0.62 で gpt-4o($0.74) より 16% 安かった(リクエスト当たりでも 12% 安い)。努力度を xhigh まで上げても隠れた推論トークンは 0 近くにとどまり、品質もコストもほとんど動かなかった — 努力度ダイヤルがどこにも配線されていない場所である。だから短い事実回答のデフォルトは gpt-5.2 none。詳細な解剖は exp001 実験ノートにある。

Q2 — 多段階では努力度を上げると割に合うのか?

仮説は単純だった。複数の段階を通る必要がある問題なら、high や xhigh の品質向上がコスト増を正当化するだろう、というもの。これを確かめるため、gpt-5.2 の五つの努力度(none から xhigh まで)を gpt-4o ベースラインと並べ、二十問を三回ずつ繰り返して比較した。

結果は仮説をひっくり返した。gpt-5.2 は none で既に 100% 正解し、正答 1,000件当たり $0.62 で gpt-4o($1.06) より 42% 安く、PTU では分当たり正答が 32.5% 多かった。意外だったのは gpt-4o も予想よりよくできた点だ — 事前に書いた 30–60% の範囲を超え、75% を記録した。標本が小さいため(N=20、信頼区間なし)、削減幅の大きさは慎重に読むべきだが、方向は明確だった。だから多段階のデフォルトは gpt-5.2 none とし、high·xhigh は採用しなかった。

Q3 — ツールエージェントでは推論が多いほど安全か?

複数のツールをつなぐ計画ほど、より多い推論が信頼性を高めそうに思えた。そこで無ツール・1ツール・マルチツールが混ざる二十タスクで、再び gpt-5.2 の努力度別に gpt-4o と競わせた。

実際に分かれた地点は、推論の量ではなくツールを呼ぶ習慣だった。gpt-4o は ‘一般知識で答えよ’ という無ツールプロンプトでも計算機を呼び、通過率が 83.3% へ下がった一方、gpt-5.2 は無ツールでも 100% を保った。コストでも gpt-5.2 low が正答 1,000件当たり $2.77(gpt-4o $3.65 比 24% 安い)、マルチツール 100%、PTU +4.3% で先行した。ただし、このときの web_search は実際のウェブではなく、固定知識ベースの検索をモックしたものという限界がある。結論はまた同じだった — 少しの推論で十分であり、ツールのデフォルトは gpt-5.2 low、それ以上はトークンの無駄である。

現場のルール

推論努力度を「賢そうに見える」からという理由で上げてはいけない。コスト · 品質 · 遅延 · トークン構成を一緒に読み、努力度が実際に割に合う地点でだけトークンを追加すること。測定した三つのタスク形状で、high と xhigh は一度もデフォルトではなかった。

次へ

次の判断 · 次の実験

次の判断。 この結論は「測定したタスク形状」の中でだけ有効です。チェーンがもっと長くなったり実ツールが入ったりすれば曲線はまた動き得るため、ワークロード形状が変わったら再測定するのがルールです。

次の実験。 ここでの PTU 数値はトークンベースの推定です(ライブ負荷ではありません)。次の実験は実際の PTU デプロイでの負荷テスト — レート制限の調整 · キューイング · 並列バッチがスループットにどう作用するかです。

その最初の結果が出た。 exp004 — スピルオーバーポリシーシミュレーション(Phase 1)では、飽和負荷で先回りする(proactive)スピルオーバーが事後対応(reactive)よりキャッシュを守れるのかを競わせた。答えはほぼ引き分けだった — 先回りした側の定常状態キャッシュはむしろ 0.1657 pp 低く、スピルオーバーを一度も発動しなかった。本当の審判は、物理的に分離された 2デプロイ負荷テスト(Phase 2)の仕事である。

そしてその審判が出た。 exp005 — デュアルデプロイのスピルオーバー検証(Phase 2)では、物理的に分離されたキャッシュを持つ二つのライブデプロイで同じ問いを再現した。今回は差がむしろ広がった — 先回りした側の定常状態キャッシュは 0.9923 pp 低く(Phase 1 の約 6 倍)、コストも高くついた。トラフィックを二つに分けると、温めておいたプールが冷めてしまうからだ。二つの Phase はどちらも同じ結論に達した — キャッシュが物理的に分かれていれば、事後対応(reactive)の方が勝つ。

そしてデプロイではなく「キー」を分けてみた。 exp006 — キャッシュキーを細かく分けてもキャッシュはほぼそのままは、一つのデプロイの中で prompt_cache_key を 1個から 8個へ分けるとキャッシュが戻るのかを問うた。答えはまた「ほぼそのまま」だった — キー一つへ文書上限の 2倍(30 requests/min)を寄せても定常状態キャッシュヒットは 93–96% で持ちこたえ、8個に分けた利得は最大 2.52%p にとどまった。大きく分かれた軸はカーディナリティではなく保持ポリシーだった — 24h 保持が尾部レイテンシ(TTFT p95)を 106s→10s へ引き下げた。

続けて: 429 はエラーではなく回復シグナル — PTU 容量が “今はだめ” と言うとき、クライアントは次の手をどう決めるべきか?

出典 & 根拠の境界

  • 横断要約: results/summary.md(§3 ヘッドライン, §5 判断境界, §6 限界)。すべてのコストはベンチマークごとの benchmarks/0[123]-*/analysis.md から再引用。
