推論強度は割に合うのか — 仮説を覆した実測結果

執筆: Hyeonsang Jeon · Global Black Belt, Cloud & AI Apps

多段階推論では高い推論強度(reasoning_effort)が割に合うはずだと、私たちは事前登録した予測に記しました。ところが、三つのベンチマークで 1,080セルを測定した結果、その予測は覆りました。短い事実回答、多段階推論、ツールエージェントのいずれでも、最適解は high や xhigh ではありませんでした。強度を中間より上げても品質は変わらず、コストが増え、スループットが低下しました。本稿では、何を予想し、何が外れ、何をデフォルトにしたのかを、タイムラインと問いごとの回顧の二つの順序でたどります。結論だけでなく、そこに至る過程も残します。さらに、冒頭のコマンド一行からすぐに再現できます。

この記事で分かること

推論強度をいつ上げるべきか

最近のモデルには 推論強度 という設定があります。回答前にモデルが内部でどこまで推論するかを調整する値です。高いほど賢くなりそうに見えるため、迷うと上げたくなります。しかし、ワークロードによっては、回答が改善しなくても強度を上げることでコストと時間が増えます。 「念のため高くする」という運用は、不要な支出を招きかねません。

本稿では、推論強度が費用に見合う場合と、無駄になる場合を実測で切り分けます。対象は、一度で終わる短い事実回答、複数の段階を踏む多段階推論、ツールを呼び出すツールエージェントの三種類です。多くのサービスの処理は、いずれかに当てはまります。

モデルと強度を本番環境向けに選ぶ際の、デフォルトの決め方も示します。まず品質の合格線を決め、それを満たす設定の中から最も安く速いものを選びます。三つの実験がこの同じ原則にどう収束したのかを、予測と実測の差とともに説明します。

問い

新しい本番タスクで推論強度を上げることは、PAYG(ドル当たりの正答)と PTU(固定容量当たりの分当たり正答)の両方で割に合うのでしょうか。

根拠

三つのベンチマーク — 01 短い事実回答(Null case) · 02 多段階(Ceiling) · 03 ツールエージェント(Mixed) — を、それぞれ N=20 サンプル × R=3 反復、強度 {none, low, medium, high, xhigh} + gpt-4o ベースラインで測定しました。合計 1,080セルです。すべてのコストを 1,000件当たりに正規化し、ベンチマーク別の analysis.md から再引用しています。

判断

最適な (モデル, 強度) はタスク特性と消費モデルによって異なります。まず品質の合格線を決め、それを満たす設定の中から最も安く速いものを選びます。三つの実験に共通した結論は明確です — high や xhigh が最適解になった例はありません。 中間を超えると品質は変わらず、コストが増え、スループットが低下しました。

タイムライン

実験の経緯

実験は一度で結論に至ったわけではありません。下の五つの場面を日付順に追うと、予測がどこで外れ、デフォルトがどこで変わったのかが順に見えてきます。

  1. 2026年 5月以前 — 事前登録した予測。 測定前に、多段階タスクでは高い推論強度が品質を高め、そのコストを正当化するはずだと記録しました。結果を見てから説明を変えられないよう、gpt-5.2 の強度を none から xhigh までの五段階に固定し、gpt-4o ベースラインと比較しました。この事前登録した予測があるからこそ、その後に予測が覆った意味を明確にできます。
  2. 2026年 5月 — 短い事実回答ケース(01)、下限を測定。 まず、推論を必要としない短い事実回答でコスト特性の下限を確認しました。三つのベンチマークのうち、この下限だけは実測で測り直しています(360セルすべて実 Azure 呼び出し、fixture マーカーなし)。gpt-5.2 は推論を無効にした none ですでに正答率 95% に達して頭打ちとなり、gpt-4o(90%)を上回りました。正答 1,000件当たりのコストは $0.62 で、gpt-4o($0.74)より 16% 安い結果でした(リクエスト 1,000件当たりでも 12% 安い)。このため、短い事実回答の PAYG デフォルトを gpt-5.2 none としました。ただし、固定容量(PTU)では両モデルのスループット差が約 1% 以内で、実質的に同等でした。詳細は exp001 実験ノートで検証します。
  3. 2026年 5月 — 多段階ケース(02)、転換点。 ここでは推論強度を上げる効果が表れるはずでした。しかし、gpt-5.2 は推論を無効にした基本状態(none)で二十問すべてに正解し、事前登録した予測は覆りました。正答 1,000件当たりのコストは gpt-4o の $1.06 から $0.62 へ 42% 下がり、PTU では分当たり正答が 32.5% 増えました。一方、強度をさらに上げても品質は変わりませんでした。そのため、多段階のデフォルトを gpt-5.2 none とし、それ以上の強度は採用しませんでした。差を生んだのは強度ではなく、モデルの変更でした。詳細は exp002 実験ノートで検証します。
  4. 2026年 5月 — ツールエージェントケース(03)、意外な発見。 最後は、ツール不要・1ツール・マルチツールを含むエージェントです。予想外だったのは gpt-4o でした。「一般知識で答える」というプロンプトでも計算機を呼び出し、ツール不要タスクの通過率が 83.3% まで下がりました。一方、gpt-5.2 は low でマルチツール 100% を維持し、正答 1,000件当たり $2.77(gpt-4o $3.65 比 24% 安い)を達成しました。このため、ツールエージェントのデフォルトを gpt-5.2 low としました。ただし、low を超えるとスループットは medium で 8.5%、xhigh で 10.8% 低下し、利点が薄れました。詳細は exp003 実験ノートで検証します。
  5. 2026年 7月 — 根拠と再現の隔たりを解消。 測定後には、別の課題が残りました。「デプロイへの関心は高いのに、README と検証手段が十分ではない」というフィードバックです。実際、新しい訪問者は編集可能インストールの失敗(PEP 660)や動かない実行コマンドで行き詰まりました。そこで、資格情報なしで一行で実行できる検証(verify_setup.sh)、実験別のガイドカード、requirements.txt の分離を追加しました。冒頭の 10秒再現はその成果です。

問いごとの回顧

なぜ実験し、何を学んだのか

ここからは同じ結果を問いごとに整理し、「何を知りたかったのか」から三つの問いに答えます。

Q1 — 短い事実回答に推論は必要か?

まず、一度で答えが出る短い事実タスク(抽出·整形·分類·音訳·算術)では、推論強度を有効にする理由がないと予測しました。この下限は実測で確認しています — 360セルすべてが実際の Azure Foundry 呼び出しで、fixture マーカーはなく、評価モデルによる採点も 360/360 です。

この予測は覆らず、実測と一致しました。gpt-5.2 は推論を無効にした none ですでに正答率 95% に達して頭打ちとなり、gpt-4o(90%)を上回りました。正答 1,000件当たり $0.62 で、gpt-4o($0.74)より 16% 安い結果でした(リクエスト当たりでも 12% 安い)。強度を xhigh まで上げても隠れた推論トークンは 0 近くにとどまり、品質もコストもほとんど変わりませんでした。短い事実回答のデフォルトは gpt-5.2 none です。詳細は exp001 実験ノートで確認できます。

Q2 — 多段階では強度を上げると割に合うのか?

事前登録した予測は単純でした。複数の段階を要する問題では、high や xhigh による品質向上がコスト増を正当化するはずだ、というものです。これを確かめるため、gpt-5.2 の五段階の強度(none から xhigh まで)を gpt-4o ベースラインと並べ、二十問を三回ずつ繰り返して比較しました。

実測結果は予測を覆しました。gpt-5.2 は none ですでに 100% 正解し、正答 1,000件当たり $0.62 で gpt-4o($1.06)より 42% 安く、PTU では分当たり正答が 32.5% 多い結果でした。gpt-4o も予想を上回り、事前登録した予測の 30–60% の範囲を超える 75% を記録しました。標本が小さいため(N=20、信頼区間なし)、削減幅の大きさは慎重に解釈する必要がありますが、方向は明確でした。多段階のデフォルトを gpt-5.2 none とし、high·xhigh は採用しませんでした。

Q3 — ツールエージェントでは推論が多いほど安全か?

複数のツールをつなぐ計画では、より多くの推論が信頼性を高めると予測しました。そこで、ツール不要・1ツール・マルチツールを含む二十タスクで、gpt-5.2 の強度別結果を gpt-4o と比較しました。

差が表れたのは推論量よりも、ツールを呼び出す傾向でした。gpt-4o は「一般知識で答える」というツール不要のプロンプトでも計算機を呼び出し、通過率が 83.3% に下がりました。一方、gpt-5.2 はツール不要タスクでも 100% を保ちました。gpt-5.2 low は正答 1,000件当たり $2.77(gpt-4o $3.65 比 24% 安い)、マルチツール 100%、PTU +4.3% でした。ただし、この実験の web_search は実際のウェブ検索ではなく、固定知識ベース検索のモックです。少量の推論で十分だったため、ツールエージェントのデフォルトを gpt-5.2 low とし、それ以上は採用しませんでした。

現場のルール

「賢そうに見える」という理由だけで推論強度を上げてはいけません。コスト · 品質 · 遅延 · トークン構成を併せて確認し、強度が実際に割に合う地点でのみトークンを追加します。測定した三つのタスク特性では、high と xhigh は一度もデフォルトになりませんでした。

次へ

次の判断 · 次の実験

次の判断。 この結論が当てはまるのは、今回測定したタスク特性の範囲です。チェーンが長くなったり、実際のツールが加わったりすれば曲線は変わり得ます。ワークロード特性が変わるたびに再測定する必要があります。

次の実験。 ここでの PTU 数値はトークンベースの推定です(ライブ負荷ではありません)。次は実際の PTU デプロイで負荷をかけ、レート制限の調整、キューイング、並列バッチがスループットに与える影響を測定します。

最初の結果。 exp004 — スピルオーバーポリシーシミュレーション(Phase 1)では、飽和負荷で proactive スピルオーバーが reactive よりキャッシュを維持できるかを比較しました。結果はほぼ同等でした — proactive の定常状態キャッシュは 0.1657 pp 低く、スピルオーバーは一度も発動しませんでした。最終判断には、物理的に分離した 2デプロイでの負荷テスト(Phase 2)が必要でした。

ライブ環境での検証。 exp005 — デュアルデプロイのスピルオーバー検証(Phase 2)では、物理的に分離したキャッシュを持つ二つのライブデプロイで同じ問いを検証しました。差はさらに広がり、proactive の定常状態キャッシュは 0.9923 pp 低く(Phase 1 の約 6 倍)、コストも高い結果でした。トラフィックの分割によって、温めたプールが冷えたためです。二つの Phase はともに、キャッシュが物理的に分かれている場合は reactive が優位という結論でした。

次にキャッシュキーを分割。 exp006 — キャッシュキーを細かく分けてもキャッシュはほぼそのままでは、一つのデプロイ内で prompt_cache_key を 1個から 8個に分けるとキャッシュが改善するかを検証しました。結果は再び「ほぼそのまま」でした — 一つのキーに文書上限の 2倍(30 requests/min)を集中させても定常状態キャッシュヒットは 93–96% を維持し、8個に分けた利得は最大 2.52%p でした。差を生んだのはカーディナリティではなく保持ポリシーで、24h 保持により尾部レイテンシ(TTFT p95)が 106s→10s に低下しました。
