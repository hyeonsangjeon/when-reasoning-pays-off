运营随笔 · 从 GPT-4o 到 GPT-5.x 的容量评估

不要仅凭模型名称来重新评估推理迁移的容量

把一个工作负载从 gpt-4o 迁移到 GPT-5.x 推理模型， 并不是一次只看一个数字的迁移。真正该问的问题不是“新模型是不是 更重？”，而是“请求形态、输出构成、隐藏的推理 token、缓存命中率 以及响应上限分别发生了什么变化？”

问题

在按 PTU 为 GPT-5.x 评估一个 GPT-4o 工作负载的容量之前，必须重新测量哪些指标？

证据

Microsoft Learn 给出了归一化 TPM 的公式；OpenAI 记录了推理 token 的计量方式。

决策

依据实测的 token 形态来评估容量，而不是依据对“5.x”这一家族层面的笼统假设。

官方行为 · 归一化 TPM

容量评估公式关乎 token 形态

Microsoft Learn 通过把流量换算为归一化 TPM 来评估 PTU 需求。 输入项包括峰值 RPM、平均 prompt token、平均生成的 output token、 缓存率、模型的输出对输入比率，以及模型每 PTU 的 Input TPM 值。

公式：

normalized_tpm = rpm × (prompt_tokens × (1 - cache_rate) + output_ratio × output_tokens)

raw_ptu = normalized_tpm ÷ input_tpm_per_ptu

正是这条公式说明了为什么家族层面的捷径会产生误导。一个模型可能 具有更重的输出比率，但每 PTU 的 Input TPM 仍然高于上一代模型。 答案取决于你的工作负载实际的 prompt、输出和缓存特征。

运营视角 · 迁移中会变化的因素

四个驱动因素决定迁移是否合适

1. 输出权重

对于 GPT-4.1 及更新的模型，Microsoft Learn 指出 output token 在利用率计算中带有特定于模型的 input-token 权重。

2. 隐藏的推理

OpenAI 将推理 token 记录为不可见的输出侧 token。请从 output_tokens_details.reasoning_tokens 测量它们。

3. 缓存率

Microsoft Learn 指出，缓存的 prompt token 会从 PTU 利用率中扣除。因此前缀形态的变化可能会改变容量评估结果。

4. 响应上限

记录 max_output_tokens。本仓库把过大的上限视为一个需要验证的 PTU 准入风险假设，而不是一个可以靠猜测得出的值。

仅看可见输出的那几行，并不能支撑“GPT-5.x 总是比 GPT-4o 效率更低” 这样的笼统结论。推理那几行揭示了陷阱：一旦出现隐藏的推理输出， 除非对缓存和响应策略进行测量与调优，否则相同的可见答案可能需要 多得多的归一化 TPM。

运营者清单 · 在购买容量前先重新测量

把迁移当作一次测量，而不是一次改名

  1. 固定任务组合。在各个模型单元之间，保持 prompt、工具、schema、检索位置以及样本分布在字节级别上稳定一致。
  2. 测量可见输出。对比迁移前后可见 output token 的均值和 p95。
  3. 测量推理输出。采集 reasoning_tokens；不要从最终答案文本去推断它。
  4. 测量缓存率。按 cache-key 分桶记录 cached_tokens / prompt_tokens，尤其是在 ReAct 或工具 schema 发生变化之后。
  5. 合理设定上限。根据一个有代表性的“可见加推理”百分位来设置 max_output_tokens，再对罕见的长答案使用逐次调用的覆盖值。
  6. 最后才评估 PTU。用当前的模型表和你实测的工作负载形态来套用归一化 TPM 公式。
